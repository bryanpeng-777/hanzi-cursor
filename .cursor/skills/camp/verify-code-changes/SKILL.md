# Verify Code Changes

## Overview

通过"理解需求 → 添加日志 → 用户运行 → 双维度分析（逻辑 + 业务）→ 修复 → 循环"的闭环流程，系统化验证代码改动是否正确实现了预期目标。

## Workflow

### Phase 0: 理解业务需求（首次执行，最重要）

在注入任何日志之前，必须先搞清楚「这次改动要实现什么业务目标」。

**Step 1：通过 diff 推断 + 代码索引定位**

运行 `git diff HEAD` 或 `git diff`，阅读改动内容，尝试推断：
- 这次改动涉及哪个业务功能/模块？
- 预期的用户行为或系统行为是什么？
- 改动的核心逻辑点在哪里？

推断出业务功能后，**查阅代码位置索引**锁定注入日志的准确位置：

> 📍 读取 `/Users/bryanpeng/.claude/skills/camp/code-locator/CODE_MAP.md`，
> 根据改动涉及的业务功能匹配相关模块路径，在对应文件中注入调试日志，不做全局搜索。

**Step 2：如有不确定，主动向用户补充询问**

如果从 diff 无法完整推断出业务目标，或存在关键歧义，必须向用户提问，例如：
- 「这次修改的预期效果是什么？比如：用户做了 X 操作后，应该看到 Y 结果」
- 「这个条件判断的业务含义是什么？什么情况下应该走 true 分支？」
- 「这个参数的合法取值范围是什么？」

> ⚠️ 不要假设业务语义，有疑问就问清楚再继续。

**Step 3：形成「业务验证清单」**

在开始注入日志前，先列出本次验证的业务目标，格式如下：

```
业务验证目标：
- [ ] 场景 A：用户执行 X 时，系统应该做 Y
- [ ] 场景 B：当条件 Z 成立时，结果应为 W
- [ ] 边界场景：当 ... 时，不应该触发 ...
```

这个清单将在 Phase 1 分析日志时逐项对照。

在注入业务调试日志之前，先用 Ralph Loop 确保代码**编译通过**，排除语法/类型错误：

> 📍 读取并执行 `/Users/bryanpeng/.claude/skills/ralph-loop/SKILL.md`
>

> - Prompt：「验证 [本次改动描述] 的代码实现，确保编译通过」
> - 退出条件：`compilation`（iOS）或 `dart-analyze`（Flutter）
> - 最大重试：3

Ralph Loop 通过后，才继续进入 Phase 1 的业务日志验证。

### Phase 1: 注入调试日志

基于业务验证清单，确定需要在哪些位置打日志：

1. **业务入口**：对应每个业务场景的触发点
2. **关键判断**：影响业务走向的条件分支
3. **核心数据**：业务关键参数的实际值
4. **最终结果**：影响用户感知的状态/输出

**Dart/Flutter 日志格式**：
```dart
debugPrint('[VerifyTag] 函数名 entered: param=$param');
debugPrint('[VerifyTag] condition=$condition, branch=xxx');
debugPrint('[VerifyTag] result=$result');
```

**Swift 日志格式**：
```swift
print("[VerifyTag] 函数名 called: param=\(param)")
print("[VerifyTag] result=\(result)")
```

**Objective-C 日志格式**：
```objc
NSLog(@"[VerifyTag] 函数名 called: param=%@", param);
NSLog(@"[VerifyTag] result=%@", result);
```

注入完成后，输出「运行指引」，然后**等待用户提供日志**，不要自行继续。

---

### 运行指引（注入日志后必须输出）

在等待用户运行之前，必须输出一份清晰的操作步骤，格式如下：

```
📋 运行指引：请按顺序执行以下操作来覆盖所有业务场景

场景 1：[场景名称，如：正常登录流程]
  操作步骤：
    1. 打开 xxx 页面
    2. 点击 xxx 按钮
    3. 输入 xxx 数据
  预期日志关键字：[VerifyTag] xxx

场景 2：[场景名称，如：Token 过期场景]
  操作步骤：
    1. 先让 Token 过期（如：修改本地时间 / 清除缓存）
    2. 触发 xxx 操作
  预期日志关键字：[VerifyTag] xxx

场景 3：[边界场景，如：空数据场景]
  操作步骤：
    1. ...
  预期日志关键字：[VerifyTag] xxx

⚠️ 提示：每个场景运行后请收集日志，全部场景完成后一次性提供给我分析。
```

**运行指引的编写原则**：
- 步骤具体到「点哪里、输入什么、怎么构造特殊场景」
- 对于难以手动触发的场景（如网络异常、特定数据状态），给出构造方法（mock 数据、修改本地存储、注释代码等）
- 对每个场景说明「预期会出现哪条 [VerifyTag] 日志」，方便用户判断场景是否成功触发

---

### Phase 2: 读取日志并双维度分析

当用户提供日志文件路径或粘贴日志内容时：

1. **读取日志**：文件路径用 Read 工具读取，文本内容直接分析
2. **过滤关键日志**：找出带 `[VerifyTag]` 的条目，按时序排列

**Step 0：场景覆盖度检查**

先确认运行指引中的每个场景是否都有对应日志出现：
- 有日志 → 场景已触发，继续深入分析
- 缺少日志 → 该场景未被触发，提示用户补充运行，或判断是否因 bug 导致日志未输出

**双维度验证**：

**维度一：逻辑正确性**
- 日志是否按预期顺序出现？
- 参数值是否在合理范围内？
- 条件分支走向是否符合代码意图？
- 有无异常、崩溃、空值等错误信息？

**维度二：业务正确性**（对照 Phase 0 的业务验证清单）
- 每个业务场景是否都被触发到？
- 业务关键数据是否符合需求定义？
- 用户预期的结果是否被正确实现？
- 边界/异常场景处理是否符合业务规则？

**给出判断**：
- ✅ **两个维度均通过**：描述验证结论，继续 Phase 4
- ❌ **存在问题**：区分是逻辑问题还是业务理解偏差，明确指出后继续 Phase 3

---

### Phase 3: 修复并再次等待

1. 根据分析结果修复代码：
   - **逻辑问题**：修正代码实现
   - **业务理解偏差**：与用户确认业务规则后再修改
2. 如有必要，调整调试日志以覆盖新的验证点
3. 告知用户修复了什么，需要再次运行，**等待新的日志**

> 重复 Phase 2 → Phase 3，直到两个维度均验证通过。

---

### Phase 4: 清理调试日志

验证通过后：

1. 删除所有带 `[VerifyTag]` 的调试日志行
2. 检查其他因验证临时添加的代码（临时 print、NSLog 等）
3. 确认代码恢复干净状态

最后，发送一句鼓舞人心的话，结束 skill。

## Analysis Checklist

### 场景覆盖度
- [ ] 运行指引中的每个场景都有对应日志出现
- [ ] 边界场景（空数据、异常、权限等）已触发

### 逻辑正确性
- [ ] 入口日志出现（函数被正确调用）
- [ ] 参数值符合预期
- [ ] 条件分支走向正确
- [ ] 循环/异步逻辑按预期执行
- [ ] 无异常日志或错误信息

### 业务正确性
- [ ] 每个业务场景的关键数据值符合需求定义
- [ ] 用户感知的最终结果符合预期
- [ ] 边界/异常场景按业务规则处理

## Quick Reference

| 阶段 | 动作 | 结束条件 |
|------|------|----------|
| Phase 0 | 读 diff + 询问用户，形成业务验证清单 | 清单明确后继续 |
| Phase 1 | 注入调试日志 | 等待用户提供日志 |
| Phase 2 | 双维度分析（逻辑 + 业务） | 通过→Phase 4；失败→Phase 3 |
| Phase 3 | 修复代码，更新日志 | 等待用户提供新日志 |
| Phase 4 | 清理所有调试日志，发鼓励语 | 结束 |
