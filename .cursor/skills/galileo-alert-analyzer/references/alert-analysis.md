# 伽利略告警体系参考文档

## 告警分级定义

| 级别 | 定义 | 影响范围 | 处理要求 |
|------|------|---------|---------|
| P0 | 系统致命性故障，核心业务功能完全不可用 | 用户无法正常使用核心功能 | 立即响应（分钟级） |
| P1 | 严重业务异常，部分功能受损但不影响主流程 | 非核心业务功能异常，用户体验显著下降 | 工作日立即响应 |
| 其它 | 潜在风险事件，业务功能正常但存在隐患 | 用户体验轻微影响 | 计划性处理，可延迟至下个迭代 |

## 漏斗模型（Start → Step → End）

### 各阶段含义

| 阶段 | 描述 | 典型告警策略 |
|------|------|------------|
| Start | 漏斗起始锚点，标记功能发起或单次离散失败事件 | 量级波动（对比前1分钟或前1天） |
| Step | 中间关键流转节点，记录步骤执行状态 | 转化率波动（时间环比、版本环比） |
| End | 流程最终交付结果（成功0/失败-1） | 成功率/完成率跌幅告警 |

### 流量分级阈值

| 流量区间 | 告警阈值 |
|---------|---------|
| > 100w | 2% 波动 |
| 10w ~ 100w | 2.5% 波动 |
| 6k ~ 10w | 3% 波动 |
| 小流量（< 6k） | 经验值，通常 30%~60% |

## 典型告警场景与排查思路

### 场景零：超频告警（X小时大于N次）

**告警示例**：`【核心业务】大图加载1小时大于100次`

**告警卡片特征**：
- 指标字段：`<指标名>-start(SUM): 112（最大阈值: 100）`
- 触发维度：`tags.imageUrl`、`tags.api` 等，表示被超频访问的具体资源
- TOP N：卡片中附带按超频次数排序的 TOP N 维度值，直接指向问题对象

**可能根因**：
1. 页面生命周期方法（如 `viewWillAppear`）每次都触发图片加载，而非懒加载
2. 列表/ScrollView 滚动时重复触发，缺少复用/缓存判断
3. 定时器或轮询逻辑没有去重，重复下载相同图片
4. 内存缓存失效（如 NSCache 被清空），导致同一图片反复走网络请求
5. 某个页面在短时间内被反复进入/退出

**排查步骤**：
1. 查看 TOP N 中的 `imageUrl`，确认该图片属于哪个页面（通过 URL 中的业务 ID 判断）
2. 搜索该图片加载逻辑所在代码，检查调用频率
3. 查看是否有缓存命中判断，是否有防重复加载机制
4. 结合 Trace Session 查看用户操作路径，确认高频触发的页面

### 场景一：Start 量级骤降

**可能根因**：
1. 代码被删除或注释（检查 git diff）
2. 入口条件变更（灰度开关、AB 实验、权限判断）
3. 新增 early return 导致代码路径未触达
4. 功能入口被隐藏或移除

**排查步骤**：
1. 搜索 `moduleName` 对应的 Start 上报代码位置
2. 查看告警时间点前后的 git 变更
3. 检查是否有条件判断包裹了上报代码
4. 对比上一版本的代码逻辑

### 场景二：错误类 Start 量激增

**可能根因**：
1. 新上线的代码引入了新的错误路径
2. 后端接口返回新的错误码
3. 某个外部依赖（网络、存储、第三方 SDK）异常
4. 并发/竞态条件导致的偶发错误变为高频错误

**排查步骤**：
1. 查看 `subModuleName`/`groupName` 字段，确认是哪个具体 API 或子功能
2. 分析错误 status 码的含义
3. 通过伽利略平台的"日志聚合"查看 TOP 错误码分布
4. 关联到 Trace，查看错误发生时的上下文

### 场景三：转化率骤降（Start→Step 或 Step→End）

**可能根因**：
1. 某个中间步骤的逻辑条件发生变化
2. 接口调用失败率升高
3. 用户流程中有新增的阻断性错误
4. Step 的上报条件变严格（原本都上报，现在只有特定情况才上报）

**排查步骤**：
1. 确认是 Start→Step1 还是 Step→End 的转化率下降
2. 在代码中找到对应 Step 的上报位置
3. 分析 Step 上报的前置条件
4. 查看该 Step 的 status 分布（是失败率升高还是 Step 上报量减少）

### 场景四：End 成功率跌幅

**可能根因**：
1. 后端接口返回错误率升高
2. End 判断成功的条件逻辑变更
3. 整个业务流程最后一步的异常
4. 网络超时、服务不可用

**排查步骤**：
1. 查看 End 上报的 status 判断逻辑
2. 关联后端接口的伽利略数据（通过 Trace 跳转后端 Session）
3. 分析 End 失败时对应的 Step 状态，缩小范围

### 场景五：量级归零

**可能根因**：
1. 上报代码被完全删除
2. 功能入口被彻底移除（如 A/B 实验关闭）
3. 整个模块被下线

**排查步骤**：
1. 直接搜索 `moduleName` 确认上报代码是否还存在
2. 查看最近是否有涉及该模块的大规模重构
3. 检查是否有全局开关控制该功能

## Trace/Log 联动排查

当需要深入排查时，利用伽利略平台的 Trace 能力：

### 从告警跳转到 Trace
1. 在告警详情页点击日志条目
2. 通过"日志聚合"查看 TOP 错误码分布，找代表性日志
3. 从日志直接跳转到关联的 Trace Session

### Trace Session 包含的关键信息
- **界面信息**：用户报错时停留的具体页面（View）
- **关键任务**：报错前后的核心动作（路由跳转、API 调用）
- **协议详情**：具体报错 Span 的错误码、耗时
- **环境信息**：App 生命周期状态、网络状态

### 跨端排查
- 终端 → 后端：点击报错协议 Span，跳转至后端伽利略视图
- 终端 → H5/Hippy：通过 `aegis_session_id` 关联 Web 页面 Trace
- 后端 → 终端：后端开发者可通过入口跳回终端 Session
