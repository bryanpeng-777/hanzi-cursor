# Bugfix

## Overview

帮助用户进行系统化的bug修复流程，确保问题被正确理解和彻底解决。

## 工作流程

### 步骤0: 查询知识库

在分析问题之前，先用 **knowledge-retriever 技能**扫描历史知识和踩坑记录：

> 📍 读取 `/Users/bryanpeng/.claude/skills/knowledge-retriever/SKILL.md`，
> 以 bug 描述中的模块名、症状关键词作为输入，执行检索流程。
> 命中记录时，将摘要结论带入后续分析步骤；未命中时直接进入步骤 1。

---

### 步骤1: 理解问题

首先收集bug的完整信息：

**如果用户提供TAPD bug ID**：
- 使用TAPD API获取bug详情
- 提取关键字段：bug标题、描述、复现步骤、预期结果、实际结果、附件、相关日志
- 记录bug ID，用于后续提交

**如果用户直接描述bug**：
- 要求用户提供清晰的问题描述
- 确认复现步骤
- 确认预期行为和实际行为
- 询问相关日志、截图或辅助信息

**关键问题清单**：
1. Bug的具体表现是什么？
2. 如何复现这个问题？
3. 预期的正确行为是什么？
4. 是否有相关的错误日志或截图？
5. 这个问题只出现在特定场景/设备/环境吗？

### 步骤2: 分析根因

**铁律：没有证据，不得提出修复方案。**

根因分析必须按以下顺序进行，不可跳步：

**阶段 A：收集诊断证据**

在提出任何假设之前，先让代码说话：
1. 完整阅读错误堆栈，逐行理解，不跳过任何 warning
2. 查看最近的 git 变更（`git log --oneline -10`），确认是否有引入此问题的提交
3. 对于多层调用链的问题，**必须加诊断日志**逐层确认数据流：
   ```objc
   // 在每个关键层边界加日志，确认数据在哪层出错
   [[WEGLogBizManager sharedManager] commonLog:OTLogLevelInfo
                                   messageName:@"debug_layer1_input"
                                    moduleName:@"YourManager"
                                          type:OTCommonLogTypeBefore
                                    attributes:@{@"data": data ?: @"nil"}];
   ```
   运行一次收集证据，再分析哪层出了问题，然后再提出修复。

**阶段 B：提出原因假设**

基于证据（不是猜测）提出可能原因：

```
可能原因1: [描述]
  证据: [具体的日志/代码行/堆栈帧支撑，不能写"可能是"]
  可能性: [高/中/低]

可能原因2: [描述]
  证据: [具体证据]
  可能性: [高/中/低]

推荐分析:
  - 根据证据，最可能的原因是: [选择]
  - 理由: [基于证据的推断]
```

**禁止出现**：`"应该是"`、`"可能是"`、`"感觉是"` 等无证据表述。

**3次修复失败铁律**：如果已经修复了 3 次仍未解决，必须停下来，向用户说明情况，重新质疑根因假设或整体方案，不得继续盲目尝试第 4 次修复。

### 步骤3: 定位代码

**首先查阅代码位置索引**（避免全局搜索）：

> 📍 读取 `/Users/bryanpeng/.claude/skills/camp/code-locator/CODE_MAP.md`，
> 根据 bug 涉及的业务功能关键词匹配相关模块路径，命中后直接读取对应文件。
> 未命中时再使用以下方式补充定位，并将新词条补录到 CODE_MAP。

补充定位方式（CODE_MAP 未命中时使用）：

1. **错误堆栈分析**: 直接定位到具体文件和行号
2. **关键字搜索**: 使用Grep搜索相关函数名、变量名、错误信息（限定在 CODE_MAP 推断的目录范围内）
3. **文件关联**: 查找引用了问题模块的文件
4. **代码导航**: 使用Task tool的Explore agent进行深度探索

**定位输出**：
```
定位到的代码位置:
  文件: [文件路径]:[行号]
  代码片段:
    [相关代码片段]

  相关文件:
    - [文件路径1]
    - [文件路径2]
```

### 步骤4: 设计修复方案

针对最可能的原因，设计修复方案：

**方案内容**：
- 修复的具体步骤
- 修改的文件和位置
- 修改前后的代码对比
- 为什么这个方案可以解决问题

**验证方法**：
- 如何验证修复有效
- 是否需要单元测试
- 是否需要手动测试场景

### 步骤5: 用户确认

在实施修复前，向用户确认：

1. 确认根因分析是否准确
2. 确认修复方案是否合理
3. 询问是否有其他考虑或约束

只有用户确认后，才进行下一步。

### 步骤6: 实施修复

使用Edit或Write工具修改代码：

**原则**：
- 最小化修改，只改动必要的代码
- 保持代码风格一致性
- 不引入不必要的重构
- 添加必要的注释说明修复原因

**修改前**：
```dart
[原代码]
```

**修改后**：
```dart
[修复后代码]
```

### 步骤7: 验证修复（Ralph Loop）

代码实现完成后，**立即启动 Ralph Loop** 做编译验证：

> 📍 读取并执行 `/Users/bryanpeng/.claude/skills/ralph-loop/SKILL.md`
>
> 传入参数：
> - Prompt：「修复 [bug描述]，确保 [具体目标]」
> - 退出条件：`compilation`（iOS/OC/Swift）或 `dart-analyze`（Flutter/Dart）
> - 最大重试：3

Ralph Loop 通过后，进行 Runtime 验证：
1. 在关键路径注入 `NSLog(@"[verify] ...")` 日志
2. 告知用户触发场景步骤，等待用户运行
3. 用户确认日志符合预期后，删除所有验证日志

### 步骤8: 提交代码

使用项目的git-commit规范提交代码：

**提交信息格式**：
```
fix(模块): [简短描述，不超过20字] --bug=<bug_id>
```

**调用方式**：
```bash
使用git-commit skill生成提交信息
```

### 步骤9: 自动判断并记录到知识库

提交完成后，AI 主动评估本次 bug 的记录价值，**满足以下任一条件则直接执行 knowledge-collector，无需用户开口**：

**自动触发条件**（满足任一）：
- 排查过程超过 3 步，或经历了错误方向的分析
- 根因涉及：多线程、生命周期、初始化顺序、内存管理、平台差异等易复发领域
- 修复方案有反直觉之处（不是一眼能看出来的解法）
- 同类问题在本次对话中出现过多次

**静默跳过条件**（同时满足则跳过）：
- 根因显而易见（如空值未判断、typo、缺少 import）
- 修改只有 1-2 行且逻辑直接

执行时告知用户：「检测到本次修复有记录价值，正在自动写入知识库...」，然后读取并执行 `/Users/bryanpeng/.claude/skills/knowledge-collector/SKILL.md`。

## 重要提示

1. **不要假设**: 基于实际证据进行分析，不要猜测
2. **充分理解**: 确保完全理解问题后再开始修复
3. **最小修改**: 避免过度修改和无关重构
4. **充分验证**: 确保修复有效且无副作用
5. **规范提交**: 使用项目约定的提交信息格式

## 项目特定规范

根据工作目录自动识别项目：
- **social-ios**: iOS原生项目，使用Swift/Objective-C
- **flutter_module**: Flutter混合模块，使用Dart

不同项目的工具链和测试方法会有差异，需要根据项目类型调整验证步骤。
