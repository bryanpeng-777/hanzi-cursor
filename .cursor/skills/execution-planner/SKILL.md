# execution-planner

执行方式决策的独立 skill。接收一个标准化的 TaskSpec，结合历史纠正台账，决定「用哪种方式执行」，输出可直接消费的 Step3令牌。

---

## TaskSpec 标准结构

调用方在传入前必须构造以下结构（字段缺失时可标注「未知」或省略可选项）：

```
任务类型: bug修复 | 功能开发 | 调研 | 埋点检查 | 文档更新 | 配置变更 | 告警分析 | 代码定位 | 其他
任务描述: <原始任务描述>
目标: <一句话，要做什么>
完成标准: <一句话，怎样算做完>
关键约束: <一句话，边界条件>（可选）
关键词: [keyword1, keyword2, ...]
涉及模块: [module1, ...]（可选）
强制步骤: (可选) 调用方声明的必须步骤，格式与 Step3令牌行一致，每行一项，例：
  - 🔒 [人工] TDD合约 — 写测试文件全FAIL后独立commit
  - 🔒 [subagent] test-assistant — 录入测试台账
强制顺序: (可选) 步骤名称间的先后约束，例：TDD合约 < 实现代码 < ralph-loop < 人工验收
```

> **注意**：`强制步骤` 由调用方（如 big-req-harness）注入，代表项目级必须步骤，不可被台账偏好或优先级规则覆盖。

## 执行流程

### Step EP-1：加载台账 & 匹配历史纠正

读取台账文件，按以下规则匹配：

1. 提取 TaskSpec 中的 `任务类型` + `关键词` 字段
2. 遍历台账中所有条目的「匹配关键词」字段
3. 有重叠关键词 → 命中，优先按纠正后清单生成；在清单上方注明「📌 参考历史纠正：`<纠正说明>`」
4. 无命中 → 按下方默认编排优先级生成

### Step EP-2：生成执行清单

**强制步骤优先处理**（在进入编排优先级之前）：

若 TaskSpec 含 `强制步骤` 字段：
1. 将这些步骤**原样插入**执行清单，标注 `🔒`，不受台账偏好覆盖、不受编排优先级替换
2. 按 `强制顺序` 声明排定位置（如无声明，按 `强制步骤` 列表顺序依次排入）
3. execution-planner 动态决策的步骤（代码定位、AI分析等）填充到强制步骤之间的空隙
4. 展示格式：`🔒 [人工] TDD合约 — 测试文件全FAIL后独立commit`

**编排优先级**（按顺序尝试，找到合适的即用）：

```
① 本地 agent / workflow（优先）
      ↓ 没有合适的
② 本地 skill（通过对应 agent/workflow 调用；若无对应 agent，才直接 Read SKILL.md）
      ↓ 没有合适的
③ Knot 平台 / Skill 平台查找外部技能
      ↓ 都没有
④ AI 自主分析（MCP工具 + WebSearch + 推理）
      ↓ 必须人工介入时
⑤ 人工步骤（仅作为必要补充）
```

**类型标注说明**：

| 类型标注 | 含义 |
|---------|------|
| `[agent]` | 通过 Task 工具拉起本地某个子 Agent |
| `[workflow]` | 通过 Task 工具拉起本地某个 Workflow |
| `[技能]` | 直接 Read 某个本地 SKILL.md 流程执行 |
| `[MCP工具]` | 直接调用 MCP 工具（Galileo、Craft、GitHub 等） |
| `[AI分析]` | 在当前上下文完成推理、搜索、输出结论 |
| `[人工]` | 需要用户手动完成的步骤 |

**任务类型参考映射**（仅参考，最终按优先级和 TaskSpec 灵活生成）：

| 任务类型 | 常见清单构成 |
|---------|------------|
| bug修复 | `[agent] dev-assistant` → `[人工] 编译验证` |
| 告警分析 | `[agent] 伽利略告警登记小助手` 或 `[MCP工具] Galileo` → `[AI分析] 根因推断` |
| 代码定位 | `[技能] code-locator` |
| 埋点检查 | `[技能] galileo-spec-checker` |
| 调研 | `[agent] product-assistant` 或 `[AI分析] WebSearch + WebFetch` |
| 文档更新 | `[agent] 文档小助手` 或 `[MCP工具] Craft` |
| 配置变更 | `[AI分析] 读文件 → 修改 → 验证` |
| 功能开发 | 按优先级编排（① agent → ② skill → ④ AI分析），不使用固定模板 |
| UI界面优化 | `[workflow] ui-design-workflow` |
| 跨域复杂任务 | 多个 `[agent]` / `[workflow]` 按依赖顺序排列 |

### Step EP-3：展示清单，等待用户确认

展示格式：

```
🔧 执行清单（共 N 步）：
  （若命中历史纠正）📌 参考历史纠正：「<纠正说明>」

  [ ] 1. [类型] 名称 — 说明
  [ ] 2. [类型] 名称 — 说明
  ...

💬 说「改第N步」调整某项，可反复修改直到满意。
🚀 确认无误后说「开始」，才会正式进入执行阶段。
⚠️  在你明确说「开始」之前，无论讨论多少轮，都不会提前执行任何步骤。
```

**处理用户纠正**：

- 用户说「改第 N 步」→ 更新对应项，重新输出完整清单，**暂存纠正内容到内存**（格式见下方）
- 用户说「开始」→ 进入 Step EP-4
- 其他隐含同意词（「好」「可以」「没问题」）→ 回复「清单已确认，说「开始」即可正式执行」，**不进入 Step EP-4**

**暂存格式**（内存中保留，待 Step EP-4 写入）：

```
纠正记录（待写入）：
- 记录时间：YYYY-MM-DD HH:MM
- 匹配关键词：<从 TaskSpec 的任务类型和关键词提取，逗号分隔>
- 原清单：...
- 纠正后清单：...
- 纠正说明：<用户纠正意图，一句话概括>
```

### Step EP-4：写入纠正记录 & 输出 Step3令牌

**第一步（不可跳过）**：检查内存中是否有暂存纠正记录：
- 有 → 追加写入台账文件，输出 `✅ 纠正记录已写入台账`
- 无 → 跳过写入

**台账追加格式**：

```markdown
---

### <任务描述简短摘要>
- 记录时间：YYYY-MM-DD HH:MM
- 匹配关键词：<逗号分隔>
- 原清单：
  1. [类型] 名称 — 说明
- 纠正后清单：
  1. [类型] 名称 — 说明
- 纠正说明：<一句话>
```

**第二步**：输出 Step3令牌（供调用方的 Step 4 消费）：

```
🚦 Step3令牌：
  [ ] 1. [类型] 名称 — 说明
  [ ] 2. [类型] 名称 — 说明
  ...
```

## 强制步骤输入约定（调用方必读）

大需求 Harness / 灵山传入的 `强制步骤` **只是约束**，不是最终执行编排：

| 允许传入 | 禁止传入 |
|----------|----------|
| 步骤意图：「TDD 独立 commit」「Playground skeleton 独立 commit」 | 完整 `🚦 Step3令牌` 或已编好序号的 8 步清单 |
| 顺序约束：`强制顺序: A < B < C` | 在 Task prompt 写「视同开始」「用户已授权执行」 |
| 强度：`strict` / `standard` / `light` 建议（EP-2 可写入 plan.md） | 预填 `[AI分析]`/`[subagent]` 且禁止 execution-planner 调整（🔒 步骤除外） |

**EP-2 处理规则**：
1. 将 `强制步骤` 中带 `🔒` 的条目**原样插入**最终清单（类型可由 EP-2 补全标注）
2. 在步骤之间按编排优先级插入动态步骤（code-locator、Read ralph-loop 等）
3. 输出 EP-3 的 `🔧 执行清单` 时，清单必须与父方传入的逐步列表**有可见差异**（至少含 EP-2 补充的步骤或类型标注）

**违规判定**：若 plan.md「执行编排」与父方 TaskSpec 中的逐步列表完全一致且对话中无 EP-3 的 `🔧 执行清单`，视为未执行本 skill。

## 强制约束：调用方不得自行规划执行路径

> ⛔ **任何调用方在决定「如何执行一个任务」时，必须通过本 skill，不得自行决策执行路径。**

这条约束覆盖所有执行编排场景，包括但不限于：
- 选择使用哪个 agent / skill / workflow / MCP 工具
- 决定人工步骤是否需要、放在哪一步
- 决定执行顺序、前后依赖和门禁
- 决定大需求小助手中的 `strict` / `standard` / `light` 执行强度
- 生成要写入 `plan.md` 的「执行编排」章节

**原因**：每个项目经过长期纠正积累，台账中已沉淀了大量项目特有的执行偏好（如「这类问题用哪个 agent 而非另一个」「这类任务的特殊约束」等）。调用方自行规划会绕过这些积累，导致遗漏或不满足项目要求。

**执行方式是本 skill 的专属职责，调用方的唯一入口是传入 TaskSpec。每个子任务必须单独调用一次，不可批量处理，不可复用上一个任务的执行清单。**

## 调用方约定

execution-planner 是**纯规划层**，不感知调用方是谁，不管理状态文件，不负责执行。调用方拿到 Step3令牌后，自行决定如何执行和持久化状态。

**通用调用模式**：
```
构造 TaskSpec（由调用方根据任务描述填写）
Read execution-planner/SKILL.md
传入 TaskSpec
execution-planner 内部处理（台账匹配 → 清单生成 → 用户确认 → 纠正记录写入）
获得 Step3令牌
调用方按 Step3令牌逐项执行
```

### 嵌入式调用模式（供 Plan Gate 使用）

仅当调用方**未**携带预写 Step3 令牌、且将在**同一会话**内由用户确认 `plan.md` 时，方可声明嵌入式。

1. 仍必须执行 EP-1、EP-2，并在对话中输出 EP-3 的 `🔧 执行清单（共 N 步）`。
2. **EP-3 仍须等待用户说「开始」**——「嵌入式」**不**得跳过此确认（2026-05-28 hanzi-ui-redesign 教训：父 Agent 不得代签）。
3. 用户说「开始」后执行 EP-4，输出 Step3 令牌，写入 `plan.md`（首行注释 `<!-- execution-planner EP-4 YYYY-MM-DD -->`）。
4. 大需求 Harness：用户另可在 Get-Bearings 后说「开始 TXXX」再启动灵山 Step 4；两层确认均保留。
5. ⛔ **以下声明无效**，不得作为跳过 EP-3 的理由：`视同开始`、`严格重跑即开始`、`Task prompt 已含 Step3 令牌`。

**hanzi-ui-redesign / 大需求子任务**：一律按**默认模式**（EP-3 等用户「开始」），不使用跳过确认的嵌入式变体。

默认模式：未满足嵌入式条件时，EP-3 等待用户说「开始」后再 EP-4 输出 Step3令牌。

**典型调用方示例**：

| 调用方 | 构造 TaskSpec 的来源 | 拿到令牌后的动作 |
|--------|---------------------|----------------|
| 灵山 | Step 2 理解结果序列化 | 写入状态文件，进入 Step 4 执行 |
| 大需求小助手 | 拆分出的每个子任务描述 | 嵌入 S1 Plan Gate，将执行编排写入 plan.md，用户确认完整 plan.md 后继续 |
| 其他调用方 | 任意任务描述 | 自行决定 |

## 注意事项

- Step EP-3 的用户确认交互完全在本 skill 内部完成，调用方无需额外处理确认逻辑
- 纠正记录写入是硬性要求，不可因「清单简单」「只有一步」等理由跳过
- 台账文件不存在时自动创建，不报错
- 同一 TaskSpec 多次调用时，如台账已有高度匹配的记录，优先复用，避免重复积累冗余纠正条目
