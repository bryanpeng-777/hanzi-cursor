# Light Daily Task Manager（灵山）

轻量版任务管理。**区别于 daily-task-manager**：规划阶段直接选「用哪个技能/工具/AI方式」，在当前上下文直接执行，不拉 subagent/Task。

---

## 编排执行清单

**每次任务开始时初始化清单，每个 Step 执行前展示当前状态，执行完成后打勾。**

清单初始状态（每次任务独立维护）：

```
[ ] Step 0：入口判断
[ ] Step 1：展示待办 & 推荐任务
[ ] Step 2：快速理解任务
[ ] Step 3：选定执行方式
[ ] Step 4：直接执行
[ ] Step 5：验证 & 收尾
[ ] Step 6：打勾 & 状态同步
```

### 清单使用规则

**执行前**：每个 Step 开始前，输出当前清单，当前步骤标 `🔄`：

```
📋 执行进度
  ✅ Step 0：入口判断
  🔄 Step 1：展示待办 & 推荐任务   ← 当前
  ⬜ Step 2：快速理解任务
  ⬜ Step 3：选定执行方式
  ⬜ Step 4：直接执行
  ⬜ Step 5：验证 & 收尾
  ⬜ Step 6：打勾 & 状态同步
```

**执行后**：Step 完成后将该项改为 `✅`，更新输出清单。

**前序校验**：执行 Step N 前，检查 Step 0 ~ N-1 是否全部打勾。若有未完成项，**必须先补做，不得跳过**，在清单中标注 `⚠️ 补做`。

> **注意**：Step 1 仅场景 A 执行，场景 B 直接跳至 Step 2，此时 Step 1 标记为 `⬜ 已跳过（场景B）`。

## 核心流程

```
轻量开工 → 入口判断 → 展示待办 → 快速理解 → 选定方式 → 用户确认 → 直接执行 → 验证完成 → 打勾
```

## Step 0：入口判断

> **清单操作**：输出清单，Step 0 标 `🔄`，无需前序校验（首步）。

### 场景 A：从 Craft 拉取（说「灵山」「轻量开工」等）

**检查状态文件**：`<Workspace Path>/aiworkspace/daily_task_state.md`

- 文件存在 + 今天 + 有进行中任务 → 展示，询问「继续 N」或「新任务」
- 文件存在 + 今天 + 候选队列已有内容 → 直接用候选队列，跳过 Craft 拉取
- 否则 → 初始化状态文件，继续拉取 Craft

**自动计算本周文件名**：

```python
monday = today - timedelta(days=today.weekday())
project = os.path.basename(os.getcwd())
filename = monday.strftime("%m%d") + "-" + project  # 例如 "0421-camp"
```

依次调用：
1. `documents_search({ "include": "<文件名>" })`
2. `blocks_get({ "id": "<documentId>", "format": "json" })` （分页读完）

### 场景 B：用户直接告知任务

分配本地临时 ID（`local-HHMMSS`），写入状态文件进行中列表，**Step 1 标记为「已跳过（场景B）」，直接进入 Step 2**。

```
收到任务：「<任务内容>」，开始分析...
```

> **清单操作**：Step 0 完成，改为 `✅`，更新输出清单。

## Step 2：快速理解任务

> **清单操作**：输出清单，Step 2 标 `🔄`，校验前序全部打勾（场景B的 Step 1 为「已跳过」视为通过）。

### Step 2-0：【最高优先级】检查匹配 Agent

在做任何关键词提取或知识库检索之前，**先扫描任务描述，匹配 agents 中最合适的 agent**（本地 `~/.claude/agents/`；Cloud Agent `.cursor/agents/`）：

| 任务关键词 | 匹配 Agent |
|-----------|-----------|
| crash / ANR / FOOM / Bugly / 崩溃 | `bugly-assistant` |
| 告警 / 伽利略 / galileo / oncall / 工单 | `oncall-assistant` |
| 营地用户 / 反馈 / 日志 / 用户排查 | `camp-problem-analyzer` |
| bug / 修复 / fix / 代码定位 | `dev-assistant` |
| review / CR / 代码审查 | `cr-assistant` |
| 测试 / 验证 / 用例 | `test-assistant` |
| 产品 / 需求 / 方案 / AB实验 | `product-assistant` |
| 项目进度 / 台账 / 上线 | `project-assistant` |
| 文档 / 腾讯文档 / 写入 | `docs-assistant` |
| 知识库 / 沉淀 | `knowledge-assistant` |
| Flutter 播放器 / thumbplayer | `flutter视频小助手` |
| CS框架 / 插件 / 接入 | `cs-assistant` |

**命中时**：用 `Task（readonly: true）` 调用对应 agent，发送轻量问询：
> 「请帮我快速理解这个任务：`<任务描述>`。只需输出：目标 / 完成标准 / 关键约束，各一句话。」

将 agent 返回结果作为理解摘要的初稿，继续走后续步骤校验后输出给用户确认。

**未命中时**：直接走下方步骤 1～4。

1. **提取关键词**，判断任务类型（代码修复 / 调研 / 文档 / 配置 / 功能开发）
2. **按需检索知识库**：有明显不确定性时用 `knowledge-retriever`；简单明确可跳过
3. **结合分区标题**理解验收标准
4. 不清楚则追问，确认后展示理解摘要：

```
📋 理解确认：
  🎯 目标：<要做什么>
  ✅ 完成标准：<怎样算做完>
  🔑 关键约束：<边界条件>
  💡 知识命中：<知识库关键结论，无则省略>

确认后继续？
```

用户确认后，将理解结果**序列化为 TaskSpec**（供后续 execution-planner 使用）：

```
TaskSpec：
  任务类型: <bug修复 | 功能开发 | 调研 | 埋点检查 | 文档更新 | 配置变更 | 告警分析 | 代码定位 | 其他>
  任务描述: <原始任务描述>
  目标: <一句话>
  完成标准: <一句话>
  关键约束: <一句话>（无则省略）
  关键词: [<从任务描述和理解中提取的关键词，逗号分隔>]
  涉及模块: [<模块名>]（无则省略）
```

> **清单操作**：用户确认后，Step 2 改为 `✅`，更新状态文件阶段为「Step 3 选方案中」，输出更新清单。

## Step 3：规划执行清单

> **清单操作**：输出清单，Step 3 标 `🔄`，校验 Step 0 ~ Step 2 已全部打勾。

Step 3 的执行方式决策已**完全委托给 execution-planner skill**。流程如下：

```
Read /Users/bryanpeng/.claude/skills/execution-planner/SKILL.md
传入 Step 2 序列化输出的 TaskSpec（若含 强制步骤，仅为约束输入，见 execution-planner「强制步骤输入约定」）
EP-1 读 step3_corrections.md 并匹配
EP-2 生成带 [类型] 标注的清单（合并 强制步骤，不得原样照抄父方预写令牌）
EP-3 向用户展示「🔧 执行清单（共 N 步）」— ⛔ 硬停，等用户说「开始」
EP-4 用户说「开始」后输出 Step3令牌，并写入 plan.md（大需求任务）
```

execution-planner 内部负责：
- 加载 `step3_corrections.md` 匹配历史偏好
- 生成带类型标注的执行清单
- 支持用户多轮「改第N步」纠正
- 等待用户说「开始」后写入纠正记录
- 输出 Step3令牌

⛔ **大需求 Scenario B 委托时禁止**：
- 跳过 EP-3，直接把父 Task / TaskSpec 里的步骤列表当作 Step3 令牌
- 在未见用户「开始」前进入 Step 4 或修改业务代码仓库
- TaskSpec 中附带完整 `🚦 Step3令牌` 或「视同开始」

拿到 Step3令牌后 → **将其写入状态文件当前任务条目**，并同步大需求 `checklist.md` 的 Step3 区块：

> **Step3令牌格式**（写入状态文件当前任务条目）：
> ```

>   [ ] 1. [类型] 名称 — 说明
>   [ ] 2. [类型] 名称 — 说明
>   ...
> ```

> **清单操作**：execution-planner 输出 Step3令牌并写入状态文件后，Step 3 改为 `✅`，更新输出清单。

## Step 4：按清单逐项执行

> **清单操作**：输出清单，Step 4 标 `🔄`，校验 Step3令牌存在（若不存在强制回到 Step 3）。

### Step 4 前置门禁：必须用户明确说「开始」+ 检查 Step3令牌

**Step 4 的唯一触发条件是用户在当前对话中明确说「开始」。**

- 用户说「改第N步」「调整一下」「换一下」→ 继续停留在 Step 3，更新清单后重新展示，**不得进入 Step 4**
- 用户说「好」「没问题」「可以」「确认」但未说「开始」→ **视为仍在讨论阶段，不得进入 Step 4**，应回复「清单已确认，说「开始」即可正式执行」
- 用户说「开始」「开始执行」「go」「干吧」→ 才进入 Step 4

进入 Step 4 后，先读取状态文件，检查当前任务条目是否存在 `🚦 Step3令牌` 字段：

```
读取状态文件 → 找到当前任务条目 → 检查是否有「🚦 Step3令牌」行
  → 有令牌 → 加载完整清单，继续执行
  → 无令牌 → 拒绝执行，强制回到 Step 3
```

> **注意**：纠正记录的写入已由 execution-planner 在用户说「开始」时完成，Step 4 无需重复处理。

### 逐项执行规则

从 Step3令牌中读取完整清单，**逐项按序执行**，每完成一项立即在状态文件和输出中打勾：

```
📋 当前执行进度（Step 4）：
  [x] 1. [技能] bugfix/SKILL.md — 已完成
  🔄 2. [subagent] dev-assistant — 执行中...
  [ ] 3. [MCP工具] Galileo
  [ ] 4. [人工] 编译运行
```

**各类型执行方式**（无限制，按清单类型灵活选用）：

| 类型 | 执行方式 |
|------|---------|
| `[技能]` | `Read` 对应 SKILL.md → 按技能流程执行 |
| `[subagent]` | 通过 `Task` 工具拉起对应子 Agent |
| `[MCP工具]` | 直接调用对应 MCP 工具 |
| `[AI分析]` | 在当前上下文完成推理、搜索、输出结论 |
| `[人工]` | 输出明确指引，**强制等待用户确认完成**，不得自动跳过 |

**逐项门禁规则**：
- 未完成当前项前，不得开始下一项
- 每完成一项，同步将状态文件中该项 `[ ]` 改为 `[x]`，并更新状态文件阶段为 `Step 4 执行中（第 N/M 项）`
- 遇到 `[人工]` 项必须等用户说「完成」「搞定」「done」后才打勾继续
- 所有项全部打勾后，整体 Step 4 才视为完成

⛔ **编排权归属（用户进化 2026-06-05）**：
- **任务执行编排只能由灵山完成**：Step 3 必须走 `execution-planner` EP-1～EP-4，产出 `🚦 Step3令牌` 后方可进入 Step 4。
- **禁止主会话 / 大需求 Harness / 其他 Agent 代写执行清单或代签「开始」**；父方只能构造富 TaskSpec 并**启动灵山**，不得附带预写令牌或「视同开始」。

⛔ **禁止自行想象执行（用户进化 2026-06-05）**：
- Step 4 **只许按 Step3令牌逐项执行**；不得替换清单中的 `[workflow]` / `[subagent]` / `[技能]` 为「我觉得更快」的捷径。
- 不得合并多步（例：ui-design-workflow Step 2+3+4 一条回复做完）、不得跳过 workflow 子文件规定的 Pre-check / GATE PASS / 用户确认点。
- `[workflow]` 类项：必须先 `Read` 该 workflow **全文**（含逐步强制执行段），**禁止用摘要代替全文**。路径：本地 `~/.claude/agents/<name>.md`；Cloud Agent `.cursor/agents/<name>.md`。
- 不得在未更新 `plan.md` / 未获用户确认的情况下，擅自改布局策略、资源口径或验收标准（T010 反例：Column↔Stack 来回、主会话直接改 Figma 实现）。
- 若执行中发现清单不适用 → **硬停**，回到 Step 3 修订编排并等用户「开始」，禁止边做边改规则。

> **清单操作**：所有清单项完成后，Step 4 改为 `✅`，更新输出清单。

## 收工流程

用户说「收工」时，**按顺序执行以下两步**，不得跳过任意一步：

### 第一步：写入周报记录

**自动计算周报文件路径**：

```python
monday = today - timedelta(days=today.weekday())
project = os.path.basename(os.getcwd())
folder_name = monday.strftime("%m%d") + "-" + project  # 例如 "0521-camp"
weekreport_path = f"<Workspace Path>/aiworkspace/{folder_name}-weekreport.md"
```

**从当前对话中回顾本次会话完成的任务**（不读状态文件的历史记录，只记当前这次开工到收工之间完成的内容），为每条任务生成一行简洁记录：

格式要求：
- 一行一条，不超过 30 字
- 带上项目名（`[<project>]`）
- 说清楚做了什么，不要废话

示例格式：
```
- [camp] 修复首页 feed 列表空状态未展示的 bug
- [camp] 优化灵山技能，收工时增加周报记录逻辑
```

**写入规则**：
- 文件存在 → 追加到文件末尾（换行后追加，不覆盖已有内容）
- 文件不存在 → 创建文件，写入日期标题 + 记录

**文件头格式**（仅首次创建时写入）：
```markdown
# <folder_name> 周报记录
```

**每次写入前自动追加日期分隔（若当天首次写入）**：
```markdown

## <YYYY-MM-DD>
```

写入完成后输出：
```
📝 周报记录已写入：aiworkspace/<folder_name>-weekreport.md
```

## 注意事项

- **始终维护执行清单**：每个 Step 前后各展示一次，不得省略
- **前序校验是硬性要求**：Step N 前若有前序步骤未打勾，必须先补做
- **Step 3 → Step 4 唯一触发词是「开始」**：任何隐含同意、沉默、或非明确的确认词，都不能触发执行，必须等用户主动说「开始」
- **Step 3 支持多轮修改**：用户可以反复说「改第N步」，每次更新完整清单并重新展示，直到用户满意并说「开始」为止
- **执行方式无限制**：可按 Step3 清单调用任意方式，包括 Task/subagent、技能、MCP工具、AI直接分析
- **发现任务跨域复杂**：在 Step 3 清单中增加多个 `[subagent]` 项，无需切换到 `daily-task-manager`
- **Craft 不可达时**：降级为口述记录，提醒用户手动打勾
- **状态文件**与 daily-task-manager 格式兼容，两者可共用同一文件
