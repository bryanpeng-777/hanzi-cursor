# 周报总结

## 脚本分工

> **脚本处理**：读取文件、提取 `[x]` 任务、按标题分桶（`scripts/extract_done.py`）
> **AI 处理**：描述包装（改写为成果导向语言）、按重要性排序取前 5 条

```bash
# 提取已完成任务
python3 scripts/extract_done.py <weekly_report.md>
# 输出 JSON（按标题分桶），AI 再做描述包装
```

---

## 工作流程

1. **读取周报 markdown 文件**，解析所有任务项
2. **筛选已完成的任务**，只保留标记为 `[x]` 的项
3. **按内容自动分类**：根据原始 markdown 文档的一级标题或缩进结构作为分类依据
4. **包装描述**：将任务描述改写为面向成果的语言，聚焦"做了什么、完成了什么"，而非"怎么做的"
5. **生成总结**：输出两层级结构，每个分类下最多保留 5 条任务
6. **输出格式**：使用 markdown 格式，分类用 `##` 标题，细项用 `-` 列表

## 分类规则

根据周报文档的原有结构进行分类：

- **如果有显式分类标题**：使用标题作为分类名
- **如果只有缩进结构**：同一缩进层级的项归为一类
- **自动分类标签**：根据任务内容特征推断分类（如："Crash & ANR"、"王者资源"、"排查问题"、"沟通协作"）

## 描述包装规则（核心）

将原始任务描述改写为**面向结果、有力度**的表述，有利于 OKR 评价：

### 改写原则

- **聚焦成果，不说过程**：去掉"通过...方式"、"调用...接口"、"修改了...参数"等实现细节
- **动词要有力**：使用"完成"、"优化"、"修复"、"推进"、"落地"、"支撑"、"建设"等有分量的动词，而非"做了"、"改了"、"看了"
- **体现影响和价值**：尽量点出这件事对用户体验、系统稳定性、团队效率的价值
- **适度抽象**：将多个细碎的技术操作合并为一个有意义的业务动作

### 改写示例

| 原始描述 | 改写后 |
|---|---|
| 修改了 xxx 方法的参数，解决了崩溃问题 | 修复 xxx 场景崩溃，提升应用稳定性 |
| 看了一下代码，排查了 xxx bug | 定位并解决 xxx 问题 |
| 调用接口拉取了用户数据然后展示 | 完成 xxx 数据展示功能 |
| 和 xxx 同步了一下需求 | 推进 xxx 需求对齐，明确实现方案 |
| 看了几个 Crash 堆栈 | 完成 x 个 Crash 问题分析与归因 |

## 输出模板

```markdown
## 分类1
- 成果描述1
- 成果描述2
...

## 分类2
- 成果描述1
- 成果描述2
...
```

## 注意事项

- 只输出已完成的任务（`[x]` 标记的项）
- 每个分类最多 5 条任务，超过则按重要性排序取前 5 条
- 改写后保持核心信息不失真，不夸大、不虚构
- 如果某个分类下没有完成的任务，则不输出该分类
- 保持语言简洁，每条不超过 25 个字
