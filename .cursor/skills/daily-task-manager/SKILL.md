# 日常任务管理 Agent

从 Craft 任务集中按优先级自动挑选待办任务，编排「理解 → 规划 → 执行 → 沉淀 → 完成」的完整工作闭环。

本 Agent 是顶层编排者，负责调度决策和流程控制；具体的理解、规划、执行能力由 references/ 下的模块提供。

## 架构

```
daily-task-manager/
├── SKILL.md                          ← 你在这里：Agent 编排层
└── references/
    ├── task-understanding.md         ← 任务理解模块（知识库检索、追问澄清、确认理解）
    ├── task-planning.md              ← 任务规划模块（subagent 级路由、分支 3.0/3.1/3.2）
    ├── task-execution.md             ← 任务执行模块（执行规则、输出格式、异常处理）
    └── skill-discovery.md            ← 技能发现模块（搜索 Skill/MCP 自动化 [人工] 步骤）
```

**按需加载**：Agent 推进到对应阶段时才读取相应的 reference 文件，无需一次性全部加载。

## 编排执行清单

**每次任务开始时初始化清单，每个 Step 执行前展示当前状态，执行完成后打勾。**

清单初始状态（每次任务独立维护）：

```
[ ] Step 0：入口判断
[ ] Step 1：展示待办 & 推荐任务
[ ] Step 2：理解任务
[ ] Step 2.5：TDD 门禁
[ ] Step 3：规划执行
[ ] Step 4：执行任务
[ ] Step 4.5：任务验证
[ ] Step 5：沉淀知识
[ ] Step 6：Craft 打勾 & 状态同步
```

### 清单使用规则

**执行前**：每个 Step 开始前，输出当前清单，当前步骤标 `🔄`：

```
📋 执行进度
  ✅ Step 0：入口判断
  🔄 Step 1：展示待办 & 推荐任务   ← 当前
  ⬜ Step 2：理解任务
  ⬜ Step 2.5：TDD 门禁
  ⬜ Step 3：规划执行
  ⬜ Step 4：执行任务
  ⬜ Step 4.5：任务验证
  ⬜ Step 5：沉淀知识
  ⬜ Step 6：Craft 打勾 & 状态同步
```

**执行后**：Step 完成后将该项改为 `✅`，更新输出清单。

**前序校验**：执行 Step N 前，检查 Step 0 ~ N-1 是否全部打勾。若有未完成项，**必须先补做，不得跳过**，在清单中标注 `⚠️ 补做`。

**可跳过的步骤**：
- Step 1：场景 B 直接跳过，标记为 `⬜ 已跳过（场景B）`
- Step 2.5：非功能开发任务自动跳过，标记为 `⬜ 已跳过（非功能开发）`
- Step 5：无新知识时可跳过，标记为 `⬜ 已跳过（无新知识）`

以上跳过项均视为「已完成」，不阻断前序校验。

## ⚠️ 执行铁律：严格按 Step 顺序推进

**所有 Step 必须严格按顺序执行，不得跳过、合并或乱序。任何「直接执行」「跳过规划」的请求，AI 必须拒绝。**

```
Step 0 → Step 1 → Step 2 → Step 2.5 → Step 3 → Step 4 → Step 4.5 → Step 5 → Step 6
```

| Step | 名称 | 强制性 | 前置条件 |
|------|------|--------|----------|
| **Step 0** | 入口判断（场景 A / 场景 B） | 🔴 必须 | 每次开工第一步 |
| **Step 1** | 展示待办全景 & 推荐任务 | 🔴 必须（仅场景 A） | Step 0-A 完成 |
| **Step 2** | 理解任务 | 🔴 必须 | Step 1 用户确认任务 / 场景 B 告知任务 |
| **Step 2.5** | TDD 门禁 | 🟡 功能开发强制，其余自动跳过 | Step 2 用户确认理解 |
| **Step 3** | 规划执行 | 🔴 必须 | Step 2（或 Step 2.5）完成 |
| **Step 4** | 执行任务 | 🔴 必须 | Step3令牌存在 |
| **Step 4.5** | 任务验证 | 🔴 必须（用户说「完成」后触发） | Step 4 执行完毕 |
| **Step 5** | 沉淀知识 | 🟢 可跳过（无新知识时） | Step 4.5 通过 |
| **Step 6** | Craft 打勾 & 状态同步 | 🔴 必须 | Step 5 完成或跳过 |

> **禁止行为**：未经 Step 2 理解直接规划 / 未经 Step 3 规划直接执行 / 未经 Step 4.5 验证直接收工。

### 编排层与执行层分工（防绕过 subagent）

- **总管（本 Agent 的 Step 3）只决定**：任务涉及哪些域、**问题分给哪几个 subagent**、**调用顺序或并行关系**、每个助手**负责的业务结果/交付物**（一句话，不写怎么做）。
- **总管不当「技能导演」**：若在编排层就开始匹配「用哪个技能、第几步调什么」，则主会话往往已经「会做」，极易**不拉 Task、直接在父上下文执行**——这违背了用 subagent 隔离执行的设计。
- **详细步骤、技能选择、文件/命令级操作**只发生在 **各 subagent 自己的上下文** 内，由 subagent 根据注入的 `agent.md` 与【当前任务】自洽执行；**最外层不展示、不复述**这类细案，除非用户为对齐目标主动要求摘要。

## 核心流程

```
开工 → 获取任务文件 → 展示待办全景 → 按优先级推荐任务(可跳过/换)
→ [理解模块] 查知识库 + 结合分区标题理解任务 → 用户确认
→ [规划模块] 总管只做 **subagent 级路由**（谁负责哪块、先后/并行）→ 用户确认；**不**在编排层写子技能名与逐步细案；执行阶段按助手顺序 `Task` 各自完成
→ [执行模块] 逐步执行(人工步骤等待, 支持回退/插入/放弃)
→ [验证] 用户说完成后触发验证(代码注日志/结论确认/文档核查) → 通过后清理
→ 沉淀知识(knowledge-collector) → Craft 打勾 → 今日小结 → 继续或收工
```

## Step 0：入口判断 — 场景 A（任务集开工）or 场景 B（直接告知任务）

> 🔴 **每次开工必须从 Step 0 开始，判断入口场景，不得跳过。**
> **清单操作**：输出清单，Step 0 标 `🔄`，无需前序校验（首步）。

---

### 场景 A：用户说「开工」等触发词（从 Craft 任务集拉取）

#### Step 0-A-1：优先检查今日状态文件

开工时，**第一件事**是检查状态文件是否存在：

```
状态文件路径：<Workspace Path>/aiworkspace/daily_task_state.md
```

其中 `<Workspace Path>` 来自对话上下文 `user_info` 中的 `Workspace Path` 字段（即当前项目根目录，例如 `/Users/pengchao/workbryan/KingGuard`）。每个项目有独立的状态文件，互不干扰。

读取状态文件后，根据以下情况决策：

**情况 1：文件存在 + 日期是今天 + 有「进行中」任务（支持并行）**

读取「🔄 进行中（并行）」列表，展示所有进行中任务：

```
📂 发现今日进度！
🔄 并行中的任务（共 N 条）：
  [1] <任务名>（上次停在：<当前阶段>）
  [2] <任务名>（上次停在：<当前阶段>）

说「继续 N」恢复某条任务 | 说「新任务」从候选队列取下一条（已进行中的任务会自动跳过）
```

- 用户说「继续 N」→ 跳过 Step 0-A-2 和 Step 1，直接恢复第 N 条任务（以状态文件中该任务的阶段为基准）
- 用户说「新任务」→ 保持已有进行中任务不动，继续 Step 0-A-2 / Step 1 选取下一条（Step 1 会自动排除进行中的任务）
- 用户说「换一个」（只有 1 条进行中时）→ 将该任务标记为「暂停」，继续 Step 0-A-2 正常开工

> **并行设计原则**：每个 Agent 实例在同一时刻只执行一条任务，但多个 Agent 可以同时运行并操作同一个状态文件。状态文件是所有 Agent 的共享账本。

**情况 2：文件存在 + 日期是今天 + 无「进行中」任务（全部完成或未开始）**

如果状态文件的「📌 候选队列」已有内容，**跳过 Step 0-A-2 的 Craft 拉取**，直接进入 Step 1 用状态文件中的候选队列展示任务全景，无需提示。

⚠️ **重要**：跳过 Step 0-A-2 时没有 block ID，无法在 Step 6 打勾。需在用户**确认开始某个任务后**（Step 1 结束时），立即补拉 block ID：
1. `documents_search({ "include": "<任务文件名>" })` 获取 documentId
2. `blocks_get({ "id": "<documentId>", "format": "json" })` 拉取完整 blocks
3. 从 blocks 中找到对应任务的 block ID，保存备用（Step 6 打勾需要）

如果候选队列为空，才继续 Step 0-A-2 拉取 Craft（此时可完整获取 block ID，无需补拉）。

**情况 3：文件不存在 or 日期不是今天**

初始化/重置状态文件，写入今日日期和空状态后，继续 Step 0-A-2。

初始内容模板：
```markdown
## 今日进度（YYYY-MM-DD）
- 📋 任务文件：（待填）
- ✅ 已完成：（无）
- 🔄 进行中（并行）：（无）
- 📌 候选队列（按优先级）：（待填，每条格式：「任务描述」blockId: <id>）
```

> **block ID 是任务的唯一标识**：候选队列、进行中、已完成三个列表都必须携带 block ID，以便按 ID 而非文本来识别、排除和追踪任务。同名任务若 block ID 不同，则视为独立任务，不会互相干扰。

#### Step 0-A-2：自动计算本周任务文件名

**自动计算本周任务文件名**：

用当前日期计算本周周一（Monday）的月份+日期，格式为 4 位数字（月份和日期各补零至 2 位），拼接「-{项目名}」。项目名从当前工作目录名自动检测（取路径最后一段），例如：当前目录为 `KingGuard`，本周周一是 3 月 31 日 → 文件名为 `0331-KingGuard`。

计算方式（Python 示例，用于理解逻辑）：
```python
import os
from datetime import date, timedelta
today = date.today()
monday = today - timedelta(days=today.weekday())  # weekday() 中 0=周一
project = os.path.basename(os.getcwd())           # 例如 "KingGuard" 或 "camp"
filename = monday.strftime("%m%d") + "-" + project  # 例如 "0331-KingGuard"
```

直接使用计算出的文件名，**无需询问用户**，仅在 greeting 中展示文件名让用户确认：

```
开工！本周任务文件：「0331-KingGuard」，正在读取...（说「换一个」可手动指定文件名）
```

如果用户说「换一个」，则询问文件名后继续。

拿到文件名后：

1. `documents_search({ "include": "<文件名>" })` 搜索文档
2. 如果返回多个结果，列出让用户选择；只有一个则直接使用
3. `blocks_get({ "id": "<documentId>", "format": "json" })` 读取完整内容（分页读取直到无 nextCursor）
4. 同时 `blocks_get({ "id": "<documentId>", "format": "markdown" })` 获取人类可读版本

**关键**：保存完整的 blocks JSON 数据，后续打勾需要用到每个任务 block 的 `id`。

读取完成后，**更新状态文件**：将任务文件名写入「📋 任务文件」字段，将候选队列（5条，每条携带 block ID）写入「📌 候选队列」字段。

> **清单操作**：Step 0-A 完成，改为 `✅`，更新输出清单。

**→ 进入 Step 1**

### 场景 B：用户直接告知任务内容

当用户直接描述任务（如「这次任务是...」「帮我做...」「我要做...」），**跳过 Step 1 的任务选取环节**，直接以用户描述作为当前任务进入 Step 2 理解阶段。

#### 开始时分配本地临时 ID

Craft 写入放在任务完成后（Step 6）统一执行，**但任务从一开始就需要唯一标识**以防止同名任务混淆。解决方式：开工时生成本地临时 ID。

**生成本地临时 ID**（无需任何用户输入，直接执行）：

```python
# 格式：local-HHMMSS，例如 local-143022
local_id = "local-" + datetime.now().strftime("%H%M%S")
```

将任务写入状态文件「🔄 进行中（并行）」列表，使用本地临时 ID：

```
- <任务内容>（blockId: local-<HHMMSS>，开始时间：HH:MM）
  - 当前阶段：Step 2 理解中
  - 🎯 任务目标：-
  - 🔑 关键约束：-
  - ✅ 完成标准：-
  - 📚 关键知识：-
```

然后直接进入任务流程，**不询问 Craft 文件名，不等待任何用户确认**：

```
收到任务：「<任务内容>」，开始规划...
```

> ⚠️ **强制约束（场景 B 专属）**：分配本地 ID 后，**必须严格按照 Step 2 → Step 2.5 → Step 3 → Step 4 → Step 4.5 → Step 5 → Step 6 的顺序推进，不得直接跳入执行**。
>
> 即使任务意图已非常明确（如用户直接给出 Bugly 链接、工蜂 MR 链接、告警 URL 等），**Step 3 规划依然是强制步骤**：必须展示「涉及域 + **子 agent 分工与顺序**」并等待用户确认后，才能开始执行；**不** 在 Step 3 写技能级细案。
>
> **正确示例**：收到 Bugly 链接 → 分配本地 ID → Step 2 理解 → Step 3 只定助手路由 → Step 4 用 Task 执行各助手 → Step 4.5 验证 → Step 5 沉淀 → Step 6 写入 Craft（直接 `[x]`）+ 替换本地 ID

> **清单操作**：Step 0-B 完成，Step 0 改为 `✅`，Step 1 标记为 `⬜ 已跳过（场景B）`，更新输出清单。

**→ 跳过 Step 1，直接进入 Step 2**

## Step 1：展示待办全景 & 按优先级推荐任务

> 🔴 **仅场景 A 执行**；场景 B 跳过本步骤，直接进入 Step 2。
> **清单操作**：输出清单，Step 1 标 `🔄`，校验 Step 0 已打勾。

### 解析文档结构

任务文档以**编号标题**（`listStyle: "numbered"` 的 block）作为分区。每条 `listStyle: "task"` 的 block 归属于其上方最近的编号标题分区。

分区标题包含了**目标定义**和**验收标准**，是理解任务的关键上下文，后续理解任务时必须结合分区标题。

### 展示全景

```
📊 任务集全景：

总计 N 条待办，已完成 M 条，剩余 X 条：
  🔴 高优先级：A 条 | 🟡 中：B 条 | 🟢 低：C 条 | ⚪ 未标记：D 条

按分区分布：
  1. 多游保障专项 — 7 条未完成 / 1 条已完成
  2. Bugly质量评分 — 4 条未完成 / 1 条已完成
  ...
```

### 扫描策略（提前停止 + 排除进行中）

按优先级顺序扫描文档：**高 → 中 → 低 → 未标记**，累计收集到 **5 条**未完成任务后立即停止，不再继续扫描剩余内容。

**排除已认领/已完成任务**：扫描时优先使用 **block ID 匹配**跳过状态文件「🔄 进行中（并行）」和「✅ 已完成」列表中已有的任务（若 block ID 已记录则用 ID 比对，否则降级为文本匹配），避免多个 Agent 重复认领同一条任务，也避免同一天内同名任务被误跳过（同名不同 block ID 的任务是不同任务，不应排除）。

优先级标记识别：`【高】` `【中】` `【低】` / `P0` `P1` `P2` / `紧急` `urgent` 等。

> 若整份文档未完成任务不足 5 条，则全部收集后停止。

### 推荐任务 & 允许换任务

从收集到的 5 条候选任务中，推荐优先级最高的一条作为当前任务：

```
🎯 推荐任务：
  📌 <任务内容> 【优先级】
  📂 所属分区：<分区标题>

是否开始？也可以说「跳过」换下一条、「选 N」指定（从下方候选列表选）、「先看列表」查看候选明细。
```

候选列表（最多 5 条，按优先级排序）在用户说「先看列表」或「跳过」多次时展示。

**用户确认开始某个任务后**，立即将新任务**追加**到状态文件「🔄 进行中（并行）」列表（不覆盖已有条目）。**必须记录 block ID**，这是任务的唯一标识，防止同名任务混淆：

```markdown
- 🔄 进行中（并行）：
  - <已有任务A>（blockId: <id>，开始时间：HH:MM）
    - 当前阶段：...
    ...
  - <新任务>（blockId: <id>，开始时间：HH:MM）   ← 追加到列表末尾
    - 当前阶段：Step 2 理解中
    - 🎯 任务目标：-
    - 🔑 关键约束：-
    - ✅ 完成标准：-
    - 📚 关键知识：-
```

> **为什么记录 block ID**：同一天内可能出现多条文字描述完全相同的任务（如多次「去 Bugly 找一个 crash 修改」），block ID 是每条任务在 Craft 中的唯一标识，是区分同名任务的唯一可靠手段。
>
> **写入时机**：必须在用户确认后立即写入，让其他 Agent 能看到「此任务已被认领」，避免并发认领冲突。

> **清单操作**：用户确认任务后，Step 1 改为 `✅`，更新输出清单。

**→ 进入 Step 2**

## Step 2：理解任务

> 🔴 **必须执行，理解未经用户确认前不得进入 Step 2.5 / Step 3。**
> **清单操作**：输出清单，Step 2 标 `🔄`，校验 Step 0 ~ Step 1 已完成（场景B的 Step 1 为「已跳过」视为通过）。

**读取 `references/task-understanding.md` 并按其流程执行。**

核心流程：提取关键词 → 检索知识库 → 结合分区标题综合理解 → 不清楚时主动追问 → 展示理解并等待用户确认。

**用户确认理解无误后**，定位状态文件「🔄 进行中（并行）」列表中**当前任务**的条目，原地更新为完整上下文（其他任务条目保持不变）：

```markdown
  - <当前任务名>（blockId: <id>，开始时间：HH:MM）
    - 当前阶段：Step 3 规划中
    - 🎯 任务目标：<这条任务具体要做什么>
    - 🔑 关键约束：<来自分区目标或用户补充的边界条件>
    - ✅ 完成标准：<怎样算做完>
    - 📚 关键知识：<知识库命中的核心结论，1-3 条，用 / 分隔>
```

这份上下文在**跨会话恢复**时同样有效——下次开工读取状态文件，即可直接还原任务背景，无需重新查询知识库或追问用户。

> **清单操作**：用户确认理解后，Step 2 改为 `✅`，更新状态文件阶段为「Step 3 规划中」，更新输出清单。

**→ 进入 Step 2.5（判断是否需要 TDD 门禁）**

---

## Step 2.5：TDD 门禁（功能开发强制触发）

> 🟡 **功能开发任务强制触发，不可跳过；Bug 修复 / 文档 / 配置 / 调研类直接跳过进入 Step 3。**
> **清单操作**：输出清单，Step 2.5 标 `🔄`，校验 Step 0 ~ Step 2 已全部打勾。若为非功能开发任务，直接将 Step 2.5 标记为 `⬜ 已跳过（非功能开发）`，进入 Step 3。

**在进入 Step 3 规划之前**，必须先判断任务类型，若属于功能开发则强制走 TDD 流程，**不需要用户提醒，不可跳过**。

### 触发条件（满足任意一项即为「功能开发任务」）

| 触发信号 | 示例关键词 |
|---------|-----------|
| 任务描述含功能开发意图 | 新增、接入、实现、开发、做一个、增加、添加 |
| 任务描述含 UI/Screen | 页面、界面、Screen、Tab、弹窗、组件 |
| 任务描述含新模块/新能力 | 支付、广告、推送、认证、登录、注册、功能 |
| 任务描述是需求 Story | 「用户可以...」「支持...」「实现...功能」 |

### 触发后的强制流程

**2.5-1 读取项目 TDD 要求**

检查当前项目目录下是否存在 `CLAUDE.md`，搜索其中是否包含 TDD 相关规定（如「测试先行」「test_manifest」「先写测试」）。

**2.5-2 读取测试台账**

```
检查路径：<项目根目录>/test_manifest.md  或  <项目根目录>/aiworkspace/test_manifest.md
```

若文件存在，读取已有用例（了解覆盖范围，避免重复）；若不存在，提示将新建。

**2.5-3 设计并输出测试用例草案**

基于对任务的理解（Step 2 的产出），设计本次功能的测试用例，格式如下：

```markdown
## TDD 门禁 — 请确认测试用例后再开始编码

本次功能：<功能名称>

| # | 测试项 | 方式（自动/手动） | 说明 |
|---|--------|-------------------|------|
| X1 | ... | 自动 | ... |
| X2 | ... | 手动 | ... |
```

**用例设计原则**：
- 至少覆盖「功能正常路径」「边界/异常路径」「降级处理（配置缺失时不崩溃）」
- 标注自动/手动（涉及真机 UI 交互标为手动）
- 若有受影响的已有用例，列出「需同步更新的用例」

**2.5-4 等待用户确认**

```
📋 TDD 门禁：以上用例你确认吗？
  ✅ 确认 → 我将用例追加到 test_manifest.md，然后开始编码
  ✏️ 修改 → 告诉我哪里需要调整
  ⏭️ 跳过 → 说「跳过测试」（不推荐，请说明原因）
```

- **用户确认** → 将用例追加写入 test_manifest.md，然后进入 Step 3
- **用户修改** → 更新用例后重新输出，再次等待确认
- **用户说「跳过测试」** → 记录跳过原因到状态文件后进入 Step 3（不强制拦截，但留档）

> **状态文件更新**：确认后将阶段更新为 `当前阶段：Step 3 规划中`，并在任务条目中记录 `🧪 TDD 用例：已确认 N 条`。

> **清单操作**：用户确认测试用例（或跳过）后，Step 2.5 改为 `✅`，更新输出清单。

**→ 进入 Step 3**

---

## Step 3：规划执行（强制：先 subagent 路由，禁止编排层写技能细案）

> 🔴 **必须执行。必须经用户确认 + 写入 Step3令牌后才能进入 Step 4。用户说「直接执行」想跳过确认时，AI 必须拒绝。**
> **清单操作**：输出清单，Step 3 标 `🔄`，校验 Step 0 ~ Step 2.5 已全部打勾（含跳过项）。
>
> 本步的「计划」= **子 agent 分工与顺序**（及必要时少量「无助手」退路），**不是** 技能列表、**不是** 父上下文里的逐步执行细案。细案在 **subagent 内部** 产生与执行。

**⚠️ 进入 Step 3 的第一个动作必须是读取 `references/task-planning.md`，然后执行 3.0 总管编排。禁止凭记忆执行。**

**🚩 红旗信号（出现以下任一条 = 错误姿态，须回到 3.0/规则重来）**：
- 在还没输出「涉及域 + 子 agent 分工」之前，就写**技能名、子技能名、文件路径级步骤、具体命令**（ = 主会话会忍不住自己执行，绕过 Task）
- 以「任务很简单」「我已经知道用哪个技能」为由跳过 3.0
- 把 3.0 写成「助手 → 子技能 A → 子技能 B」的**技能跑单**（子技能只许出现在 subagent 内，不许作为编排层交付物）
- 在编排层用「[技能名] 逐步」代替「[助手名] 负责 <业务块>」

该模块含三段式规划（按顺序尝试，找到合适方案即停），详见 `task-planning.md`：

| 分支 | 含义 | 编排层输出什么 |
|------|------|---------------|
| **3.0 总管编排**（最优先、不可跳过） | 分析任务涉及域与**哪几个小助手**、各自**负责的业务块/交付物**、**顺序/并行** | 仅 **助手名 + 责任边界 + 依赖**，**不写** 子技能 |
| **3.1 单点委派** | 可映射到**一个**能整体承接的助手或「无助手」专项能力时 | **一个** 委派句（多优先写助手整体承接，而非技能名排程） |
| **3.2 组合/兜底** | 3.0/3.1 无法覆盖时 | 仍只拆 **域/角色/助手**，不写技能级多步；不得已需人工时标 `[人工]`，**不** 在父层写「调用某技能第几步」 |

> 「明确」（编排层）= 说清**哪些 subagent、各管什么结果、谁依赖谁、是否并行**；禁止用技能细案偷换「明确」。
> 「完整」（编排层）= 从任务目标到**助手级责任**能闭环，不遗漏应参与的助手；**不** 要求把执行细步写在父层。

无论走哪个分支，最终都必须：
1. 通过 `task-planning.md` 中的**编排层**自检（含「是否违规写出技能/细案」）
2. 等待用户确认
3. 将**助手路由摘要**写入 `🚦 Step3令牌` 字段，写入失败则暂停

> **清单操作**：Step3令牌写入成功后，Step 3 改为 `✅`，更新输出清单。

**→ Step3令牌写入成功后，进入 Step 4**

---

## Step 4：执行任务

> 🔴 **必须执行。执行前强制检查 Step3令牌，令牌缺失则强制回到 Step 3，无任何例外。**
> **清单操作**：输出清单，Step 4 标 `🔄`，校验 Step 0 ~ Step 3 已全部打勾。Step3令牌缺失则强制回 Step 3。

### Step 4 前置门禁：检查 Step3令牌

**执行任何操作之前**，必须先读取状态文件，检查当前任务条目是否存在 `🚦 Step3令牌` 字段：

```
读取状态文件 → 找到当前任务条目 → 检查是否有「🚦 Step3令牌」行
  → 有令牌 → 继续执行
  → 无令牌 → 拒绝执行，强制回到 Step 3
```

```
🚫 缺少已确认的编排（Step3令牌不存在）！
执行前必须先：
  1. 走 Step 3 的三段式规划（3.0 总管 → 3.1 单点委派 → 3.2 组合/兜底，详见 task-planning.md）
  2. 用户确认：**子 agent 分工与顺序**已对齐（不是确认「技能跑单」）
  3. 写入 🚦 Step3令牌

正在返回 Step 3 进行规划...
```

> ⚠️ 此门禁无任何例外。只要令牌不存在或用户未确认编排，都必须拒绝并回到 Step 3。确认的是 **助手级路由**，不是父上下文里的技能逐步。

### 执行

**读取 `references/task-execution.md` 并按其流程执行。**

核心流程：按 Step3 确定的 **subagent 顺序** 用 `Task` 依次（或依依赖）推进 → 每个 subagent 内部自行拆步、选技能；若计划中含 `[人工]` 则等待用户 → 支持异常处理（重试/跳过/回退/放弃）。**主会话不** 为「有归属助手的子技能」执行 Read SKILL/跑脚本（见 task-execution.md）。

执行开始时，定位并更新状态文件中**当前任务**条目的阶段字段：`当前阶段：Step 4 执行中（助手或步骤 N/M）`。N/M 在 **3.0 多助手** 时优先表示 **第几个助手**；若单助手内仍需多轮 Task，可再细分。

每完成一个关键步骤后同步更新（精准替换该行，不影响其他并行任务的条目）。

> **清单操作**：用户说「完成」后，Step 4 改为 `✅`，更新输出清单。

**→ 用户说「完成」「搞定」「done」后，进入 Step 4.5**

---

## Step 4.5：任务验证

> 🔴 **必须执行。用户说「完成」后立即触发，不可跳过（用户主动说「跳过验证」除外，但须提示风险）。**
> **清单操作**：输出清单，Step 4.5 标 `🔄`，校验 Step 0 ~ Step 4 已全部打勾。

更新状态文件阶段：`当前阶段：Step 4.5 验证中`

### 验证类型判断

根据任务性质选择对应验证方式：

| 任务类型 | 验证方式 |
|---------|---------|
| iOS/Flutter 代码修改 | 注入验证日志 → 用户编译运行 → AI 检查日志 → 删除日志 |
| 技术调研 / 分析类 | 展示产出结论，用户确认是否覆盖所有疑问 |
| 文档 / Craft 更新 | 读取修改后的文档内容，与目标对比确认 |
| 配置 / 开关变更 | 列出变更清单，用户确认每项生效 |
| 其他 | AI 提出验证方案，用户确认后执行 |

### 代码修改验证流程（最常见）

参考 `verify-code-changes` 技能，使用 `WEGLogBizManager commonLog` 注入验证日志：

```
[AI]    在关键逻辑处注入 verify_ 前缀的日志
[人工]  编译运行 App，触发相关功能
[AI]    在 aiworkspace/log 中搜索 verify_ 日志，判断逻辑正确性
[AI]    验证通过 → 删除所有验证日志，恢复干净状态
        验证失败 → 告知问题，回到 Step 4 继续修复
```

### 验证结果处理

- **通过** → 输出验证结论，进入 Step 5
- **失败** → 说明具体失败原因，回到 Step 4 继续修复，修复后重新触发 Step 4.5
- **用户说「跳过验证」** → 提示「建议验证，跳过可能导致错误上线」后放行，直接进入 Step 5

> **清单操作**：验证通过后，Step 4.5 改为 `✅`，更新输出清单。若用户说「跳过验证」，标注 `✅ 已跳过（用户主动跳过）`。

**→ 验证通过后，进入 Step 5**

---

## Step 5：沉淀知识

> 🟢 **可跳过**：任务简单无新知识时，告知用户并直接进入 Step 6。
> **清单操作**：输出清单，Step 5 标 `🔄`，校验 Step 0 ~ Step 4.5 已全部打勾（含跳过项）。

任务完成后，回顾执行过程，识别有价值的知识（新发现、踩坑经验、知识更新/删除）。

- 如果没有新知识，主动告知并建议跳过
- 有知识则展示沉淀计划，用户确认后按 `knowledge-collector` 技能执行
- 用户说「跳过」则直接进入 Step 6

> **清单操作**：知识沉淀完成（或跳过）后，Step 5 改为 `✅`（跳过时标 `✅ 已跳过（无新知识）`），更新输出清单。

**→ 进入 Step 6**

---

## Step 6：Craft 打勾 & 状态同步

> 🔴 **必须执行。场景 A 直接打勾；场景 B 先写入 Craft 再打勾（见下方「场景 B」小节）。**
> **清单操作**：输出清单，Step 6 标 `🔄`，校验 Step 0 ~ Step 5 已全部打勾（含跳过项）。

### 场景 A：直接打勾

通过 `blocks_update` 将已完成任务的 markdown 中 `- [ ]` 替换为 `- [x]` 写回：

```
blocks_update({ "blocks": [{ "id": "<blockId>", "markdown": "- [x] <任务内容>" }] })
```

### 场景 B：先写入 Craft，再替换本地 ID

任务完成后，在打勾之前先补写 Craft：

1. 询问写入哪个 Craft 文件（默认本周任务文件，用户可指定其他）：
   ```
   ✅ 任务完成！写入 Craft 并打勾，文件用「<本周文件名>」？（说「其他」可指定）
   ```
2. `documents_search` 定位目标文档
3. `blocks_create({ ..., "afterBlockId": null, "blocks": [{ "markdown": "- [x] <任务内容>" }] })` 直接插入**已完成**状态（`[x]`），无需后续再打勾
4. 从响应中取出真实 block ID，**替换状态文件中的本地临时 ID**：
   ```
   # 将「blockId: local-HHMMSS」更新为「blockId: <真实id>」
   ```

**若 Craft 不可达**：以本地 ID 维持状态文件记录，提示用户手动打勾，不阻断流程。

### 同步更新状态文件

**只操作当前任务，保留其他并行任务**：

1. 从「🔄 进行中（并行）」列表中**移除当前任务**条目（按 block ID 精确匹配，不按任务名）
2. 将当前任务追加到「✅ 已完成」列表，**保留 block ID**

```markdown
✅ 已完成：
  - <之前已完成的任务>（blockId: <id>，完成时间：HH:MM）
  - <当前任务描述>（blockId: <id>，完成时间：HH:MM）   ← 追加
🔄 进行中（并行）：
  - <其他仍在进行的任务A>（blockId: <id>，开始时间：HH:MM）   ← 保持不变
  （若列表为空则写「（无）」）
```

展示今日进度：

```
✅ 任务「<任务>」已完成！
📊 今日已完成 N 条 | 并行进行中 P 条 | 候选队列 M 条
说「继续」取下一条 | 说「收工」结束今天
```

> 若还有其他并行任务仍在进行中，额外提示：「另有 P 条任务仍在其他 Agent 中并行执行中」

> **清单操作**：打勾与状态同步完成后，Step 6 改为 `✅`，输出最终清单（九项全部打勾）：
>
> ```
> 📋 执行进度（完成）
>   ✅ Step 0：入口判断
>   ✅ Step 1：展示待办 & 推荐任务
>   ✅ Step 2：理解任务
>   ✅ Step 2.5：TDD 门禁
>   ✅ Step 3：规划执行
>   ✅ Step 4：执行任务
>   ✅ Step 4.5：任务验证
>   ✅ Step 5：沉淀知识
>   ✅ Step 6：Craft 打勾 & 状态同步
> ```

**→ 用户说「继续」回到 Step 1；用户说「收工」进入收工流程**

---

## 循环与收工

**继续**：回到 Step 1，无需重新读取文档。

**收工**：触发 `wrap-up` 技能前，先检查所有「已完成」任务是否已在 Craft 中打勾（Step 6）。如有遗漏，先补执行 Step 6，再触发 wrap-up。

```
📋 今日工作小结：
完成：N 条 | 跳过：M 条 | 知识沉淀：K 条 | 剩余：X 条
  ✅ <完成的任务列表>
  ⏭️ <跳过的任务及原因>
  📝 <沉淀的知识文章>
```

**全部完成**：自动提示并输出成果小结。

## 注意事项

- **顺序不可打乱**：Step 0 → 1 → 2 → 2.5 → 3 → 4 → 4.5 → 5 → 6，禁止跳步、合并步骤
- **理解确认不可跳过**：Step 2 展示理解后必须等用户确认，才能进入 Step 2.5 / Step 3
- **计划确认不可跳过**：Step 3 展示 **助手级路由/单点/组合** 后须等用户确认并写入令牌，才能进入 Step 4；确认的不是父层技能细案
- **人工步骤必须等待**：Step 4 中不要在用户未确认完成时自动跳过
- **验证不可跳过**：Step 4.5 在用户说「完成」后强制触发，用户主动说「跳过验证」才放行
- **知识沉淀可跳过**：Step 5 任务简单无新知识时用户可跳过
- **保持上下文**：后续任务可复用前序任务的分析结果
- **Craft 分页读取**：`nextCursor` 存在时继续读取；`CURSOR_INVALID` 则从头重新读取
- **Craft 不可达降级**：告知用户并降级为手动模式（口述任务、提醒自行打勾）
- **放弃不打勾**：放弃的任务保持未完成状态
