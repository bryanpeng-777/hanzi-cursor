# 任务理解模块

Agent 在选中一条任务后，通过本模块深入理解任务含义，确保人机对齐后再进入规划。

---

## 2.1 提取关键词

从任务描述中提取 2-5 个检索关键词，进行同义词扩展。

## 2.2 检索知识库

按照 `knowledge-retriever` 技能的流程检索：**通用索引 + 当前项目索引**（旧库仅当用户或任务明确要求时再搜），对每份选中的索引分别 `document_search`（或 `blocks_get` 回退），`blockId` 以该技能 Step 1.5 为准（勿写死单一 pageId）。

```
MCP Server: user-craft
Tool: document_search
参数示例（每个索引各调一次）: {
  "blockId": "<knowledge-retriever Step 1.5 选中的索引 pageId>",
  "pattern": "<关键词1>|<关键词2>|...",
  "caseSensitive": false
}
```

如果知识库无命中，不必强行等待，直接基于任务描述本身进行理解，并告知用户「知识库暂无相关记录，以下是我基于任务描述的理解」。

## 2.3 综合理解

结合**分区标题**、知识库检索结果和任务描述本身，形成对任务的理解：

- **分区上下文**：该任务所属分区的目标和验收标准是什么？这条任务是如何服务于分区大目标的？
- 这个任务要做什么（目标）
- 涉及哪些模块/技术栈
- 有哪些已知的经验或注意事项（来自知识库）
- 可能的难点或风险

分区标题往往揭示了任务的「为什么」，例如一条「增加预约多游的P0监控」任务，如果脱离分区标题「持续优化终端伽利略能力建设，需覆盖新版本，活动，业务等更多场景，同时达成并保持核心业务链路的MTTD<10分钟」来理解，会丢失监控覆盖度和 MTTD 指标这两个关键约束。

### 主动追问澄清

**如果任务描述过于简短或模糊，无法形成清晰理解**，应主动向用户提问澄清，而不是猜测。任务集中的描述往往是随手记的备忘，可能省略了大量上下文。

常见需要追问的情况：
- 任务描述不到 10 个字，缺少具体目标（如「研究下 XX」→ 研究什么方面？产出是什么？）
- 涉及人名但不清楚要做什么（如「和 XX 对一下」→ 对什么内容？需要得到什么结论？）
- 有代词或缩写无法推断含义（如「那个」「上次说的」→ 具体指什么？）
- 无法判断任务边界（如「Bugly 这一套研究」→ 研究到什么程度算完成？）

追问格式：
```
这条任务的描述比较简短，我有几个疑问想确认：

❓ 1. <具体问题>
❓ 2. <具体问题>

请补充一下，帮助我更准确地理解和规划。
```

用户补充后，将补充信息融合到理解中，再进入确认。

## 2.4 确认理解

将理解结果展示给用户确认：

```
我对这个任务的理解如下：

📂 所属分区：<分区标题>
   分区目标：<分区标题中的目标/验收标准>
🎯 任务目标：<这条任务具体要做什么，以及它如何服务于分区目标>
🔧 涉及模块：<模块列表>
📚 知识库参考：
  - 《相关文章1》→ <关键结论>
  - 《相关文章2》→ <关键结论>
⚠️ 注意事项：<来自知识库的经验提醒>

请确认我的理解是否正确？如有偏差请补充说明。
```

**等待用户确认后**才继续下一步。如果用户补充了信息，更新理解并再次确认。

> ⚠️ **严禁跳过规划阶段**：用户对理解的任何回复（无论是确认还是补充新信息），都必须先进入 Step 3 规划阶段，展示执行计划并等待确认，再开始执行。
> 典型错误：用户说「看 0318 版本就好，帮我定位根因」→ 正确做法是先列出执行计划等确认，而不是直接开始查 Bugly 或搜索代码。
