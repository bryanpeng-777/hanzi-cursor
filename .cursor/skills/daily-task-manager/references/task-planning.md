# 任务规划模块

> 🚨 **核心铁律（编排层 = 子 agent 路由，不是技能跑单）**：进入 Step 4 之前，**必须**输出一份**已获用户确认**的编排，并写入 `🚦 Step3令牌`。
>
> **编排层**只回答：`涉及哪些域 / 分派给**哪些** subagent / 各自**负什么业务责** / **先後或并行** / 是否含**必须人工**的环节`。  
> **不回答**（禁止写在给用户看的 Step 3 里）：`具体用哪种子技能、第几步、读哪个文件、跑哪条命令`——这些若写在父层，主会话会**直接自己执行**并**绕过** `Task(subagent)`，与架构相悖。
>
> **「明确」（编排层）** = 每个助手都有清晰的一句话**责任边界**与**可验收结果**；助手之间**依赖**说清。禁止用「第 N 步调某某技能」代替责任描述。
>
> **「完整」（编排层）** = 为达成任务目标，该参与的助手都**挂上了**；不遗漏强依赖的协作链（例：先分析后 review）。不强制在父层列出「从打开 IDE 到提交」的微观步骤。

本模块按以下三段式推进规划：**总管只做子 agent 分配**；**技能与微观步骤 = 各 subagent 内部**。

```
3.0 总管编排（强制最优先）
  ├─ 涉及域 + 哪几个小助手 + 各负责什么业务结果 + 顺序/并行
  ├─ 用户确认 → 写入 🚦 Step3令牌（只含助手与路由，不含子技能名）
  └─ 若无法由助手覆盖整任务 → 进入 3.1

3.1 单点委派
  ├─ 优先：整任务交给 **一个** 小助手，由其在内部选技能
  ├─ 次选：无对应助手、确需**独立技能**在子上下文中跑完时，令牌标注「[3.1] 子上下文执行 <技能名>」（父会话仍不读 SKILL 执行）
  └─ 用户确认 → 写入 🚦 Step3令牌；仍不合适 → 3.2

3.2 组合 / 兜底
  ├─ 以「域 / 角色 / 助手」拆块，必要时标 [人工]；**不在父层**写技能名排程
  └─ 用户确认 → 写入 🚦 Step3令牌
```

无论走 3.0、3.1 还是 3.2，**最终都必须将「助手路由摘要」写入状态文件的 `🚦 Step3令牌` 字段**，否则 Step 4 会拒绝执行。

## 3.0 总管编排（强制最优先，不可跳过）

> ⚠️ **无论任务意图多么明确，此步骤都必须执行**，不得以「任务简单」「只涉及一个助手」为理由跳过。
> 总管编排的价值：**让用户确认「谁管哪块」、暴露跨域依赖、避免漏环节**；**不是** 在父层做「技能导演」。

### 执行方式

读取 `~/.claude/agents/master-assistant.md`（或项目内等价的总管 agent），使用**意图识别 + 域划分 + 多助手依赖**逻辑，对当前任务描述做分析。

**在输出方案前须知**：各小助手一律通过 `Task` 在**隔离子上下文**中执行，总管**不在此阶段**为各助手预分配子技能名。

> 🚨 **为什么编排层禁止写「助手 → 子技能」**  
> 若总管已经细化到子技能，父上下文通常已知道「调哪个 SKILL、跑什么」，极易**不拉起 subagent 直接执行**——这正是要杜绝的。子技能**只许**出现在 subagent 读 SKILL 的那一刻，**不许**作为 Step 3 给用户的成稿内容。

### 协作方案输出格式（只写：助手 + 责任边界，不写子技能）

```
🧭 总管编排（子 agent 级）：

任务：「<任务描述>」

涉及域：<域1>、<域2>（如只涉单域则只列一个）

子 agent 分配：
① [<小助手A>] 负责：<要达成的业务结果 / 要交付的可见产出，一句话>
   输入/前置：无 或「来自用户的原始信息」
② [<小助手B>] 负责：<业务结果>
   输入/前置：依赖 ① 的结论文本摘要（**不写** ① 在内部用了哪种子技能）
③ [<小助手C>] 负责：<业务结果>
   输入/前置：…

执行顺序：① → ② → ③（串行）  /  ① ‖ ②（并行，仅当彼此输入确实独立）

说「开始」按此执行 | 说「调整」改分工 | 说「进 3.1/3.2」仅当**确实无助手能覆盖**时再走分支说明
```

> ❌ **错误写法**（编排层）  
> - 出现任何 **子技能全名、技能目录名、SKILL 路径**  
> - 「先 `code-locator` 再 `bugfix`」这类**父层技能排程**  
> - 把**文件路径、方法名、命令**写在 Step 3（属于执行细案，应在 subagent 内）
>
> ✅ **正确写法**（编排层）  
> - `[bugly-assistant] 负责：查明该 userId 在指定日的 crash/ANR 并给出可行动结论`  
> - `[cr-assistant] 负责：在代码改动后做提交前 review`  
> - 不指定 bugly 内部用 `bugly-user-investigator` 还是别的子技能 —— **由 bugly-assistant 内部决定**

### 上下文模式含义

| 标记 | 含义 | 执行方式 |
|------|------|---------|
| 🧊 隔离上下文 | 所有小助手（subagent） | 使用 `Task` 工具，以 `subagent_type='<名称>'` 启动独立 subagent |

> 所有小助手均已转为 `~/.claude/agents/` 下的 subagent，统一通过 Task 工具调用，无需区分共享/隔离模式。

> ⚠️ **无论哪种情况，有小助手时执行阶段都必须只通过 `Task` 进小助手**，由小助手**内部**调度子技能。规划层**不预写**子技能名，正为了避免父层与执行层「对表技能名」后绕开 subagent。

### 方案确认后的执行（必须先写入 Step3 令牌）

用户说「开始」确认协作方案后，**在启动任一 subagent 之前**，将令牌写入状态文件中当前任务条目：

```markdown
- 🚦 Step3令牌：<助手路由摘要，只含助手名与责任/顺序，不含子技能名>
```

**令牌内容示例**：
- 走 3.0：`[3.0] bugly-assistant(用户侧异常根因) → cr-assistant(改动后 CR)`
- 走 3.1：`[3.1] dev-assistant 全栈包干 或 [3.1] 子上下文:bugfix（主会话不执行）`
- 走 3.2：`[3.2] 多助手：A(定位域) → B(实现域) + [人工] 发版`

**写入失败处理**：若状态文件不可达，必须告知用户并暂停，不得继续执行。

### 子助手执行方式

所有小助手均为 subagent，统一使用 `Task` 工具启动，在 `prompt` 中注入：

1. 上游结论摘要（根因分析、受影响文件路径、代码 diff 描述等）
2. 明确的输出要求

#### ⛔ 规划确认后的执行禁区（在启动 subagent 之前绝对不允许做的事）

| ❌ 禁止动作 | 为什么禁止 |
|-----------|-----------|
| `Read ~/.claude/skills/<子技能名>/SKILL.md` | 一旦读了子技能内容，父上下文会「滑入执行模式」，直接跑脚本，绕过 subagent |
| 在父上下文中运行子技能涉及的任何脚本/命令 | 即使只有一行 shell，也是绕过 subagent |
| 以「任务简单」「脚本已知」为由跳过 Task() | 没有例外 |

> **从「写入 Step3令牌」到「Task() 调用完毕」期间，父上下文唯一允许的文件读取是 `Read ~/.claude/agents/<助手名>.md`，其他任何 Read 都是错误。**

#### ⚠️ Cursor 环境下的启动方式（强制）

`~/.claude/agents/` 下的自定义 subagent 是 **Claude Code 原生机制**，Cursor 的 Task 工具**不支持自定义 `subagent_type` 名称**（直接写 `bugly-assistant` 等助手名会静默失败或报错）。

**Cursor 中必须按以下步骤启动**：

```
Step 1: Read("~/.claude/agents/<助手名>.md")   ← 先读取 agent 文件全文
Step 2: Task(
  subagent_type="generalPurpose",              ← 固定用 generalPurpose
  description="<助手名>：<业务块简述>",
  prompt="""
    你现在扮演 <助手名>，请严格按以下指令执行：

    ===== <助手名>.md 全文 =====
    <agent 文件全文，完整粘贴，不得省略>
    ===========================

    【上游背景】
    <上游助手的结论摘要：受影响文件路径、代码改动描述、根因分析结论等>

    【当前任务】
    <用业务语言描述要这个 subagent 完成什么、可验收结果是什么>
    # 不要写「请调用某子技能」——由 subagent 根据 agent 文档自行选技能

    【输出要求】
    <具体要 subagent 返回什么，如：CR 报告、风险评分、修复建议等>
  """
)
```

**三条铁律**：
- 🔴 `subagent_type` **永远写 `"generalPurpose"`**，不写助手名
- 🔴 agent 文件全文**必须完整注入** prompt，不能只写助手名
- 🔴 每个助手**独立一次 Task 调用**，保证上下文隔离（不在同一 prompt 里合并多个助手）

### 用户响应处理

- **用户选「调整」**：只改**助手分工/顺序/责任句**，不改成技能排程
- **用户选「进 3.1」/ 总管分析后无合适助手覆盖整任务**：进入 3.1

> **设计原则**：子助手的 `context_mode` 各助手自理；父层不维护技能映射表、不在 Step 3 为助手挑子技能。

## 3.1 单点委派（优先整包给**一个**助手；独立技能进子上下文）

在 3.0 无法自然拆成多助手、或**整任务**明显落在某个助手职责内时，用本分支，**仍不在父层做技能级排程**。

### 优先：一个助手全包

将任务**用业务话**包给**一个**小助手，Step 3 只展示例如：

```
🔍 单点委派
  ① [<助手名>] 全责：<一句话任务目标与验收口径>
执行顺序：仅一步（一次 Task）
说「用」确认 | 说「多助手」回到 3.0 重拆
```

**用户确认后** 令牌写：`[3.1] <助手名> 全包: <6 字内主题>`。执行 = **只** 对该助手做一次 `Task`，由其内部选子技能、拆步。

### 次选：无合适助手、却有成熟独立技能

仅当**任何**小助手都不覆盖该题、且你确有「专项技能能一口吃掉」时，才在令牌标注 **`[3.1] 子上下文执行:<技能名>`**（示例：`bugfix`、`tapd-tech-story`）。**父会话不** `Read` 该 `SKILL.md` 自跑；**必须** 用 `Task(generalPurpose)` 在**子上下文**里读技能并跑完（见 `task-execution.md`）。给用户看的 Step 3 **仍只写**「本任务将交给独立工作流在隔离环境完成」，不展开技能内步骤表。

- **不进入 3.2** 若 3.0/3.1 已能覆盖；进入 3.2 当需要**多段责任**又不宜再拆 3.0 时。

---

## 3.2 组合 / 兜底（仍只到「助手/域/人工点」，父层无技能表）

进入此分支说明：多助手 3.0 仍不贴切，且 3.1 单点也不合适。此时**只** 产出：

- 若干条 **`[<助手名>] 负责：<业务域或交付物>`** + **先后/并行**；或
- 明确 **`[人工] <环节名>`**（如「真机点按验证」「走审批」）而不写 `compile`/`git-commit` 等技能名；具体用哪个技能在 **Step 4 + task-execution** 中再对路由。

**禁止** 在 3.2 输出中恢复「旧版」那种 **逐步「调用某技能 + 具体文件/方法/行号」** 的长列表——那会把父上下文变成执行手册，诱发自执行。

**覆盖多种任务类型**（**编排层**只选形态，微观步骤在 subagent/执行模块）：

| 任务类型 | 父层长什么样（示例） |
|---------|-------------------|
| 多域协作 | `dev-assistant(实现) → cr-assistant(改后审查) → [人工] 发版` |
| 调研 | `某助手(调研+结论) 或 [人工] 决策拍板` |
| 需人多点 | 标 `[人工]` 节点名，不写命令 |

### 输出格式（示意）

```
📋 3.2 组合（无技能名版）

① [助手A] 负责：<域/结果>
② [助手B] 负责：<域/结果>，依赖 ①
③ [人工] <环节>（在 Step 4 中再配工具/说明）

说「用」确认
```

### ⚡ 必做：有人工节点时的「自动化可能」**一句话**（不展开技能清单）

**展示 3.2 后**，若含 `[人工]`，用**一句**话提示「到执行阶段可按 skill-discovery 再收紧」，**不要**在 Step 3 列出一串技能名当计划正文。

## 检查任务计划（3 轮自检，展示给用户前强制执行）

> 🔴 **无论走 3.0、3.1 还是 3.2，草案完成后、展示给用户前，须完成 3 轮。任何一轮失败 → 删改父层里违规的「技能/细案」后重过。**

### 轮次总览

| 轮次 | 检查主题 | 核心问题 |
|------|---------|---------|
| 第 1 轮 | **防「技能泄露」** | Step 3 成稿中是否**仍含** 子技能名、技能级跑单、文件/行号/命令等父层禁止项？有则**删回** 助手+责任 表述。 |
| 第 2 轮 | 总管安排合理性 | 助手**顺序/并行/依赖**是否合理？有否重复分派同一事？**不** 再检查「每技能是否写对助手名」—编排层**不该出现**技能。 |
| 第 3 轮 | 遗漏助手 | 从任务类型看，是否**缺了应出面的助手**？若缺的是「某**技能**」→ 不在这里补技能名，改为补 **哪个助手** 负责该能力域。 |

---

### 第 1 轮：防技能与细案泄露到父层

扫描**即将给用户看的 Step 3 正文**（不含内心独白）：

1. 是否出现 **`/` 式技能路径、`.md` 技能文件名、`子技能` 字样**？→ 删掉，改成助手责任句。
2. 是否出现 **「第 N 步调某某技能 / Read 某某 SKILL」**？→ 删掉，把「要的业务结果」留在助手责任里。
3. 是否出现 **可让父上下文直接动手的** 超细项（**精确文件路径+行号+贴代码**）？→ 移到**不展示**区或留给 subagent 执行时再生。

**发现问题 → 改父层文案，不得用「对表技能名」当修正手段**

```
🔍 第 1 轮：防泄露
  ❌ 稿中含「code-locator」→ 已删，改为 [dev-assistant] 负责：代码定位到可改状态
  ✅ 子技能 0 处出现在成稿
第 1 轮通过 ✅
```

---

### 第 2 轮：总管安排合理性

1. **顺序/依赖**：后游助手若需要上游的**结论文本**，顺序是否正确？并行列是否真的独立？
2. **冗余**：两个助手是否在做同一段业务事？
3. **context_mode**（若仍在你用的 agent 里维护）：**执行时**再核实即可；不在 Step 3 正文中展开技能以「对齐 context」。

---

### 第 3 轮：遗漏助手

仍用**任务域** 对照**应有助手**（下表是 **助手** 名，不展开为子技能）：

| 任务特征 | 常应出现的助手 | 在编排层怎么补 |
|---------|--------------|--------------|
| 有代码变更需 review | `cr-assistant` | 加一条 `[cr-assistant] 负责：提交前/合并前审查` |
| 上线风险关 | 同上域或 `cr-assistant` 包掉「风险/审查」**业务句** | 不写在父层 `production-risk-checker` 五字当步骤 |
| Bugly 域 | `bugly-assistant` 等 | 加助手责任，不写具体 investigator 名 |
| 伽利略 域 | `galileo-assistant` | 同理 |

- **必要** → 把**助手+责任**补进 3.0/3.2 稿，再给用户看  
- **建议** → 问用户是否加一轨助手，**仍不写技能**

---

### 3 轮全部通过后

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
🔎 计划自检（3 轮，编排层）
  第 1 轮 防泄露：✅
  第 2 轮 顺序/冗余：✅
  第 3 轮 助手覆盖：✅（含 1 条待用户定夺是否加助手轨）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**→ 再展示终稿、进入计划确认与 Step3 令牌**

## 计划确认 & Step3 令牌写入（强制门禁）

无论走 3.0、3.1 还是 3.2，**等待用户明确确认** 后，按以下流程结束规划阶段。

### 计划完整性自检（输出前 AI 自查，**编排层** 版）

- [ ] **子 agent 清单 + 各负责一句业务/验收** 已写清，或 3.1 单点/独立技能**一句**说清
- [ ] 成稿中 **0** 处子技能全名、**0** 处「父层技能排程」、**0** 处诱导父执行的微观代码/行号/命令**清单**（人工节点名可保留）
- [ ] **依赖/顺序/并行** 可读懂
- [ ] 无「TBD」类占位；不强迫在父层写清「全路径技战法」
- [ ] 该出现的助手**轨** 已出现（用第 3 轮表）

> 与旧版不同：不再把「每步都写了技能全名」当完整性的必要条件 —— 那是 **subagent 内** 的事。

### 用户确认

- 用户确认 → 写 Step3 令牌
- 用户要调整 → 只调**助手/责任/顺序**，不改成技能手册
- 用户说「直接执行」想跳过 → 拒绝；说明确认的是**路由**不是嗦技能

### 写入 Step3 令牌

```markdown
- 🚦 Step3令牌：<仅助手路由/单点/子上下文执行标记的摘要，见下表>
```

| 分支 | 摘要示例（均**不含** 子技能链） |
|------|-------------------------------|
| 3.0 | `[3.0] bugly-assistant(异常结论) → cr-assistant(改后审查)` |
