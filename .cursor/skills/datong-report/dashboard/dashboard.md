# 大同指标看板创建

核心目标：通过**自动分析用户项目代码**，完成「判断项目类型 → 规划指标 → 确保埋点就绪 → 生成指标看板」的全流程。



## 工作流程

```
Step 1：项目分析 → 扫描代码判断项目类型和技术栈
Step 1.5：场景识别 → 基于项目分析结果，匹配业务场景库，获取经验指标推荐
Step 2：指标规划 → 结合场景推荐 + 项目性质 + 用户意图，设计指标清单
Step 3：埋点就绪检查 → 检查埋点覆盖，缺失则进入埋点接入流程
Step 4：确认方案 → 先确认指标，再设计看板布局，用户可在对话中反复调整
Step 5：生成看板 → 生成 Prompt 并调用 MCP 接口创建看板
Step 6：引导埋点接入 → 询问用户是否开始埋点，进入埋点接入流程
```

---

## Step 1：项目分析

### 1.1 扫描项目，判断工程类型

自动扫描用户项目根目录，判断工程类型：

| 检测特征 | 判定结果 |
|---------|---------|
| 存在 `package.json` 且含 `react` / `vue` / `next` / `nuxt` / `vite` / `webpack` 等 Web 框架依赖 | **Web（H5）工程** |
| 存在 `build.gradle` + `com.android` | Android 终端工程 |
| 存在 `Podfile` 或 `.xcodeproj` + Swift/ObjC 源码 | iOS 终端工程 |
| 存在 `app.json` + `app.wxss` 或 `project.config.json` 中含 `miniprogramRoot` | 微信小程序 |
| 存在 `package.json` 但仅含 `express` / `koa` / `nest` / `egg` 等后端框架，无前端页面 | Node.js 后台服务 |
| 纯 Go / Java / Python 等后端项目 | 后端服务 |

判定完成后，记录工程类型，进入 Step 1.2 分析项目性质。

> ⚠️ 如果是全栈项目（如 Next.js 同时有前后端），以前端部分为主进行分析。

### 1.2 分析项目性质

确认工程类型后，进一步扫描代码理解项目性质：

**扫描内容：**

1. **路由文件** — 扫描 `router`、`routes` 相关文件，了解有哪些页面
2. **页面组件** — 扫描 `pages/`、`views/`、`src/` 下的主要组件，了解页面功能
3. **API 调用** — 扫描 `api/`、`services/` 目录或 `fetch`/`axios` 调用，了解业务接口
4. **状态管理** — 扫描 `store`、`redux`、`pinia`、`vuex` 等，了解核心数据模型
5. **package.json** — 分析依赖库推断业务方向（如 `antd-pro` → 管理后台，`video.js` → 视频类）

**产出项目分析摘要：**

```markdown
## 项目分析

- **框架**：{React/Vue/...} + {构建工具}
- **项目性质**：{如：企业管理后台 / 内容展示站 / 数据可视化平台 / 在线工具 / ...}
- **核心页面**：{列出主要页面及功能}
- **关键交互**：{列出主要的用户操作，如表单提交、列表筛选、文件上传等}
```

### 1.3 确定指标规划方向

| 情况 | 处理方式 |
|------|---------|
| 用户有明确的指标需求（如"我想看转化率"） | → 围绕用户需求规划，项目分析作为补充 |
| 用户无明确需求（如"帮我建个看板"） | → 基于项目分析，推荐通用指标 + 个性化指标 |

**不要主动询问用户"你是什么业务场景"，而是通过代码分析自行判断。**

### 1.4 用户说"生成埋点"时的边界

如果用户仅要求生成埋点代码，**不触发看板流程**，直接走埋点接入流程处理。

但如果对话上下文暗示用户可能还想做指标看板，可以**在埋点完成后**提示：

```markdown
埋点代码已生成。你是否还需要基于这些埋点事件创建指标看板？
```

> ⚠️ 不要在用户明确只要埋点的情况下强行推荐看板。

## Step 1.5：场景识别（经验指标推荐）

在项目分析完成后、指标规划开始前，通过场景库匹配业务场景，获取经验指标推荐。场景库提供了 10 个垂直行业的指标推荐方案，每个指标带有完整的口径定义和所需埋点。

### 【前置】检查业务自定义指标规范

进入本步前，执行 `custom-specs/` 前置检查（详见 `../references/custom-specs.md`）：

1. 扫描 skill 根目录下 `custom-specs/` 是否存在与**指标规范**相关的 md（文件名含 `metric`/`indicator`/`kpi`/`okr`/`northstar`，或通用补充）
2. 若命中：解析 `## 覆盖` / `## 补充` 章节，作为**最高优先级**输入，并入本步的场景打分、准入判断与指标清单合并
3. 若存在自定义**必选指标** → 合并到推荐清单中；存在**禁用指标/指标类型** → 从推荐结果中剔除；存在自定义**场景打分规则** → 覆盖默认打分
4. 目录不存在、无命中文件或内容为空 → 回退默认规则（场景库 + `metrics-planning.md`），无缝继续
5. 冲突硬性约束 → 暂存以写入最终指标清单的「规范来源」块

> 📖 场景库使用总则和规则 → `references/scenario-library/00-usage-guide.md`
> 📖 场景总索引 → `references/scenario-library/01-scene-index.md`

### 1.5.1 场景识别

基于 Step 1.2 的项目分析结果，按以下四类证据给场景打分：

| 证据类型 | 示例 |
|---------|------|
| 业务词 | 商品、购物车、课程、关卡、订阅、工单、KYC、pipeline、campaign |
| 核心实体 | `order`、`subscription`、`course`、`lead`、`ticket`、`wallet` |
| 关键流程 | 浏览→加购→支付、trial→付费、注册→KYC→首笔交易 |
| 页面/模块 | PDP、结算页、billing、课程页、CRM pipeline、客服工作台 |

**阈值判定：**

| 得分 | 判定 |
|------|------|
| >= 6 分 | **主场景** → 读取对应场景 md |
| 4～5 分 | **副场景** → 若与主场景强相关，再读 1 个 |
| < 4 分 | 不主推该场景指标 |

**读取策略：** 默认只读 **1 个主场景**，若第二高场景与主场景强相关，再读 **1 个副场景**。不要同时读 3 个以上场景文件。

> 📖 各场景文件见 `references/scenario-library/02-*.md` 至 `references/scenario-library/11-*.md`

### 1.5.2 从场景库筛选指标

读取场景 md 后，按以下准入条件筛选指标（三项中至少满足两项）：

1. **场景证据**：该指标是场景内的默认优先指标
2. **仓库证据**：代码、表结构、页面流程或埋点里能看到对应实体/动作
3. **数据可落地**：口径能写清楚，所需埋点/数据能拿到或可低成本补齐

### 1.5.3 输出场景推荐结果

将场景识别结果作为 Step 2 指标规划的输入：

| 情况 | 处理方式 |
|------|---------|
| 成功匹配到场景 | → 场景推荐指标作为指标规划的**经验参考基线**，与通用指标合并规划 |
| 未能明确匹配任何场景（得分均 < 4） | → 跳过场景推荐，按原有通用指标 + 个性化指标规划 |
| 匹配到场景但仓库证据不足 | → 将不满足准入条件的指标标记为 `not-ready`，在指标清单中标注缺失项 |

**场景推荐的指标默认上限：**

- 1 个 North Star 候选
- 5～8 个核心结果指标
- 3～6 个诊断指标
- 2～4 个护栏指标

> ⚠️ 场景不确定时，宁可少推也不要凑数。严格遵守各场景文件中「不要乱推」章节的约束。

> 📡 **上报 `metrics_recommended`**：本步完成后（无论是命中场景、降级为通用还是完全跳过）立即执行，记录推了什么：
> ```bash
> bash ../tools/report_event.sh metrics_recommended '{"skill_rec_flow":"dashboard","skill_rec_scene":"<scene_id|generic|none>","skill_rec_scene_score":"<score>","skill_rec_scene_secondary":"<scene_id_or_empty>","skill_rec_metric_count":"<N>","skill_rec_northstar_count":"<N>","skill_rec_core_count":"<N>","skill_rec_diagnostic_count":"<N>","skill_rec_fallback":"<yes/no>","skill_rec_note":"<≤200字：场景判断依据+关键证据+指标取舍原因，便于日后复盘>"}'
> ```
> 工作目录为 skill 根目录（`skills/datong-report/`），故路径前缀为 `../tools/`。

## Step 2：指标规划

### 【前置】检查业务自定义指标规范

进入本步前，执行 `custom-specs/` 前置检查（详见 `../references/custom-specs.md`）：

1. 若 Step 1.5 已完成前置检查，直接复用检查结果，不重复扫描
2. 业务自定义**必选指标**合并进清单；**禁用指标/类型**从清单排除
3. 业务自定义**清单列结构**（如额外增加"负责人"、"OKR 对齐"列） → 在下方 2.3 输出时采用自定义列
4. 业务自定义**计算口径**覆盖默认计算方式
5. 目录不存在或无命中 → 按默认规则执行

### 2.1 检查已有埋点信息

按以下顺序检查项目中是否已有埋点产出：

1. **检查 `dt_tracking_plan/` 目录** — 是否有埋点接入流程生成的埋点事件表格
2. **检查 `dt_tracking_info/` 目录** — 是否有通过 MCP 拉取的通用版埋点信息
3. **检查 `dt_page_structure/` 目录** — 是否有标准版页面结构信息

| 检查结果 | 后续路径 |
|---------|---------|
| 找到埋点信息文件 | → 读取文件，基于已有事件规划指标 |
| 用户提供了埋点信息码 | → 调用 `get_dt_tracking_info(code)` 获取 |
| 用户提供了 appId + pageId | → 调用 `get_page_structure(appId, pageId)` 获取 |
| 什么都没有 | → Step 2.2 从零开始 |

### 2.2 从零开始：指标驱动埋点

当项目没有任何埋点信息时，需要**指标驱动埋点**：

1. **优先使用 Step 1.5 的场景推荐指标**作为核心指标基线（如有）
2. **补充通用指标和个性化指标**（见 `references/metrics-planning.md`），与场景指标合并
3. **为每个指标推导出需要的埋点事件和参数**
   - 场景库中每个指标已自带「需要的埋点/数据」字段，可直接使用
   - 场景库中的业务语义事件名（如 `order_pay_success`）落地到大同时，映射为自定义事件或 `dt_` 标准事件
4. **确定每个指标的埋点方式**（声明式 or 代码打点）
5. **生成埋点事件表格**（复用 `../references/tracking-table-format.md` 格式）
6. 保存到 `dt_tracking_plan/` 目录

> 📖 指标规划的详细分类和规则见 `references/metrics-planning.md`
> 📖 场景库指标的口径定义和埋点需求见 `references/scenario-library/` 对应场景文件

### 2.3 输出指标清单

无论哪条路径，都需要产出一份**指标清单表**：

> 🔀 **自定义规范消费（来自 custom-specs/）**：
> - 若业务自定义规范声明了**自定义清单列结构** → 在下方默认表格基础上按自定义规则新增列或替换列（列名/语义可变，**列数与列顺序**可按业务规范调整）
> - 若业务自定义规范声明了**计算方式模板或分类体系** → 采纳自定义模板
> - 未被覆盖的格式项沿用默认
>
> 📌 **指标清单头部必写「规范来源」块**（详见 `../references/custom-specs.md` 第 6 节）：
>
> ```markdown
> > **规范来源**
> > - 自定义规范文件：{命中的 custom-specs/*.md 文件名列表；若无命中固定写作「无（使用默认规范）」}
> > - 已应用规则：
> >   - {例：必选指标 tenant_health_score（来自 metrics-spec.md 补充）}
> >   - {例：禁用 PV/UV 基础指标（来自 metrics-spec.md 覆盖）}
> > - 被拒绝覆盖的条目（如有）：
> >   - {条目 + 原因}
> ```

```markdown
## 指标清单

| 序号 | 指标名称 | 指标类型 | 计算方式 | 依赖事件 | 依赖参数 | 埋点方式 |
|:----:|---------|---------|---------|---------|---------|:-------:|
| 1 | 页面 PV | 基础指标 | COUNT(dt_pgin) | dt_pgin | dt_pgid | 声明式 |
| 2 | 页面 UV | 基础指标 | COUNT(DISTINCT user_id) WHERE event=dt_pgin | dt_pgin | dt_pgid | 声明式 |
| 3 | 平均停留时长 | 基础指标 | AVG(dt_lvtm) WHERE event=dt_pgout | dt_pgout | dt_pgid, dt_lvtm | 声明式 |
| 4 | 元素点击率 | 互动指标 | COUNT(dt_clck) / COUNT(dt_imp) | dt_clck, dt_imp | dt_eid | 声明式 |
| 5 | 表单提交成功率 | 业务指标 | COUNT(form_submit_success) / COUNT(form_submit) | form_submit, form_submit_success | form_name | 代码打点 |
```

**埋点方式判定规则：**

| 埋点方式 | 适用场景 | 说明 |
|---------|---------|------|
| **声明式** | 页面曝光（`dt_pgin`）、页面退出（`dt_pgout`）、元素曝光（`dt_imp`）、元素结束曝光（`dt_imp_end`）、元素点击（`dt_clck`） | 通过在 DOM 元素上标记 `dt-eid`、`dt-pgid` 等属性，采集 SDK 自动检测并采集，无需手写上报代码 |
| **代码打点** | 自定义行为事件（如表单提交、搜索、支付、文件上传等） | 需要在对应业务代码位置手动调用 SDK 上报方法 |

> ⚠️ 判定原则：如果指标依赖的事件属于 SDK 内置自动采集的事件类型（页面曝光、元素曝光、元素点击），则为声明式；否则为代码打点。

## Step 3：埋点就绪检查

确认指标清单所依赖的埋点事件是否已就绪。**缺失埋点时，保存指标清单后直接进入埋点接入流程。**

### 3.1 检查已有埋点

扫描项目中是否已有埋点：

| 检查位置 | 说明 |
|---------|------|
| `dt_tracking_plan/` 目录 | 埋点接入流程生成的埋点事件表格 |
| `dt_tracking_info/` 目录 | 通过 MCP 拉取的通用版埋点信息 |
| 代码中的 `dt-eid`、`dt-pgid` 属性 | 声明式埋点标记 |
| 代码中的 SDK 上报调用 | 代码打点 |

### 3.2 对比埋点覆盖情况

将指标清单中**依赖的事件**与**已有的埋点事件**做对比：

| 情况 | 处理方式 |
|------|---------|
| 所有依赖事件都已有埋点 | → 直接进入 Step 4 |
| 存在缺失的埋点事件 | → 输出指标清单，进入埋点接入流程完成埋点 |

### 3.3 缺失埋点时的处理

当存在缺失埋点时，将指标清单保存到 `dt_tracking_plan/dashboard-metrics.md`，然后提示用户：

> 📌 **保存到 `dt_tracking_plan/dashboard-metrics.md` 前，必须在文档头部插入「规范来源」块**（详见 `../references/custom-specs.md` 第 6 节）；无命中时固定写作「无（使用默认规范）」。

```markdown
指标看板需要以下埋点事件支持，我已将指标清单整理到 `dt_tracking_plan/dashboard-metrics.md`。

| 缺失事件 | 埋点方式 | 用途 |
|---------|:-------:|------|
| `dt_pgin` / `dt_pgout` | 声明式 | 页面 PV/UV/停留时长 |
| `dt_clck` | 声明式 | 元素点击率 |
| `form_submit` | 代码打点 | 表单提交统计 |

接下来我将为你完成这些埋点的代码接入。
```

随后直接进入主 SKILL.md 的**埋点接入流程**（从 Step 1 开始），使用 `dt_tracking_plan/dashboard-metrics.md` 作为埋点输入。埋点完成后自动回到 Step 4 继续看板流程。

**指标清单文件格式：**

指标清单需要包含足够信息供埋点接入流程直接消费：

```markdown
## 看板指标清单（供埋点接入流程消费）

| 序号 | 指标名称 | 依赖事件 | 事件含义 | 依赖参数 | 埋点方式 | 备注 |
|:----:|---------|---------|---------|---------|:-------:|------|
| 1 | 页面 PV | dt_pgin | 页面曝光 | dt_pgid | 声明式 | SDK 自动采集 |
| 2 | 平均停留时长 | dt_pgout | 页面退出 | dt_pgid, dt_lvtm | 声明式 | SDK 自动采集 |
| 3 | 按钮点击率 | dt_clck | 元素点击 | dt_eid | 声明式 | 需标记 dt-eid |
| 4 | 表单提交数 | form_submit | 表单提交 | form_name, result | 代码打点 | 需手动上报 |
```

## Step 4：确认指标方案 & 看板布局

本步骤包含**两轮确认**：先确认指标，再确认看板布局。用户可在对话中反复调整，直到满意为止。

### 4.1 展示指标方案

```markdown
## 指标看板方案

### 看板名称：{项目名称}数据看板

### 项目分析
- **项目性质**：{项目性质}
- **核心页面**：{页面列表}

### 指标列表

| 序号 | 指标名称 | 指标类型 | 计算方式 | 埋点方式 | 状态 |
|:----:|---------|---------|---------|:-------:|:----:|
| 1 | 页面 PV | 基础指标 | COUNT(dt_pgin) | 声明式 | ✅ 就绪 |
| 2 | 页面 UV | 基础指标 | COUNT(DISTINCT user_id) | 声明式 | ✅ 就绪 |
| 3 | 平均停留时长 | 基础指标 | AVG(dt_lvtm) | 声明式 | ✅ 就绪 |
| 4 | 表单提交率 | 业务指标 | 提交数/访问数 | 代码打点 | ⚠️ 缺埋点 |

---
> 指标列表有需要增减或调整的吗？确认后我来设计看板布局。
```

**用户可能的调整操作：**

| 用户意图 | 处理方式 |
|---------|---------|
| 增加指标 | 补充指标到清单，重新评估埋点覆盖 |
| 删除指标 | 从清单移除 |
| 修改计算方式 | 更新对应行 |
| 确认指标 | → 进入 4.2 看板布局设计 |

> 📡 **上报 `metrics_confirmed`**：用户对指标清单给出最终反馈后（可能经 1~N 轮调整）立即执行，记录推荐效果：
> ```bash
> bash ../tools/report_event.sh metrics_confirmed '{"skill_conf_flow":"dashboard","skill_conf_action":"<accept_all/modified/rejected>","skill_conf_final_metric_count":"<N>","skill_conf_added_count":"<N>","skill_conf_removed_count":"<N>","skill_conf_rounds":"<N>","skill_conf_scene":"<scene_id>","skill_conf_note":"<≤200字：用户改了哪些+用户给出的理由+复盘要点>"}'
> ```
> - `accept_all`：用户直接确认，未做任何增删改
> - `modified`：用户做了增加/删除/修改后确认
> - `rejected`：用户明确拒绝推荐（如「不要这些指标，我自己决定」）

## Step 5：生成看板

### 5.1 生成看板 Prompt

本 skill 的 MCP 接口（`create_dashboard`）接收的不是 JSON 配置，而是一段**结构化 Prompt**，交给智能看板平台解析并自动创建看板。

Prompt 由两部分组成：

```
Part 1：埋点方案 — 描述业务埋点的事件、参数、触发时机
Part 2：看板方案 — 描述看板的图卡布局 + 每个图卡的伪 SQL 计算逻辑
```

**生成规则：**

1. **Part 1（埋点方案）**：基于 Step 2-3 已确定的埋点事件，按模块/页面分组，列出事件表格（含 trigger、ui、event_code、dt_pgid、dt_eid、udf_kv、remark）
2. **Part 2（看板方案）**：基于 Step 4 最终确认的看板布局，为每个图卡编写 ASCII 布局图和伪 SQL 计算逻辑

> 📖 Prompt 的详细格式规范、字段说明和完整示例见 `references/dashboard-prompt.md`

### 5.2 调用 MCP 接口创建看板

调用 `create_dashboard` MCP 工具，传入生成的 Prompt 文本。

> ⚠️ `create_dashboard` 工具需要在 MCP 服务器中注册（如尚未实现，需先添加该工具）。

**Prompt 开头固定引导语：**

```
这个知识库里包含业务的埋点明细数据。请基于明细数据和以下信息，生成看板图卡。（这些埋点才刚实现，线上可能还没有正式上报数据，所以查询无数据属于正常现象。）
```

### 5.3 保存看板方案文档

将完整的 Prompt 保存到项目中：

- **目录**：项目根目录下的 `dt_tracking_plan/`（不存在则创建）
- **文件名格式**：`{看板名称}-YYYYMMDDHH.md`
- **内容**：完整的 Prompt（含埋点方案 + 看板方案）

### 5.4 引导用户使用看板 Prompt

Prompt 文件保存后，向用户发送以下提示：

```markdown
✅ 看板 Prompt 文档已生成：`dt_tracking_plan/{文件名}.md`

你可以将此文档的内容复制到大同平台的**智能看数**模块，自动生成看板图卡。

👉 前往智能看数：https://trackmate.woa.com/#/d/repRegistry-dola?appId={appId}&menuN=RepRegistryDola

> 💡 Tip：新创建的应用需要先开启「智能看数」功能才能使用。
```

**`appId` 获取方式：**

- 如果流程中已通过 `get_by_appkey` 工具获取过 `appId`，直接使用
- 如果尚未获取，此时调用 `get_by_appkey`（传入项目的 appkey）获取 `appId`
- 如果 `get_by_appkey` 调用失败（未配置 MCP），链接中 `appId` 部分使用占位符 `YOUR_APP_ID`，并提示用户手动替换

## 大同事件名称规范

本 skill 涉及的所有事件必须使用以下标准名称：

| 事件名 | 含义 | 类型 | 关键参数 |
|--------|------|------|---------|
| `dt_pgin` | 页面曝光（页面进入） | 自动采集 | `dt_pgid`（页面标识） |
| `dt_pgout` | 页面结束曝光（页面退出） | 自动采集 | `dt_pgid`, `dt_lvtm`（页面停留时长，毫秒） |
| `dt_imp` | 元素曝光 | 自动采集 | `dt_eid`（元素标识） |
| `dt_imp_end` | 元素结束曝光 | 自动采集 | `dt_eid` |
| `dt_clck` | 元素点击 | 自动采集 | `dt_eid` |
| 自定义事件 | 业务自定义行为 | 手动上报 | 业务自定义参数 |

> 不要使用 `page_exposure`、`element_click` 等非标准名称。所有事件名称必须严格遵循上述规范。
> 不要使用 pgid + dt_pgin 或者 dt_eid + dt_clck 组合成一个event_code, 在计算指标条件是，是where的两个条件，而不是组合成一个event_code 条件，这是错误的方式。

## 看板流程与埋点接入流程的内部协作

本文件（看板流程）与主 SKILL.md 中的埋点接入流程同属一个 skill 的两个子流程，通过 `dt_tracking_plan/` 目录下的文件衔接。

| 场景 | 看板流程做什么 | 埋点接入流程做什么 |
|------|-------------|-----------------|
| 用户只要埋点 | 不介入 | 全权处理 |
| 用户要看板，已有埋点 | 规划指标 → 生成看板 | 不介入 |
| 用户要看板，没有埋点 | 规划指标 → 输出指标清单到 `dt_tracking_plan/` → 进入埋点接入流程 → 埋点完成后回来继续生成看板 | 消费指标清单，完成 SDK 初始化 + 埋点代码生成 |
| 用户先做埋点再要看板 | 读取 `dt_tracking_plan/` 产出 → 规划指标 → 生成看板 | 先独立完成（产出文件供看板流程读取） |

**协作原则**：
1. **职责清晰**：看板流程只做「指标规划 + 看板生成」，埋点接入流程只做「埋点实现」
2. 两个流程通过 `dt_tracking_plan/` 目录下的文件作为衔接契约
3. 指标清单中的**埋点方式**字段是关键桥梁——埋点接入流程据此决定生成声明式属性还是手动上报代码

## 核心概念

- **指标（Metric）**：基于埋点事件计算的业务数据项，如 PV、UV、转化率
- **看板（Dashboard）**：多个指标的可视化集合，包含卡片、图表、表格等组件
- **埋点事件（Event）**：SDK 上报的原始数据，是指标计算的数据源
- **声明式埋点**：在 DOM 元素上标记 `dt-eid`、`dt-pgid` 等属性，采集 SDK 自动检测采集，无需手写代码
- **代码打点**：在业务代码中手动调用 SDK 上报方法，用于自定义行为事件
- **appkey**：SDK 初始化用的应用标识，在 https://datong.woa.com 获取
- **appId**：大同平台应用 ID，用于接口调用
