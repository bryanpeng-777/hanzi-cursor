# 场景库使用总则

## 1. 目标

这套场景库不是“KPI 大全”，而是一个**受约束的指标推荐器**。

它解决两个问题：

1. 避免 SKILL 在不懂业务时胡乱推荐一堆指标。
2. 让每个被推荐的指标都自带：**适用条件、建议口径、所需埋点/数据、关键切片**。

---

## 2. 使用顺序

```text
读代码仓库 / 页面结构 / 数据模型
→ 识别主场景（最多再加 1 个副场景）
→ 读取对应场景 md
→ 挑出“场景适用 + 仓库可支持”的指标
→ 再生成指标方案 / 看板草图 / 补埋点建议
```

---

## 3. 场景识别规则

建议按四类证据给场景打分：

- 业务词：商品、购物车、课程、关卡、订阅、工单、KYC、pipeline、campaign
- 核心实体：`order`、`subscription`、`course`、`lead`、`ticket`、`wallet`
- 关键流程：如浏览→加购→支付、trial→付费、注册→KYC→首笔交易
- 页面/模块：如 PDP、结算页、billing、课程页、CRM pipeline、客服工作台

简单阈值建议：

- **>= 6 分**：主场景
- **4～5 分**：副场景
- **< 4 分**：不要主推该场景指标

---

## 4. 指标是否允许被推荐

每个指标至少同时满足下面三项中的两项，才允许进入“推荐列表”：

- 场景证据：该指标是场景内的默认优先指标
- 仓库证据：代码、表结构、页面流程或埋点里能看到对应实体/动作
- 数据可落地：口径能写清楚，所需埋点/数据能拿到或可低成本补齐

---

## 5. 每个推荐指标必须写出的字段

- **类型**：North Star / 核心结果 / 诊断 / 护栏
- **何时推荐**：什么业务前提下才该推荐
- **建议口径**：分子、分母、时间窗口、cohort 起点、是否去重
- **需要的埋点 / 数据**：业务事件、业务表、必要字段
- **关键属性 / 常见切片**：如 `channel`、`sku_id`、`plan`、`country`

推荐输出格式：

```md
- 指标：支付转化率
- 类型：诊断
- 何时推荐：仓库存在详情、加购、结算、支付链路
- 建议口径：支付买家数 / 到站访客数（总览口径）；同时展示详情→加购→结算→支付分段转化
- 需要的埋点 / 数据：visit、view_item、add_to_cart、begin_checkout、order_pay_success
- 关键属性 / 常见切片：channel、category、sku_id、device、region
```

---

## 6. 事件命名与大同映射

场景库里优先用**业务语义事件名**，例如：

- `order_pay_success`
- `course_complete`
- `subscription_cancel`
- `transaction_failed`

真正落地到大同时，再映射为：

- 自动事件：`dt_pgin` / `dt_pgout` / `dt_imp` / `dt_clck`
- 自定义事件：带业务语义的 custom event
- 参数：如 `order_id`、`plan`、`course_id`、`country` 等

这样场景库能跨端复用，也更容易先讨论“业务口径”，再讨论“SDK 写法”。

---

## 7. 默认推荐上限

- 1 个 North Star 候选
- 5～8 个核心结果指标
- 3～6 个诊断指标
- 2～4 个护栏指标

场景不确定时，宁可少推，也不要凑数。

---

## 8. 禁止乱推的通用规则

1. 没有订单 / 支付，不要推 GMV。
2. 没有订阅 / 账单，不要推 MRR / NRR。
3. 没有工单状态流转，不要推 FRT / 解决时长。
4. 没有 cohort 起点或时间窗，不要装作已经定义了留存、复购、LTV。
5. 没有稳定用户 ID，不要轻易推荐跨天/跨周期指标。
