# custom-specs 目录读取与合并规则

> 本文定义 skill 如何识别、读取、合并业务方放在 `../custom-specs/` 下的自定义规范文档。  
> 在指标规划与埋点方案设计流程中，所有引用本机制的步骤都以"**先查 custom-specs**"作为前置指令。

---

## 1. 识别规则

扫描 `../custom-specs/` 目录（相对 skill 根目录：`skills/datong-report/custom-specs/`）下所有 `.md` 文件（递归 1 层即可，忽略 `README.md`）。按文件名关键词分类：

| 关键词（文件名小写含任一即命中） | 归类为 | 消费场景 |
|----------|-------|---------|
| `metric`、`indicator`、`kpi`、`okr`、`northstar` | **指标规范** | `dashboard/dashboard.md` 的 Step 1.5 / Step 2；`references/tracking-plan.md` 的 Step 0b |
| `tracking`、`event`、`plan`、`param`、`naming` | **埋点方案规范** | `references/tracking-plan.md` 的 Step 1b / Step 3b；`references/tracking-table-format.md` |
| 以上都不命中 | **通用补充** | 两类流程均会读取，作为补充参考 |

> ⚠️ 同一份 md 同时含多个关键词时，两类场景都会读取该文件。  
> ⚠️ 关键词匹配**大小写不敏感**。

---

## 2. 覆盖 vs 补充语义

业务方在自定义 md 内用**二级标题**显式声明每个章节的意图：

| 二级标题 | 语义 | 合并方式 |
|---------|------|---------|
| `## 覆盖` 或 `## Override` | 覆盖默认规范中对应项 | 高优先级规则整段替换默认对应章节的指令 |
| `## 补充` 或 `## Append` | 在默认规范基础上追加 | 高优先级规则与默认规则**合并使用** |
| 未声明 | 默认视为"补充" | 同上 |

**示例：**

```markdown
## 覆盖：事件命名规则

所有 event_code 必须以 biz_ 前缀开头，使用 snake_case。

## 补充：必选公参

除 SDK 默认参数外，所有事件必须携带：
- tenant_id（租户ID）
- user_tier（用户等级）
```

---

## 3. 优先级链（从高到低）

合并多来源规范时，严格按以下固定顺序处理：

| 级别 | 来源 | 说明 |
|------|------|------|
| 🥇 P1 | `custom-specs/` 目录下的业务自定义规范 | 本机制新增入口，最高优先级 |
| 🥈 P2 | 项目中已有的埋点/指标产出 | `dt_tracking_plan/` / `dt_tracking_info/` / `dt_page_structure/` 下的历史方案，用于保持项目一致性 |
| 🥉 P3 | skill 内置默认规范 | `metrics-planning.md` / `scenario-library/*` / `tracking-plan.md` / `tracking-table-format.md` |

**合并原则：**

1. **高优先级有规定** → 采用高优先级，不做静默合并。
2. **高优先级未规定（留空）** → 用低优先级兜底补齐该项。
3. **高优先级声明 `## 补充`** → 与低优先级规则叠加使用。
4. **高优先级声明 `## 覆盖`** → 整段替换对应章节的低优先级规则。

---

## 4. 硬性约束清单（不可被覆盖）

以下项即使业务自定义规范声明"覆盖"，系统也 SHALL 拒绝采纳，并在对话中明确提示用户：

| 约束项 | 原因 |
|-------|------|
| **`event_code` 作为埋点主键**，不得省略或用其他字段替换；完整主键三字段为 `event_code` + `dt_pgid` + `dt_eid` | 数据库主键，修改会导致历史数据断裂；缺失 `event_code` 会使事件无法唯一定位与聚合 |
| `tracking-table-format.md` 固定 7 列的**列名与语义**（`trigger` / `ui` / `event_code` / `dt_pgid` / `dt_eid` / `udf_kv` / `remark`） | 下游解析契约，列名变更会导致解析失败 |
| 大同标准事件名语义：`dt_pgin` / `dt_pgout` / `dt_imp` / `dt_imp_end` / `dt_clck` | SDK 自动采集语义固定，与上报协议强绑定 |
| MCP 接口契约（工具名、入参 scheme） | 平台接口规范，与后端服务强约束 |

> ⚠️ 业务自定义规范**可以新增**（如附加列、必选公参、必选指标），但**不可修改或删除**上述硬性约束项。  
> ⚠️ 遇到冲突时，在对话中向用户说明被拒绝的条目与原因（详见第 6 节）。

---

## 5. 回退行为

当以下任一条件成立时，完全回退到 skill 内置默认规范，行为与未引入 `custom-specs/` 时一致：

- `custom-specs/` 目录不存在
- 目录存在但没有任何 `.md` 文件（或仅有 `README.md`）
- 目录下所有 md 文件内容为空或未命中识别规则

回退时：
- 不阻塞任何流程
- 产出文档头部显式标注"使用默认规范（无业务自定义规范）"

---

## 6. 自定义规范的记录（内部参考）

自定义规范的命中情况仅作为**内部执行参考**，不写入最终产出文件：

- `dt_tracking_plan/` 下的埋点方案文档：**只包含 `## 埋点事件表` + 表格数据，不允许有任何标题、引用块或说明性文字**
- 指标清单：在对话中向用户展示即可，无需写入文件头部

**内部记录方式**（不输出到文件）：
1. 命中自定义规范 → 在执行过程中参考其覆盖/补充规则
2. 存在硬性约束冲突 → 在对话中向用户说明被拒绝的条目及原因

---

## 7. 前置指令清单（供各流程文档引用）

各流程文档在进入对应环节时，都应先执行以下前置指令：

```
【custom-specs 前置检查】
1. 扫描 skill 根目录下的 custom-specs/ 目录是否存在
2. 若存在，按第 1 节识别规则筛选相关 md 文件
3. 读取命中的文件，解析 ## 覆盖 / ## 补充 章节
4. 按第 3 节优先级链与默认规范合并
5. 若命中硬性约束冲突（第 4 节），记录冲突项（内部参考，不写入文件）
6. 若目录不存在或无命中文件，直接使用默认规范（第 5 节）
```
