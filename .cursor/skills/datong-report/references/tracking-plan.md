# 从零开始的埋点方案设计流程

> 本文档仅在用户选择了「B）从零开始」时使用。详见 SKILL.md 中 Step 1.5 的条件判断（A/B 两个选项）。

---

## SDK 选择

根据 Step 1 识别的技术栈，选择对应平台的默认 SDK：

| 技术栈 | 默认 SDK | 上报方式 | 文档路径 |
|--------|---------|---------|----------|
| H5 | universal-report | 声明式埋点（标签）+ 手动埋点 | `../sdk/h5/universal-report/quickstart.md` |
| Android | beacon | 手动埋点 | `../sdk/android/beacon/quickstart.md` |
| iOS | beacon | 手动埋点 | `../sdk/ios/beacon/quickstart.md` |

> ⚠️ H5 端默认使用 **universal-report**，优先采用声明式标签埋点（`dt-pgid`、`dt-eid`、`dt-params`），与页面和元素无关联的事件使用手动埋点 API（`reportEvent`）。仅在用户明确指定时才使用其他 SDK（如 `beacon-web-sdk`、`autotrack`）。

---

## 总体流程

```
Step 0b：场景识别 & 指标推荐（业务目标对齐）
Step 1b：由指标反推事件，生成埋点方案文档（md）
Step 2b：根据方案编写上报代码
Step 3b：将埋点方案整理成表格式文档（md）
→ 完成后执行 SKILL.md 中的「埋点方案上传规则」
```

> 🎯 **核心思想：指标驱动埋点**。从零开始时不盲目穷举页面元素，而是先通过业务场景识别出用户最关心的业务指标，再由指标反推所需的埋点事件。这样产出的埋点方案是"有业务价值的埋点"，而非"把所有按钮都埋一遍"。

## Step 0b：场景识别 & 指标推荐

在开始设计埋点前，先对齐业务目标：扫描项目 → 识别业务场景 → 推荐核心指标 → 与用户确认。

### 【前置】检查业务自定义指标规范

进入本步前，先执行 `custom-specs/` 前置检查（详见 `custom-specs.md`）：

1. 扫描 skill 根目录下 `custom-specs/` 是否存在与**指标规范**相关的 md（文件名含 `metric`/`indicator`/`kpi`/`okr`/`northstar`，或通用补充）
2. 若命中：解析 `## 覆盖` / `## 补充` 章节，作为**最高优先级**输入并入本步的场景打分、指标准入与清单输出
3. 若存在自定义**必选指标** → 合并进推荐清单；存在**禁用指标/类型** → 从推荐清单排除；存在自定义**清单列结构** → 输出清单时采用自定义列
4. 目录不存在、无命中文件或内容为空 → 回退默认规则，无缝继续
5. 冲突硬性约束 → 记录被拒绝条目（内部参考用），流程继续

### 执行步骤

1. **项目分析**（轻量版，不出完整的项目摘要，只记录关键信号）
   - 扫描路由、页面组件、API 调用、状态管理、`package.json` 依赖
   - 识别关键业务词、核心实体、关键流程、页面/模块类型

2. **场景匹配**（读取场景库）
   - 首先读取场景总索引：`../dashboard/references/scenario-library/01-scene-index.md`
   - 按四类证据（业务词 / 核心实体 / 关键流程 / 页面模块）对各场景打分
   - 得分 ≥ 6 → 确定主场景，读取对应的场景文件（`02-*.md` 至 `11-*.md`）
   - 得分 4-5 且与主场景强相关 → 可选再读 1 个副场景
   - 所有场景均 < 4 分 → 跳过场景推荐，降级为通用指标推荐

   > 📖 场景库使用规则详见 `../dashboard/references/scenario-library/00-usage-guide.md`

3. **输出指标推荐清单**（精简版，不做看板布局设计）

   向用户展示以下精简格式：

   ```markdown
   ## 📊 业务指标推荐

   基于项目代码分析，识别到的业务场景：**{场景名}**（命中证据：{业务词/实体/流程}）

   推荐你优先关注以下指标（埋点会围绕这些指标设计）：

   | 序号 | 指标名称 | 指标类型 | 业务含义 | 所需核心事件 |
   |:----:|---------|:-------:|---------|-------------|
   | 1 | {North Star} | 北极星 | {说明} | {事件列表} |
   | 2 | {核心结果指标} | 核心 | {说明} | {事件列表} |
   | ... | ... | ... | ... | ... |

   ---
   > 👉 这些指标合适吗？你可以：
   > - ✅ 确认 → 我将据此设计埋点方案
   > - ➕ 增加指标（如"还想看 XX"）
   > - ➖ 删除某个指标
   > - 🔄 改为通用页面行为指标（PV/UV/点击率等）
   ```

   **指标推荐上限**（避免过度推荐）：
   - 1 个 North Star 候选
   - 3-5 个核心结果指标
   - 2-3 个诊断指标

   > 📡 **上报 `metrics_recommended`**：清单输出给用户后立即执行，记录推了什么：
   > ```bash
   > bash tools/report_event.sh metrics_recommended '{"skill_rec_flow":"tracking","skill_rec_scene":"<scene_id|generic|none>","skill_rec_scene_score":"<score>","skill_rec_scene_secondary":"<scene_id_or_empty>","skill_rec_metric_count":"<N>","skill_rec_northstar_count":"<N>","skill_rec_core_count":"<N>","skill_rec_diagnostic_count":"<N>","skill_rec_fallback":"<yes/no>","skill_rec_note":"<≤200字：场景判断依据+关键证据+指标取舍原因，便于日后复盘>"}'
   > ```

4. **用户确认**

   | 用户选择 | 处理方式 |
   |---------|---------|
   | ✅ 确认指标 | → 进入 Step 1b，由指标反推事件 |
   | ➕➖🔄 调整指标 | 更新清单后重新展示，直到用户确认 |
   | 明确说"不要推荐指标，直接扫代码埋点" | → 跳过 Step 0b，按旧逻辑穷举页面元素（见 Step 1b 备选路径） |
   | 场景未命中（降级情况） | → 使用通用指标模板：PV/UV、页面停留时长、关键元素点击率、核心表单提交率 |

   > 📡 **上报 `metrics_confirmed`**：用户给出最终反馈后（可能经 1~N 轮调整）立即执行，记录推荐效果：
   > ```bash
   > bash tools/report_event.sh metrics_confirmed '{"skill_conf_flow":"tracking","skill_conf_action":"<accept_all/modified/rejected>","skill_conf_final_metric_count":"<N>","skill_conf_added_count":"<N>","skill_conf_removed_count":"<N>","skill_conf_rounds":"<N>","skill_conf_scene":"<scene_id>","skill_conf_note":"<≤200字：用户改了哪些+用户给出的理由+复盘要点>"}'
   > ```
   > - `accept_all`：用户直接确认，未做任何增删改
   > - `modified`：用户做了增加/删除/修改后确认
   > - `rejected`：用户明确拒绝指标推荐（选择穷举页面或通用模板）

> ⚠️ Step 0b 的产出是**指标清单**，不是埋点方案。不在此步写事件命名细节，那是 Step 1b 的任务。
>
> ⚠️ 指标推荐要**克制**，宁可少推不要凑数。每个推荐指标都要能从仓库找到证据（有对应页面/接口/实体）。

## Step 1b：由指标反推事件，生成埋点方案

基于 Step 0b 确认的指标清单，为每个指标反推所需的事件和参数，结合项目代码定位事件的触发位置，产出 **md 格式的埋点方案文档**。

### 【前置】检查业务自定义埋点方案规范

进入本步前，执行 `custom-specs/` 前置检查（详见 `custom-specs.md`）：

1. 扫描 skill 根目录下 `custom-specs/` 是否存在与**埋点方案规范**相关的 md（文件名含 `tracking`/`event`/`plan`/`param`/`naming`，或通用补充）
2. 若命中：解析 `## 覆盖` / `## 补充` 章节，作为**最高优先级**输入并入本步的事件命名、参数设计、事件分类、方案组织方式
3. 具体消费方式详见下方「事件设计规则」与「方案文档保存规则」章节
4. 目录不存在、无命中文件或内容为空 → 回退默认规则
5. 冲突硬性约束（事件三字段主键、标准事件名语义等） → 记录被拒绝条目（内部参考用），不写入最终文档

注意： 如果业务代码已存在埋点，不要去修改， 除非是用户指明要修改。原因：比如原来标记页面id为A， 我们直接改的话变成B会影响业务已有的数据分析统计，所以不改；但是用户觉得原来的A要调整，那我们的埋点方案才改。

### 分析步骤

1. **指标 → 事件映射**：遍历 Step 0b 指标清单，为每个指标列出所需事件（事件名、dt_pgid、dt_eid、关键参数）
2. **事件 → 代码位置映射**：扫描项目路由/组件，为每个事件定位对应的页面和元素
3. **补齐基础埋点**：除指标直接依赖的事件外，补充必要的基础事件（如页面曝光 `dt_pgin`、页面退出 `dt_pgout`）
4. **按页面组织输出**：按页面维度汇总事件，产出埋点方案文档

### 备选路径：用户明确不要指标推荐

如果用户在 Step 0b 明确拒绝指标推荐，则按原有逻辑穷举：

1. **识别所有页面**（路由级组件/视图）
2. **逐页面分析交互元素**（按钮、卡片、弹窗、标签页、表单、列表项等）
3. **为每个页面和元素确定埋点事件**

### 埋点方案文档格式

产出的方案文档按**页面维度**组织，每个页面列出页面级事件和该页面下的元素级事件：

```markdown
# 埋点方案

## 页面：首页（home）

### 页面事件
- **页面曝光** `dt_pgin` dt_pgid=`home`：进入首页时上报
- **页面离开** `dt_pgout` dt_pgid=`home`：离开首页时上报（高优先级）

### 元素事件
- **帖子卡片点击** `dt_clck` dt_pgid=`home` dt_eid=`post_card`：用户点击帖子卡片时
  - 参数：`post_id` 帖子ID；`post_title` 帖子标题
- **搜索按钮点击** `dt_clck` dt_pgid=`home` dt_eid=`search_btn`：用户点击搜索按钮时
  - 参数：`keyword` 搜索关键词
- **轮播图曝光** `dt_imp` dt_pgid=`home` dt_eid=`banner`：轮播图进入可视区域时
  - 参数：`banner_id` 轮播图ID；`position` 位置索引

## 全局（不绑定特定页面）

### 元素事件
- **导航菜单点击** `dt_clck` dt_eid=`nav_menu`：用户点击侧边栏导航菜单项时（dt_pgid 置空）
  - 参数：`target_page` 目标页面

### 独立业务事件
- **搜索确认** `search_confirm`：用户提交搜索时（dt_pgid 和 dt_eid 均置空）
  - 参数：`keyword` 搜索关键词；`result_count` 结果数量

## 页面：详情页（post_detail）

### 页面事件
- **页面曝光** `dt_pgin` dt_pgid=`post_detail`：进入详情页时上报
- ...

### 元素事件
- ...
```

### 事件设计规则

> 🔀 **自定义规范消费（来自 custom-specs/）**：
> - 若业务自定义规范声明了**事件命名规则**（如 `event_code` 前缀、`dt_pgid`/`dt_eid` 风格约束） → 按自定义规则生成事件名，覆盖下方默认 `snake_case` 约定
> - 若业务自定义规范声明了**必选公参**（如所有事件必须带 `tenant_id`、`user_tier`） → 为每个事件自动补齐这些参数到 `私有参数 udf_kv` 列
> - 若业务自定义规范声明了**自定义事件分类**（在默认 5 类之外新增一类业务类别） → 在分类表和方案中采纳该分类
> - 若业务自定义规范尝试修改**事件三字段主键**（`event_code` + `dt_pgid` + `dt_eid`） → **拒绝采纳**，保留默认硬性约束

1. **⚠️ 事件唯一标识（主键）**:

   `event_code`（事件英文名）+ `dt_pgid`（页面英文名）+ `dt_eid`（元素英文名）三个字段组成数据库主键，用于唯一确定一条事件。

   - **一旦确定，不要轻易修改**，否则会导致数据断裂
   - 如果事件没有关联页面，`dt_pgid` 置空
   - 如果事件没有关联元素，`dt_eid` 置空
   - 同一个 `event_code` 可以在不同页面/元素下复用（因为主键是三字段组合）
   - **⚠️ 每个主键组合必须独立一行，严禁将多个 dt_pgid 或 dt_eid 合并到同一行**（即使事件名称相同）

   | 场景 | event_code | dt_pgid | dt_eid | 说明 |
   |------|-----------|------|-----|------|
   | 页面事件 | `dt_pgin` | `home` | - | 页面级事件，无元素 |
   | 元素事件 | `dt_clck` | `home` | `post_card` | 某页面下的元素事件 |
   | 独立业务事件 | `search_confirm` | - | - | 与页面和元素均无关联 |
   | 全局元素事件 | `dt_clck` | - | `nav_menu` | 全局元素，不绑定特定页面 |

2. **`element_name`（dt_eid）命名规范**: 使用 `snake_case`，描述元素本身而非行为
   - ✅ `like_btn`, `post_card`, `search_modal`
   - ❌ `clickLike`, `PostCard`, `search-modal`

3. **页面命名规范**（dt_pgid）:
   - 页面: `home`, `post_detail`, `profile`, `settings`
   - 弹窗/浮层: `search_modal`, `login_modal`

4. **事件分类**:

| 类别 | event_code | 说明 |
|------|-----------|------|
| 页面曝光 | `dt_pgin` | 进入页面时 |
| 页面离开 | `dt_pgout` | 离开页面时（高优先级上报） |
| 元素曝光 | `dt_imp` | 元素进入可视区域时 |
| 元素点击 | `dt_clck` | 用户点击元素时 |
| 独立业务事件 | 自定义命名 | 与页面/元素无直接关联的业务行为（如 `search_confirm`、`comment_submit`） |

5. **上下文参数**: 根据业务场景携带必要的上下文
   - 内容类: `post_id`, `post_title`, `author_id`
   - 操作类: `action`（如 `like`/`unlike`）, `tab_name`
   - 度量类: `stay_duration`, `like_count`, `result_count`, `comment_length`
   - 索引类: `image_index`, `current_page`

### 方案文档保存规则

> 🔀 **自定义规范消费（来自 custom-specs/）**：
> - 若业务自定义规范声明了**自定义 slug 命名规则或文件名格式** → 采用自定义格式，默认的 `{summary-slug}-YYYYMMDDHH.md` 作为兜底
> - 若业务自定义规范声明了**附加章节**（如"责任人""上线版本""审核人"列或块） → 按自定义格式在文档中加入

### 方案文档保存规则

- **目录**：项目根目录下的 `dt_tracking_plan/`（不存在则创建）
- **文件名格式**：`{summary-slug}-YYYYMMDDHH.md`
  - `{summary-slug}`：模型基于本次埋点需求起的**总结性短标题**，用于一眼看出这份方案是做什么的
    - 使用**小写英文 + 连字符**（kebab-case），例如 `content-feed-tracking`、`ecommerce-checkout-tracking`、`saas-onboarding-tracking`
    - 长度控制在 2-5 个单词，语义要具体（不要用 `tracking-plan`、`events` 这种通用词）
    - 优先体现「场景 + 主题」：若 Step 0b 命中了场景库，直接用场景关键词；未命中则用项目核心业务词
  - `YYYYMMDDHH`：当天日期 + 小时（24h）
  - 示例：
    - `content-feed-tracking-2026042022.md`（内容社区 feed 流埋点）
    - `ecommerce-checkout-tracking-2026042022.md`（电商下单埋点）
    - `signup-funnel-tracking-2026042022.md`（注册漏斗埋点）
- **重名处理**：若文件已存在，在文件名末尾追加 `-序号`（从 1 递增）
  - 示例：`content-feed-tracking-2026042022-1.md`、`content-feed-tracking-2026042022-2.md`

## Step 2b：根据方案编写上报代码

基于 Step 1b 产出的埋点方案，为项目编写上报代码。

### H5 端：universal-report（默认）

加载 `../sdk/h5/universal-report/quickstart.md` 获取 SDK 使用方法。

#### 声明式标签埋点（页面和元素事件）

页面级和元素级事件**默认使用声明式标签埋点**，在 HTML/模板中添加 `dt-` 属性：

- **页面埋点**：在页面根元素添加 `dt-pgid` + `dt-params`
  - SDK 自动上报 `dt_pgin`（页面曝光）和 `dt_pgout`（页面退出）
- **元素埋点**：在元素上添加 `dt-eid` + `dt-params`
  - SDK 自动上报 `dt_imp`（元素曝光）、`dt_clck`（元素点击）、`dt_imp_end`（元素退出）
- **组件埋点**：在组件上添加 `dt-eid` + `dt-params`
  - SDK 自动上报 `dt_imp`（元素曝光）、`dt_clck`（元素点击）、`dt_imp_end`（元素退出）

#### 手动埋点 API（独立业务事件）

当用户明确使用手动上报, 那些与页面和元素**无直接关联的独立业务事件**（如 `open_hongbag`、`watch_author` 等具有实际业务场景自定义事件）时，才使用 `reporter.reportEvent()` 手动上报。
非必要时，不要使用手动上报，走声明式标签埋点。


### Android / iOS 端：beacon（默认）

- Android：加载 `../sdk/android/beacon/quickstart.md`
- iOS：加载 `../sdk/ios/beacon/quickstart.md`

使用 beacon SDK 的手动上报 API 完成所有事件的上报。

### 代码产出

```
src/tracking/
├── reporter.ts / reporter.js   # SDK 初始化封装
├── index.ts / index.js         # 统一导出
```

1. **SDK 初始化封装**：创建 `reporter.ts`（初始化 universal-report / beacon）
2. **统一导出**：创建 `index.ts`
3. **入口初始化**：在 `main.ts` 中添加初始化调用
4. **页面/组件插桩**：为页面和元素添加声明式标签（H5）或手动上报调用（Android/iOS）

## Step 3b：整理埋点方案为表格式文档

将 Step 1b 产出的埋点方案**整理成表格式**，严格按 `tracking-table-format.md` 中定义的格式输出，不能随意改格式。

> 🔀 **自定义规范消费（来自 custom-specs/）**：
> - 若业务自定义规范声明了**自定义表格列结构**（如追加「责任人」「上线版本」列） → 在默认 7 列基础上按自定义规则新增列
> - 默认 7 列（`trigger` / `ui` / `event_code` / `dt_pgid` / `dt_eid` / `udf_kv` / `remark`）的**列名与语义属硬性约束**，不可被删减或更名
