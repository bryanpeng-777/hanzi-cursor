# md制作

## 1. 背景与挑战：打破终端监控的“石器时代”

### 1.1 现状差异：存在的“监控孤岛”

- **平台现状**：伽利略平台（Galileo）建设早期，后台与前端团队已率先接入，并建立了成熟的线上指标监控体系，现网问题排查收益显著。
- **终端缺失**：相比之下，终端侧（iOS/Android）长期缺乏统一有效的监控标准和平台。这种监控能力的缺失不仅导致终端自身问题发现滞后，更阻断了终端与后、前端监控数据的有效联动，形成了数据孤岛。

### 1.2 历史包袱：难以维护的旧体系

- **历史债务**：虽然营地终端早在 2021 年曾接入“天机阁”并投入了大量维护成本，但实际效果不尽人意。
- **痛点显著**：
    - **开发体验差**：实际上报与维护体验仍停留在“石器时代”。
    - **效率低下**：缺乏标准化配置，告警误报、漏报频发，导致问题定位成本极高，严重拖累了研发效率。

### 1.3 建设驱动：全链路闭环的迫切需求

- **核心驱动力**：为了解决上述痛点，推动终端全面接入伽利略平台已成为刚需。
- **核心价值**：本次建设不仅仅是补齐终端监控能力的短板，更是为了建立一套覆盖“**问题发现”到“问题定位”的全流程统一标准，最终实现终端、前端、后台“三端联动”**，全方位提升现网质量保障体系。

## 2. 核心目标

### 2.1 总体愿景

建立一套标准、统一且有效的终端指标监控体系，打破“发现”与“定位”的壁垒，全方位提升现网问题的排查效率，保障用户体验 。

### 2.2 核心能力拆解

我们将终端接入伽利略的实践划分为两大核心流程，分别对应不同的技术手段与优化目标 ：

核心能力拆解图

- **支柱一：问题发现**
    - **核心目标**：及时、准确地感知现网异常，致力于缩短 **平均检测时间 (MTTD)** 。
    - **关键技术**：基于 **漏斗模型** 的标准化监控告警体系 。
    - **解决痛点**：解决告警配置不统一、误报漏报频发的问题。
- **支柱二：问题定位**
    - **核心目标**：高效、精准地锁定问题根因，致力于缩短 **平均解决时间 (MTTR)** 。
    - **关键技术**：基于 **Trace/Log 联动** 的全链路上下文分析能力 。
    - **解决痛点**：解决排查线索碎片化、缺乏上下文、跨端定位难的问题。

分析发现，尽管这些业务的交互形态各异，但其底层逻辑呈现出高度的共性：它们均属于**“有向的、序列化的业务流程”**。 这些流程通常具备三个关键特征：

- **起点明确**：如进入登录页、发起支付请求。
- **路径关键**：如点击隐私协议、确认支付金额等中间操作。
- **终点可判**：如成功进入首页、支付回调成功。

监控系统不仅需要关注最终的“结果”（Success/Fail），更需精确追踪流程是否正常“开启”（Start）以及中间环节（Step）的流转效率 。

### 3.2 建模需求：统一标准的必要性

针对终端监控长期存在的“上报随意、难以量化”痛点，我们需要引入一个高度抽象的通用模型 。该模型必须具备以下能力：

- **标准化**：提供统一的数据结构，将所有“重要功能模块”纳入同一套度量体系。
- **可量化**：将异构的业务行为转化为可比较、可分析的指标数据。
- **通用性**：能够适配从简单操作到复杂交互的所有终端场景。

### 3.3 选型对比与决策

在明确建模需求后，我们对业界主流的监控模型进行了多维度的对比分析 ：

- **Apdex** (应用性能指数)：侧重于“体验”视角，适用于衡量慢请求、卡顿等资源类问题，但难以描述复杂的业务逻辑转化。
- **FSM** (有限状态机)：侧重于“逻辑”视角，适用于解决复杂的交互 Bug 和并发状态管理，但作为通用监控模型，其建设与维护成本过高。
- **SRE/USE**：侧重于“资源”视角（CPU/内存），无法反映业务层面的成功率。
- **路径分析**：侧重于“探索”未知路径，更适合离线数据挖掘而非实时的稳定性监控。
- **漏斗模型** ：侧重于**“结果”**视角，能够直观反映流程的转化率和总体失败率，完美契合我们对“流程化业务”的监控需求。

**最终决策：基于“结果导向”和“标准化落地”的考量，我们最终选择了漏斗模型作为伽利略平台的统一监控语言 。**

## 4. 标准化监控体系构建

### 4.1 核心方法论：业务流程的“漏斗抽象”

#### 4.1.1 痛点分析

在引入漏斗模型之前，终端上报存在极大的随意性。由于缺乏统一规范，开发者往往“想到哪报到哪”，导致监控数据的质量难以把控，漏报和误报现象频发，监控体系难以形成合力。

#### 4.1.2 模型定义与价值

为解决上述痛点，我们引入了漏斗模型作为统一的监控语言。该模型将所有异构的业务模块（无论是线性的登录流程，还是离散的视频播放事件）统一抽象为 **Start (发起) -> Step (关键路径) -> End (结果)** 的三段式结构 。

*图4：漏斗模型示意图*

**核心价值**：

1. 标准化：将复杂的业务流程抽象为通用的“Start-Step-End”结构，为监控提供了一套通用语言。
2. 策略复用：统一的模型允许我们建立可复用且一致的告警策略（如“Start 量级波动”或“转化率跌幅”），新功能接入时可直接复用现有策略，极大提升了建设效率。
3. 统一视角：该模型将“流程性功能”（如登录）和“错误型事件”（如视频播放失败，视为仅有 Start 的错误事件）纳入同一套度量体系。

#### 4.2.3 伽利略平台管道加工

为了提升监控的灵活性并降低客户端发版依赖，我们利用伽利略平台的管道能力对上报数据进行**无侵入式处理** ：

- **二级分类 (Secondary Classification)**： 在伽利略平台通过规则对日志进行分组。例如，针对“网络报错”指标，自动解析日志内容并按 API 接口（如 `user/login`）进行聚合，从而实现接口维度的细粒度告警，而非仅有笼统的网络报错。
- **阶段标记 (Stage Marking)**： 原始上报中可能未包含步骤顺序信息。通过管道配置，我们可以自动识别并标记 `Step1`、`EndBefore`（结束前一步）等标签，无需修改客户端代码即可让通用告警策略识别出转化率计算的分子分母。
- **字段加工**： 支持通过 Python 脚本对字段进行二次计算（如计算链接长度），满足特定维度的分析需求。 

*图7：使用管道对支付流程进行标记*

**为何使用管道？**

1. **降低成本**：减少客户端非必要信息的上报量。
2. **提升灵活性**：业务流程变化时，只需调整服务端管道配置，无需客户端发版 。

### 4.3 告警策略：动态阈值与分级治理

#### 4.3.1 流量分级策略

我们根据模块的日活量级设定了差异化的波动阈值, 这些流量的计算都是基于PV的：

- 大流量 6k~~10w、10w~~100w、>100w：波动 2%左右 即触发告警（对核心业务保持高敏感）。
- 小流量 细分为 80~~300、300~~600、600~6k, 具有两位数的波动容忍度（避免因个位数波动导致的误报）。

#### 4.3.2 类型分级策略

- 常规指标：关注 Start 量级的跌幅（功能不可用）。
- 错误指标：关注 Status < 0 的 Start 量级涨幅（异常激增）。
- 转化率指标：关注流程转化率的波动 。

#### 4.3.3 阈值计算模型与迭代策略

基于前述的流量分级策略，我们需要为不同层级的告警设定精确的告警阈值。这并非简单的经验拍脑袋，而是结合了**数学推导**与**现网迭代调优**的产物**。**

#### 1. 大流量场景：基于理论极值的推导

对于大流量模块，样本分布相对均匀，具备统计学意义。为了平滑波动，我们采用 **1小时滑动窗口**作为对比周期，以 **1分钟** 为检测粒度。

- **理论噪点计算**： 基于“上报数据在单位时间内呈均匀分布”的数学假设，我们可以推导出自然波动的理论上限：
    - **分子波动**：下一分钟的增量预期不超过总量的 1/60，即约为 **1.7%**。
    - **分母波动**：作为对比基准的历史周期数据同样存在1/60, 即**1.7%** 的波动可能。
    - **叠加极值**：综合分子与分母的波动，理论上的最大自然波动范围（即噪点上限）约为 **3.4%**。
- **去噪策略与阈值修正**： 在实际监控中，为了过滤偶发的“告警突刺”，我们引入了”连续命中3次“的去噪策略。 这也决定了我们的阈值选取逻辑：**告警阈值必须低于理论噪点值（3.4%）**。
    - *原因*：如果阈值设定高于 3.4%，要求连续 3 次波动都超过该极值的概率极低，这将导致监控过于迟钝，极易漏报真正的业务问题。
    - *结论*：通过“调低阈值”保证灵敏度，通过“连续次数”保证准确性。

基于此逻辑，结合现网持续调优，我们最终确立了以下梯队阈值：

- **上报量[6000 ~ 10w]**：**3%**
- **上报量[10w ~ 100w]**：**2.5%**
- **上报量[> 100w]**：**2%**

#### 2. 小流量场景：经验主导的动态调优

对于小流量模块，由于数据稀疏且非均匀分布，不具备稳定的统计学规律，无法套用上述数学模型。因此，其阈值选取主要依赖**现网经验值**。我们通常采用“宽进严出”的策略，在初期设定较宽松的阈值（如 30%~60%），随后根据实际误报率进行收敛回调。

#### 4.3.4 智能降噪：基于多指标联动的波动抑制

仅依赖单一指标的波动阈值进行告警，容易受业务自然增长或运营动作的干扰而产生“误报”。在实际场景中，存在两类典型的**良性波动**：

- **版本发布期**：新版本上线或灰度放量阶段，新版本的 Start 量级天然会呈现从 0 到 N 的激增过程。
- **流量高峰期**：周末、节假日或运营活动带来的日活（DAU）自然上涨，会导致所有业务指标的量级同步水涨船高。

解决方案：多指标联动，**多指标联动**的判定策略。我们将业务侧指标（如功能 Start 量、报错 Error 量）与大盘基准指标（如 App 启动次数、实时 DAU）进行关联分析。

- **判定逻辑**：在一个检测周期内，若发现业务指标（如登录 Start）大幅上涨，同时基准指标（如实时 DAU）也呈现同比例的升高，那么将判定该波动由流量增加引起，属于正常现象，从而**自动抑制告警**。
- **阈值调优和风控**：在关联告警中基准指标间的取值区间要结合现网实践进行反复微调。过于严格的抑制策略可能导致真正的现网问题被掩盖（漏报）。因此在策略上线初期需保持审慎, 建议遵循**“由松入紧”**的迭代原则，逐步收敛阈值。

### 4.4 典型告警场景

在实际运行中，我们处理了多种类型的告警场景，积累了丰富的实战经验：

#### 4.4.1 常规异常告警

**当现网指标出现异常波动时，系统会根据告警级别（P0/P1）推送到企业微信。**

- 示例：某小流量模块 Start 量级环比下跌 20%，系统自动推送告警卡片，包含模块名、当前量级、对比阈值及持续时间，并提供“静默”和“认领”快捷操作 。对告警进行分级，以免漏掉一些特别重要的告警。尤其是周末和节假日，这种分类特别有意义。

## 5. 精准定位：Trace/Log 深度联动体系

在通过标准化监控实现“快速发现问题”（缩短 MTTD）之后，下一步的核心诉求是构建一套能够高效、精确“定位问题”的体系，以缩短平均修复时间（MTTR）。伽利略平台通过 Trace（链路） 与 Log（日志） 的深度联动实现了这一目标。

### 5.1 设计理念：View + Task 的上下文重构

**为确保全员认知的统一，我们明确了以下核心概念 ：**

- **Trace**：树形结构的 Span 集合，记录一次完整的用户会话（Session）或启动流程。由框架层自动维护，业务开发者无需过多关注底层实现。
- **Span**：具有明确开始和结束时间的工作单元（如一次网络请求、一个业务动作）。与日志的核心区别在于 Span 具备**时间跨度**属性。
- **Log**：记录瞬时状态的信息点，分为用于排查的“普通日志”和用于监控的“指标日志”。

#### 5.1.2 架构选型：View 与 Task 的结合

在 Trace 体系建设初期，我们在两种技术路线中进行了权衡 ：

- **路线一：基于用户操作**。记录每一次点击、滑动等精准操作。
    - *优点*：信息精确，路径还原度高。
    - *缺点*：数据量巨大，成本高昂；链路冗余信息多，分析效率低。
- **路线二：基于用户状态**。记录用户当前所在的界面（View）状态。
    - *优点*：结构清晰，便于定位；成本可控；支持动态开关。
    - *缺点*：中间操作细节需一定程度推理。

**最终决策**： 为了在“信息完备性”与“工程落地成本”之间取得平衡，我们最终确立了 **“基于用户状态结合关键任务”** 的架构方案。

- **以 View 为骨架**：Trace 树的主干对应用户的页面流转（Session），由框架自动维护。
- **以 Task 为血肉**：将路由跳转、核心指标上报、API 调用等关键业务动作作为 Span 挂载在 Trace 主干上，填充细节。

### 5.2 核心机制：Log 自动挂载与上下文联动

#### 5.2.1 联动原理

为了解决告警（Log）与排查（Trace）割裂的问题，我们利用框架能力实现了 **Trace + Log 的自动绑定** 。 **实现方式**：当业务上报指标日志时，框架层会自动将其作为子节点挂载到当前上下文对应的 Span之下。

举个例子，当日志 InnerRouter-start上报时，它会在框架层自动被挂载到对应的 Span-routeControllerWithUrl下（如下图所示），这样路由跳转相关的详细信息我们就只需要在日志处上报一份（节省成本），对应的Trace就不需要再冗余上报。当告警触发时，排查人员可以直接在伽利略平台上通过日志快速跳转到所属的Trace，看到该日志所处的完整上下文。

*图14：Trace + Log 上报流程图*

- **开始:** Trace的开始和指标上报一起执行
- **中间流程:** 在中间可以经历很复杂的流程，也可以有一些额外的关键日志上报（在上图中就是在路由跳转中经历了路由替换），这些上报最后都会被框架挂载到该Trace下
- **结束:** Trace的结束和指标的结束一起执行

*图15：Trace和Log 伽利略效果*

#### 5.2.2 核心价值

采用这种联动上报方式，带来了三重收益 ：

1. **缩短 MTTR**：打通了告警与 Trace，收到告警后可直接点击日志跳转至对应的 Trace 上下文，复原用户操作全景。
2. **节省成本**：异常详情只需在日志中上报一份，Trace 中无需冗余记录，平台侧自动关联。
3. **提升效率**：一次编码同时完成“监控告警”和“链路追踪”两项建设，无需重复开发。

#### 5.2.3 关键任务覆盖

【**第一部分**】：所有的在4.2.2节中提到的**【基础指标】**和**【核心指标】**都是我们的的关键任务，换句话讲，他们既承担了我们告警监控的任务，也会助力我们排查定位问题。

**【第二部分】**：除基础指标外，我们将以下关键信息纳入 Trace 的自动挂载范围，作为排查问题的核心线索 ：

- **组件异常**：视频、图片、PAG 动画组件的报错信息。
- **配置与通信**：Shiply 开关配置、OneEvent/OneApi（多端通信组件）报错信息。
- **业务流程**：分享报错、文件上传异常。
- **环境状态**：网络切换事件、App 生命周期切换事件。

【**第三部分**】：这部分内容将由我们的各业务负责同学进行建设。一方面他们需要按照漏斗模型来建设指标，用于告警；一方面他们也会有自己的Trace上报用来定位排查问题。

### 5.3 成本治理：前置/后置 (Before/After) 采集策略

随着建设的全面铺开，**“数据完备性”与“高昂成本”之间的矛盾日益凸显。为此，我们设计了核心的分级采集策略**对成本进行严格管控

## 6. 全链路协同：打破端侧孤岛实现端到端追踪

### 6.1 协作痛点：跨端排查的“协作墙”

在日常的现网问题排查中，经常遇到需要卷入多端（终端、后端、前端）同学共同参与的复杂场景。传统模式下，这种“多方会诊”往往要求相关人员在同一时间段内强制中断手头工作进行同步联调，导致协作成本高昂且严重影响开发体验 。

我们的目标是优化“问题定位”阶段的协作模式：在问题归属不明确时，应尽可能减少参与排查的人员数量。理想状态下，由单人完成初步定位后，再将问题流转给对应的责任人，使其能够根据个人时间表进行异步处理，从而最小化沟通联调成本 。

### 6.2 基于 Context 透传的链路打通

为了实现这一目标，我们基于伽利略平台提供的能力构建了**多端串联**能力。其核心机制是通过 Trace/Span 实现端到端的上下文透传，该逻辑由框架层统一维护，业务开发者无需关注底层实现 。

#### 6.2.1 终端与后台的串联

- 实现机制：终端在发起网络请求时，自动将 Trace ID（或 Span ID）注入到 HTTP 请求头（Header）中 。
- 平台能力：
    - 跳转后台：终端开发者可通过 Trace 或 Span 直接跳转至对应的后台伽利略视图 。
    - 协议详情：查看具体的后端协议交互信息 。
    - 双向溯源：后台开发者也可通过入口跳转回关联的终端 Session，实现双向排查

*图20：终端Session和后台互跳*

#### 6.2.2 终端与前端的串联

- **实现机制**：将终端的 `Trace ID` 传递给 H5 或 Hippy 环境。
    - **Android**：通过注入 Cookie 进行传递。
    - **iOS**：考虑到 Cookie 方案在 iOS 上的性能问题，改为拼接在 URL 后缀进行传递 。
- **平台能力**：支持从终端 Session（如 `aegis_session_id`）直接跳转至 H5 页面视图，打通 Native 与 Web 的上下文壁垒 。

*图21：终端Session和前端互跳*

目前，伽利略平台已具备串联终端、后端、前端（H5 和 Hippy）的全链路追踪能力 。

### 6.3 效能变革：从“多方会诊”到“全景视图”

多端串联的落地显著改善了开发体验。它赋予了任意一端（终端/前端/后端）开发者查看全链路信息的能力，在很多场景下实现了“非本端同学”也能独立完成问题定位 。

## 7. 实战成效：监控体系的价值验证

经过 3 个多月的现网建设与调优，目前营地的这套告警与定位体系已稳定运行。截至发稿前，该体系辅助发现并解决了约 300 个有效问题 。以下选取四个典型案例，展示该体系在不同场景下的实战价值。

### 7.1 复杂场景溯源：从“大海捞针”到“按图索骥”

#### 案例一：后台耗电无法挂起的根因定位

- **痛点**：用户反馈 App 退后台后不挂起，导致持续耗电。由于该问题涉及场景广泛且极难复现，传统的排查手段（逐一排查代码点、分析离散日志）收效甚微，排查一度陷入僵局 。
- **解决路径**：
    1. **Session 对比**：通过伽利略平台对比多个异常用户的 Trace Session，发现一个清晰的共性规律：“所有出现问题的用户，在退出前均停留在‘个人主页’（`UserProfile_main_page_sub`）” 。
    2. **关键任务分析**：结合 Trace 中的关键任务节点，发现用户触发了 `AppDidEnterBackground`（退后台）后，最终触发了 `BackGroundKill` 保护机制（注：营地设有保护策略，若 App 后台运行超过 10 分钟未挂起，会主动触发自杀） 。
    3. **根因锁定**：结合“个人主页”与“后台保活”两个线索，迅速定位到是主页封面视频的循环播放逻辑触发了系统级 Bug，导致锁未释放。

*图26：用户退后台App无法正常挂起*

- **成效**：成功将排查范围从 App 全局缩减至单个页面，快速修复了该顽疾 。

#### 案例二：无业务堆栈 Crash/ANR 的精准定位

- **痛点**：在 Bugly 上报中，常遇到仅含 Flutter SDK 或系统层通用堆栈的 Crash/ANR，缺乏业务层堆栈。此类问题通常被视为“盲盒”，补充日志不仅滞后且难度大，导致修复效率极低 。
- **解决路径**：
    1. **用户关联**：提取发生此类 Crash 的用户 ID。
    2. **场景还原**：在伽利略中查看这些用户的 Trace Session，发现所有崩溃用户的最后操作路径均指向“Flutter (web) 商城页面” 。                                                            

*图27：某个crash上报*

- **成效**：将问题范围从无头绪的“底层库异常”瞬间收敛至具体的“Flutter 商城”页面，极大加速了定位效率 。

### 7.2 极致体验保障：透视“长尾”与“个例”

针对**大盘监控容易忽略的极端个案**，我们建立了精细化的单用户监控维度。

#### 案例三: 单用户高频崩溃的捕捉

- **痛点**：传统大盘监控关注整体崩溃率。某些极端情况（如某用户 1 分钟内崩溃 13 次）虽然对个体体验是毁灭性的，但因样本量小，在大盘数据中容易被平均化而被忽视 。
- **解决路径**：
    1. **策略建设**：建立“单用户维度”监控告警，例如【核心业务 - 1 分钟内同一用户 Crash 数超过 2 次】 。
    2. **排查闭环**：
        - **Step 1**：通过 Bugly 查询堆栈。
        - **Step 2**：通过 Trace 查看用户崩溃前的完整场景。
        - **Step 3**（备用）：通过 Span 中自动携带的日志地址，直接捞取该用户的详细崩溃日志

*图28：某个用户出现严重crash*

- **成效**：精准捕获并修复了此类严重影响特定用户体验的长尾问题。通常仅需前两步即可解决绝大多数问题 。

### 7.3 隐性债务治理：性能与资源的深度优化

针对**不影响功能但消耗资源**的“隐性问题”，我们通过细粒度指标进行了专项治理。

#### 案例四：网络请求超频治理

- **痛点**：业务开发中常存在非必要的重复请求（如主动轮询或逻辑缺陷导致的多次调用）。此类问题虽不影响功能使用，但会消耗用户流量并增加服务器负载，且在常规测试中难以被发现 。
- **解决路径**：
    1. **策略建设**：建立接口超频告警，例如【单接口 150ms 内调用超过 2 次】或【单接口 1h 累计超频上报超过 100 次】 。
    2. **问题发现**：系统捕获了大量超频请求。例如，接口 `a/getanniversaryconf` 在同一个 Trace 界面下被连续调用了 3 次 。

*图29：告警超频Trace*

- **成效**：根据告警线索，推动业务团队清理了大量历史遗留的超频技术债，优化了 App 性能与带宽成本 。

### 8. 总结与展望：构建可持续的质量护城河

### 8.1 体系回顾：数据驱动的闭环

本实践建立了一套高度依赖于终端标准化数据的监控闭环体系。其核心流转机制如下 ：

- **标准化采集**：无论是用于“问题发现”的漏斗指标（Start/Step/End），还是用于“问题定位”的 Log/Trace 信息，均通过统一标准进行上报。
- **平台化处理**：伽利略平台侧对上报数据进行实时的 **Log-to-Metric（日志转指标）** 处理和管道归类（如基于 `groupName` 的分组），将非结构化日志转化为可度量的指标数据。
- **闭环响应**：最终数据汇入统一的监控与告警系统，形成了从“数据采集”到“问题响应”的完整自动化闭环。

尽管我们已取得阶段性成果，但这套体系的演进仍在路上。我们将从技术、运营、文化三个维度持续深化建设。

### 8.2 技术演进：深度与成本的再平衡

- **Trace 结构优化**： 进一步优化排查视图中的 Trace 树结构，使其更贴合终端的实际业务逻辑，降低开发者的认知负荷，提升定位速度 。
- **智能成本控制**： 探索更优的日志分级上报策略。例如，利用 **Shiply** 动态配置特定日志的采样率，在严控存储与传输成本的同时，确保关键问题排查细节的完整性 。

### 8.3 运营精细化：提升告警信噪比

- **告警质量治理**： 持续打磨告警的稳定性与有效性，建立更精细化的告警分级策略（如 P0/P1/P2），确保高优先级问题能被最高效地触达 。
- **存量问题出清**： 以监控倒逼质量，积极推动已发现的 300 多个存量告警问题的根本性修复，消除由存量 Bug 导致的“噪音”，让监控大盘回归纯净 。

### 8.4 文化赋能：从“工具”到“习惯”

- **研发流程融合**： 将监控体系的建设融入常态化的**技术方案评审**中，要求新功能上线必须配套相应的监控方案 。
- **深化团队共建**： 推动所有业务开发同学共同参与建设，实现从“专人维护”向“全员共建”的模式转型，持续提升监控覆盖的广度与深度 。
