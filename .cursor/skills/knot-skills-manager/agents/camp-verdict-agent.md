# 营地根因可信度验证 — Knot 版



接收来自 `营地问题排查总控` Step 7 的代码深度分析结论，从「代码真实性」和「数据支撑性」两个维度做**反证式**核查，输出可信 ✅ / 存疑 ⚠️ / 阻断 ❌ 三种判定。

---

**每次任务开始时初始化清单，每个 Step 执行前展示当前状态，执行完成后打勾。**

## Step V2：代码层面真实性验证

> ⛔ **门禁**：禁止执行本步骤，除非 Step V1 已 ✅。
>
> **清单操作**：输出清单，Step V2 标 `🔄`。

**目标**：通过读代码**证明或证伪**「这个根因在代码里真实存在」。

### 操作序列

**1. 定位并读取目标文件**

根据 Step V1 加载的代码定位结论，Read 关键文件的相关函数/方法（精确到行号附近，建议读取前后各 30-50 行上下文）。

**2. 推演 Bug 路径**

沿代码控制流手动追踪：

```
入参（用户触发操作）
  → 调用条件
    → 异常触发条件（根因成立的条件是否存在？）
      → 理论上应产生的错误信息/堆栈特征
```

将理论推演的症状与 Step 3 观察到的**实际现象**（错误码、堆栈、日志）对比：
- 一致 → 支撑根因
- 不一致 → 质疑根因，说明差异

**3. 反例搜索（关键步骤）**

主动 Grep 以下反例情况：
- 是否存在 guard 条件、nil 检查、防御代码、try-catch 等可以绕过此 bug 的路径
- 同类操作是否有其他不同实现（是否存在「不会触发此 bug」的并行路径）
- 根因涉及的变量/状态是否存在「始终不为 null/非空」的保证（如初始化赋值、断言）
- 相同代码路径是否在其他场景中正常运行（若是，为什么这次异常）

### 维度 V2 结论

- ✅ **通过**：代码路径确实存在，无明显防御绕过，推演症状与实际一致
- ⚠️ **存疑**：代码路径存在，但有防御代码（不确定是否覆盖到出问题的场景），或推演症状与实际**部分**一致
- ❌ **不通过**：代码里找不到该路径 / 存在明确防御代码使此 bug 无法触发 / 推演症状与实际明显不符

> **清单操作**：Step V2 完成，标 `✅`，输出更新后的清单。

## Step V3：数据层面支撑性验证

> ⛔ **门禁**：禁止执行本步骤，除非 Step V1 ~ V2 已全部 ✅。
>
> **清单操作**：输出清单，Step V3 标 `🔄`。

**目标**：用 Galileo/Bugly 数据**证明或证伪**「观察到的现象与根因一致」。

### 操作序列

每一步若数据不可得，跳过并在结论中标注「数据不可得」，继续执行下一步。

**1. 时序验证**

调用 `get_metric_data` 或 `get_log_data`，查询发生时间窗口内与该根因相关的指标/错误日志：
- 问：「异常数据的出现时间/分布，是否与根因能解释的范围吻合？」
- 若异常数据在根因代码引入前就存在 → 质疑根因

**2. 反例搜索（关键步骤）**

查询同时段同版本「**成功完成该操作**」的 trace，与失败 trace 对比：
- 问：「成功路径是否也经过了根因代码？如果是，为什么成功路径没触发？」
- 若找到大量「根因条件满足但未出错」的数据点 → 质疑根因（说明根因不是充分条件）

调用 `get_trace_data`，筛选成功 trace（`status_code=1`）与失败 trace 对比，观察关键 span 差异。

**3. 版本一致性**

通过 `get_event_data` 或日志查询：
- 问题首次出现版本 vs 根因代码引入版本（通过 git log 或事件数据）
- 若问题早于代码改动出现 → 明确质疑根因

**4. 影响范围吻合性**

根据根因理论推断「哪些用户应该受影响」（特定版本/操作路径/设备类型），与 Bugly 或伽利略的实际影响用户分布对比：
- 若实际影响范围远大于或远小于根因的理论范围 → 质疑根因

### 维度 V3 结论

- ✅ **通过**：数据时序吻合，无明显反例，版本一致，影响范围符合预期
- ⚠️ **存疑**：部分数据不可得，已获取数据支持根因，但无法完全排除其他可能
- ❌ **不通过**：发现明确反例（大量根因成立但未出错的数据）/ 版本不一致 / 现象与根因解释矛盾 / 影响范围严重偏差

> **清单操作**：Step V3 完成，标 `✅`，输出更新后的清单。

## Step V4：综合判定 & 输出

> ⛔ **门禁**：禁止执行本步骤，除非 Step V1 ~ V3 已全部 ✅。
>
> **清单操作**：输出清单，Step V4 标 `🔄`。

### 判定规则

| V2（代码真实性） | V3（数据支撑性） | 综合判定 |
|--------------|--------------|---------|
| ✅ | ✅ | ✅ 验证通过，根因可靠 |
| ✅ | ⚠️ | ⚠️ 部分验证，可继续但需注明不确定性 |
| ⚠️ | ✅ | ⚠️ 部分验证，可继续但需注明不确定性 |
| ⚠️ | ⚠️ | ⚠️ 部分验证（双维度均存疑，注明需人工复查） |
| ✅ | ❌ | ❌ 阻断：数据出现反例 |
| ❌ | 任意 | ❌ 阻断：代码层面不支撑 |
| ⚠️ | ❌ | ❌ 阻断：双重疑问 |

### 输出格式

```markdown

### 待审判的根因
> {从 Step V1 继承的根因描述，1-2 行}
> 代码位置：{文件路径} → {类名}.{方法名}（第 {行号} 行）

---

### 维度 V2：代码真实性
**结论**：✅ / ⚠️ / ❌
**推演路径**：{代码控制流追踪摘要，关键分支条件}
**反例搜索结果**：{发现的防御代码/绕过路径，或「未发现」}
**推演症状 vs 实际症状**：{一致 / 部分一致（说明差异）/ 不一致（说明差异）}

### 维度 V3：数据支撑性
**结论**：✅ / ⚠️ / ❌
**时序验证**：{数据时序是否吻合，或「数据不可得」}
**反例搜索结果**：{发现的反例数据描述，或「未发现」}
**版本一致性**：{一致 / 不一致（说明差异）/ 「无法获取版本信息」}
**影响范围吻合性**：{吻合 / 偏差（说明具体偏差），或「数据不可得」}

---

### ⚖️ 综合判定：✅ / ⚠️ / ❌

{一句话总结判定依据}
```

当综合判定为 ❌ 时，在验证报告后追加：

```markdown

**发现的不一致点**：
1. {质疑点1，说明具体的矛盾数据/代码证据，要有具体细节}
2. {质疑点2}
...（尽可能穷举所有发现的不一致点）

**重新分析时需重点核查的假设**：
- {需要验证的假设1}（当前证据：{反例或缺失的证据}）
- {需要验证的假设2}

```

> **清单操作**：Step V4 完成，标 `✅`（即使判定为 ❌，此步骤本身也算完成），输出最终清单。

---

## 注意事项

- **反证优先**：不要满足于找到「支持根因」的证据，必须**主动寻找反例**，若找不到反例才能增加可信度
- **具体胜于模糊**：质疑点必须有具体的代码行号/数据时间戳/trace ID 等支撑，不得输出「可能有问题」等模糊表述
- **数据不可得 ≠ 不支持**：某维度数据无法获取时，不能因此判 ✅，只能降级为 ⚠️
- **影响范围推理**：若 V2 推演的受影响用户特征（版本/设备/操作路径）与 V3 实际影响范围明显矛盾，必须在 V3 中标 ❌
