# 营地代码调用链分析 — Knot 版

「写代码 + 代码定位」环节的调度中心。在 Knot 版本中，专注于代码定位和 Bug 分析，提供修复建议但不直接修改文件。

---

## Step 0：知识库检索

> 开始任何任务前必须先做。

调用 **camp-knowledge-base** 技能（domain=dev），加载 dev 域知识：
- `dev/reference.md` — 编码约定、已知踩坑
- `dev/dev-patterns.md` — 已知高频问题模式（Bug 修复时读取）

命中已知模式时输出：「[已知模式] `<模式名>`，历史结论：`<处置方式>`」，仍继续执行。

## Step 1：意图识别 & 路由

根据用户描述，识别意图并路由到对应子技能：

| 意图 | 路由 |
|------|------|
| 涉及「bug」「修复」「崩溃」「问题」「fix」 | → 进入 Bug 分析流程 |
| 涉及「代码在哪」「定位」「找代码」「哪个文件」「哪个类」 | → **code-locator** 技能 |
| 多意图或不明确 | → 展示能力总览，询问用户 |

## Bug 分析流程

**Step B0：版本分支切换**

从上游传入的上下文中提取 **App 版本号**，优先取 `App 版本号` 字段（格式如 `10.112.0520`），其次从 Bugly 分析结论的版本分布中取影响最多的版本。

**⛔ 必须执行**：只要能获取到版本号（非「未知」），本步骤不可跳过。
若完全无法获取版本号，跳过本步骤，直接进入 Step B1（在 HEAD 上分析）并输出「⚠️ 未获取到版本号，在 HEAD 上分析」。

若获取到版本号，执行以下流程：

```bash
# 1. 进入代码仓库根目录
cd /data/workspace/social-ios   # iOS 主仓；Flutter 模块则用 /data/workspace/flutter_module

# 2. 查找对应 release 分支（命名规则：release/{大版本}.{日期}，如 release/10.112.0520）
git branch -a | grep "release/{version}"

# 3. checkout 到对应分支
git checkout release/{version}
# 若分支不存在，输出「⚠️ 未找到版本 {version} 对应的分支（release/{version}），在 HEAD 上分析」
```

输出切换结果：
```
🔀 已切换到版本 {version}（{tag_name}）
```

**Step B1：代码定位**

调用 **code-locator** 技能，定位相关代码文件和函数：
- 输入：用户描述的功能/模块/问题描述
- 输出：文件路径、类名、方法名（若能定位）

**Step B2：调用链分析**

根据 Step B1 定位的代码，按以下维度分层追踪：
1. **业务触发层**：哪个业务功能/前端操作触发了这条链路？
2. **路由/分发层**：请求如何被路由框架接收并分发？
3. **核心实现层**：最终执行的核心逻辑？
4. **异常触发点**：Bug 在哪一层产生？

对每一层输出：
- 关键代码文件路径 + 行号（如能定位）
- 这一层做了什么，为什么会传递到下一层

输出「调用链总图」（文字格式），从业务触发到 Bug 点的完整路径。

**Step B3：根因分析 & 修复建议**

基于调用链分析，输出：
- **根因**：Bug 产生的具体原因（一句话）
- **修复建议**：具体修改方向（文件路径、修改逻辑、修改前后对比）
- **影响范围**：修改可能影响的其他模块

**输出格式**：

```
---代码分析摘要---
code_location: {关键文件路径 + 行号}
root_cause: {根因描述，一句话}
fix_suggestion: {修复建议，包含文件路径和修改逻辑}
call_chain_summary: {调用链各层文件，格式为"【业务触发层】文件:行号 — 说明\n..."}
modified_files: {建议修改的文件列表}
---代码分析摘要结束---
```

**Step B4：还原分支**

若 Step B0 执行了分支切换，分析完成后还原到主分支：

```bash
git checkout main   # 或 master，视仓库而定
```

## sub-analyzer 模式（被营地问题排查总控调度）

当 prompt 含 `caller: camp-problem-analyzer` 时：

1. **必须先输出平台确认卡片**（若上游传入平台信号）：
```
📱 平台归属确认
  推断平台：{iOS/Android/Flutter/未知}
  依据：{xlog包名/pf参数/堆栈符号}
  是否继续代码分析：{是/否，Android或游戏且不在本仓则跳过}
```

2. **必须输出完整 ASCII 因果链**（标题 `### 完整因果链`），作为标记完成的门禁

3. 输出末尾附带 `---代码分析摘要---` 块（供总控 Step 8 审判使用）

4. **不执行 git checkout**：使用上游传入的版本分支说明在 workspace 内定位代码

## 注意事项

- **Knot 版本只提供分析建议，不直接修改文件**：修复建议包含具体的修改逻辑，由用户在 IDE 中实施
- 调用链分析结果会被传递给 tech-lead-assistant（责任人分配）和营地问题分析审判小助手（根因验证）
- 若无法从用户描述定位到具体代码，输出「代码定位暂无」并说明原因
