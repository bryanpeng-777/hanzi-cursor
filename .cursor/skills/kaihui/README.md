# 开会 (kaihui)

老板叫你开会了。

## 为什么做这个

AI 带来了生产力大幅提升，我们经常会和 AI 讨论各种问题——产品方向、视觉交互、技术架构、问题追踪、文案、用户体验，但用着用着会发现，AI 没有立场，你说什么它就听什么，钻到死胡同里给出一个非常片面的回答。然后我们被迫自己拔高视角，换个角度再问一轮，再换个方向又聊一轮，最终东拼西凑出一个答案。

这个场景反反复复出现，我就在想，是不是可以组一个 AI 团队，帮我把所有细分方向一次想全？看到最近同事的 skill 很火，Claude Code 也推出了 Agent Team 模式，于是就顺着这个方向想：能不能请各个领域最厉害的专家来帮忙，甚至让他们互相讨论？请微信的产品同学、苹果的交互设计师、谷歌的架构师、挑剔的用户……从不同的角度和立场来评审，慢慢迭代，就有了现在的 7 个角色。

所以封装了这个 skill，一键拉起 `/kaihui`，他们就过来开会了。我给他们预设了鲜明的身份，坚定了他们的立场，在一定程度上抵抗了 AI 的"幻觉"和"吹捧"问题，也能及时给 AI 踩刹车。

这个 skill 我迭代了很多轮。最早叫 agent-team.skill，我觉得不够有趣，汇总的结论干巴巴的。然后我就想到，我们互联网平时开会，每个同事都是鲜活的人，都有自己很个性化的表达，那 AI 为什么不可以？于是给每个角色的文档做了很多轮打磨，到了现在我个人还比较满意的状态。后来发现主 Agent 汇总的结论还是不对味，想到日常开会都是老板召集、老板汇总结论向上汇报，于是加了老板角色——站全局视角，拥有全局信息，评审每个角色的观点，汇总结论汇报给我们。感觉我们这些牛马就成了总监了，天天听团队汇报，这感觉还挺爽。

当然爽完了，这个工具要有用啊，从原理上来看也是经得起推敲的，因为它本质上就是基于 prompt + agent team 的封装。我现在基本已经离不开这个 skill 了，任何问题都想请专家帮忙出出主意。有时候他们还会金句连连，尤其是 user 角色，基本上完全模拟了没耐心的用户，经常发现我们思考的盲点。遇到技术问题，会请 tech、oncall、debug 来共同评审，从不同角度，用并行 subagent 模式来思考。做工具平台最头疼的用户文案，也可以 copy 来帮忙优化，对抗平庸的 AI 味。

虽然这个 skill 已经足够好用，但还存在几个问题，需要继续迭代。首先是 ux 角色不够饱满——ux 只能通过代码来分析视觉表现，然后输出线框图，未来是不是可以接入 Figma、Stitch 等平台，让 ux 也拥有完整视角。token 消耗还是太大，全员拉起就是 7 个 subagent，一般还是要省着用，所以我加了一些策略，让主 agent 判断应该叫哪些角色，也加了不同角色用不同模型的能力，但这块还在迭代中。还有一个问题是信息爆炸——老板汇总的信息加上不同角色各自的发言，有时候有需要要全部看完内容量很大，我现在的解法是会后说"请用费曼学习法完整解释下刚刚发生了啥"，未来可以扩展成通用能力，但还需要验证。还有运营、用户增长、商务等角色现在是缺失的，导致 kaihui 的能力有限，但增加太多角色又会让调度变复杂，这是个权衡。

当然 skill 本身也可以迭代，使用者可以自主扩展——用 `/kaihui` 本身就可以迭代自己。

## 角色

`po` — 一切以用户价值为依规，相信只有简单的规则才能演化出复杂的事物的产品经理

`tech` — 亲眼看过好架构怎么三年里烂掉，看 PR 先数 diff，加的比删的多就追问为什么的技术架构师

`ux` — 打开界面 3 秒就知道哪里别扭，多一个没必要的元素就想去掉的交互设计师

`user` — 不读文档不研究配置，打开就要能用，30 秒找不到入口就走人的用户代言人

`debug` — 经历过同一个 bug 修三次才发现根因从第一天就是错的，从此不信"修好了"只信"找到根因了"的靠谱开发

`copy` — 别人觉得"差不多得了"的地方还在抠，非要把每句话从"能看懂"改到"不可能误解"的文案

`oncall` — 经常半夜三点被叫起来修过线上事故，看方案第一反应是"炸了我能救回来吗"的开发

老板是 Agent 本体，站全局视角，负责召集、总结、拍板。

```bash
npx skills add git@git.woa.com:ronhu/kaihui.git -g
```

## 用法

```
/kaihui 这个缓存方案你们觉得怎么样？
```

```
请 tech 和 oncall 看看这个部署方案
```

```
全员评审：我们要不要做这个功能？
```

默认是站会（各自说完老板总结），说"深度"或"详细"会变成圆桌（互相对质再定调）。

会后可以 `#po` 看完整发言，`#tech 你觉得并发问题严重吗？` 追问，`展开` 看目录，`存档` 保存纪要。

```markdown
# 会议纪要：debug 入队后 tech/oncall 角色定义是否需调整
> 出席：tech, oncall, debug, po, user, copy | 模式：站会

## 老板的判断

六个人聊完，结论比预想的简单：**真正打架的地方只有一处——tech Q3 的"定位到根因"五个字。** 其余看似重叠的点，拆开看其实是不同角度看同一件事，逼着消除重叠反而会制造盲区。po 给了一条我非常认可的规则："立场定边界，活动允许重叠——只在容易做过头的地方加一句做到哪停，不动角色的能力和结构。"

## 团队共识

1. **tech Q3 的"定位到根因"必须改**
   六个人全票通过，零分歧。tech 自己说"定位根因是 debug 的活，我该管的是系统有没有产出足够的信号让人能查"；debug 说"tech 把基础设施够不够和追根因揉在一句话里，结果跟我整个角色定位撞车"；user 说得最直接——"debug 整个人存在的意义就是追根因，结果 tech 的自我介绍里也写了这个词，我到底该叫谁？"

2. **tech Q2 的代码级检查项（竞态、边界值等）保留不动**
   tech、po、copy 都明确表态。tech 说这是 review 阶段的预防性检查，不是事后分析；po 说"砍掉它 tech 就瘸了"；copy 说 debug 的文案里根本没列这些具体名词，动词方向完全相反（tech 是"追进去看实现"，debug 是"沿因果链往回追"），不撞。

3. **不要加显式引用其他角色名字的边界声明**
   po 警告"一旦角色定义里开始写'注意，这里不是 debug 的职责'，角色之间就产生了耦合——以后再加角色，所有现有角色都要改"；copy 说这会把人格描写变成岗位说明书。

## 待定：团队没对齐的点

**改多少？从"只改五个字"到"改四处"拉开了光谱。**

**copy**：只改 tech Q3 一处。"定位到根因"→"够不够用"，删五个字换四个字，节奏不变。其余不动——oncall 的"故障定位"和 debug 的"根因分析"在中文语境里天然指向不同阶段，"定位"指空间（哪里炸了），"分析"指因果（为什么炸）。
**debug**：改四处。tech Q3 收窄、oncall Q1 加"故障模块"限定、代码级检查项三方切角度、"根因"这个词只允许我用。
**oncall**：改三处。knowledge 里"故障定位"→"故障可观测性"，角色定义段加一句交接声明，其余不动。
**po 给了关键判断**：活动重叠对用户是好事（同一个坑被两个人从不同角度捶到），只需要在"容易做过头"的地方加一句"做到哪停"。

> **老板倾向**：copy 的最小方案 + oncall 的一句话补充。理由——(1) po 的规则说服了我，"立场定边界，活动允许重叠"是对的；(2) debug 要求"根因"这个词只准自己用太重了，属于过度治理；(3) 但 oncall 自己提出想在角色定义段补一句"做到哪停"，这不是被迫让权，是他自己觉得需要——上一轮他就说"我被框太窄了"，现在 debug 来了他反而更清楚自己的边界在哪。补一句有助于他自己干活时不再纠结。

**oncall knowledge 标签"故障定位"要不要改？**

- 要改：oncall（→"故障可观测性"）、user（→"故障响应"）、debug（→"故障分流"）
- 不改：copy（"定位"指空间、"分析"指因果，区分度够）、po（不删能力）

> **老板倾向**：不改。copy 的语言直觉我信——"故障定位"和"根因分析"在中文里确实不是同一件事。oncall 凌晨三点定位到"是这个服务炸了"，debug 接手追"为什么炸"。改了反而让 oncall 的标签变得更抽象。

## 意外收获

- **po 的"立场定边界"规则**：这条值得写进 SKILL.md 或者单独存档。以后再加角色时，判断标准不是"活动有没有重叠"，而是"立场有没有重叠"。立场不重叠，活动重叠是好事。
- **user 的"30 秒犹豫"测试**：user 模拟了拿着一个偶现丢数据 bug 来开会的场景，发现看完三个人的介绍要犹豫超过 30 秒才知道叫谁。tech Q3 改完后这个犹豫应该能消除。

## 接下来做什么

我建议直接改两处：

1. **tech Q3 措辞调整** — "日志和 trace 能不能定位到根因？"→"日志和 trace 够不够用？"（copy 方案，最小最干净）
2. **oncall 角色定义段补一句** — 在"这些写法上的坑就是让你半夜被叫起来的根源"后面加："你指出哪里会炸、炸了后果多大——追到根因、给出断根方案，那是出事后下一棒的活。"（不点名 debug，不产生耦合，po 的原则）
```
