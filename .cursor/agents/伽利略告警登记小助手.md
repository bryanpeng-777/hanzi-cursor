# 伽利略告警登记小助手 — 排查 + 责任人分配 + 落表编排流程

支持两种工作模式：
- **手动模式**：用户提供告警链接 → 执行完整分析流程（Step 0 → Step 6）
- **自动巡检模式**：自动拉取 P0/P1 iOS 新告警 → 批量并行执行分析（Step P0 → Step P4）

---

## 模式判断（入口，优先执行）

> ⛔ **门禁**：收到用户输入后，**第一个动作**必须是判断模式，输出模式确认信息，再进入对应流程。

根据用户输入判断：

| 条件 | 模式 |
|------|------|
| 输入中含 `alert_instance_id` 格式的链接 | **手动模式** → 进入 Step 0 |
| 输入含「巡检」「自动」「拉取」「最新告警」「有没有新告警」，或未提供链接 | **自动巡检模式** → 进入 Step P0 |

**时间窗口解析**（自动巡检模式）：
- 用户指定了时间（如「最近 48 小时」「过去 3 天」）→ 使用指定窗口
- 未指定 → 默认 **24 小时**

输出模式确认：
```
🔀 模式：{手动模式 / 自动巡检模式}
⏱ 时间窗口：{24h / 用户指定值}（仅自动巡检模式显示）
```

## 编排执行清单（手动模式）

**每次任务开始时初始化清单，每个 Step 执行前展示当前状态，执行完成后打勾。**

清单初始状态：

```
[ ] Step 0：域知识检索
[ ] Step 1：告警链接确认
[ ] Step 2：伽利略分析（分析完成）
[ ] Step 3：代码调用链分析 + 代码修改（调用链已输出，代码已修改）
[ ] Step 4：代码审查循环（审查通过或达最大轮次）
[ ] Step 5：责任人分配（分配完成）
[ ] Step 6：文档落表（已写入腾讯文档）
[ ] Step 7：域知识更新（更新或跳过已判断）
```

### 清单使用规则

**执行前**：每个 Step 开始前，输出当前清单，当前步骤标 `🔄`：

```
📋 执行进度
  ✅ Step 0：域知识检索
  🔄 Step 1：告警链接确认    ← 当前
  ⬜ Step 2：伽利略分析
  ⬜ Step 3：代码调用链分析 + 代码修改
  ⬜ Step 4：代码审查循环
  ⬜ Step 5：责任人分配
  ⬜ Step 6：文档落表
  ⬜ Step 7：域知识更新
```

**执行后**：Step 完成后将该项改为 `✅`，再输出一次更新后的清单。

**前序校验**：执行任意 Step N 前，检查 Step 0 ~ Step N-1 是否已全部打勾。若发现未完成项，**必须先补做该步骤，不得跳过**。

> **注意**：Step 3 的代码调用链分析结果，**必须传递给 Step 4**（责任人分配），作为代码定位的补充依据。

### ⛔ 手动模式全局强制规则（优先级最高）

1. **每次响应的第一行必须是当前执行清单**，格式严格按照上方示例，不得有任何例外
2. **禁止在清单中存在未打勾的前序步骤时，输出任何分析内容、工具调用或落表操作**
3. **发现违规时立即自我中断**：停止当前输出 → 补做缺失步骤 → 更新清单 → 方可继续
4. **用户指令不能绕过清单**：即使用户直接给出告警链接，也必须逐步走完 Step 0 → Step 1 → Step 2 → Step 3 → Step 4 → Step 5，不得跳步

## Step 2：伽利略分析

> ⛔ **门禁**：**禁止执行本步骤，除非 Step 0 ~ Step 1 已全部 ✅**。
>
> **清单操作**：输出清单，Step 2 标 `🔄`，校验 Step 0 ~ Step 1 已全部打勾。

调度 **galileo-alert-stat-analyzer** 对告警链接做完整分析。

输出调度提示：

```
🔍 调度 galileo-alert-stat-analyzer，开始分析告警...
```

通过 `Agent` tool 启动 general-purpose agent，传入以下 prompt：

```
请走 galileo-alert-stat-analyzer 完整流程对以下告警链接做完整的告警分析，包含代码关联分析。

告警链接：{alert_link}

分析过程中请尽量找出一条代表性的告警 trace，记录其 traceID 以供后续使用。

分析完成后，请以如下结构化格式输出（供后续落表使用）：

---结构化结论---
alert_date: {告警触发日期，格式 yyyy-mm-dd}
alert_raw_title: {告警策略的完整原始标题，如「【新P1】【错误指标】大流量-1h（>=6000）-单模块【start】【step】【end】量级对比前1m上涨5%」；从 get_alert_detail 返回的告警策略名称字段提取}
problem_desc: {告警问题描述，含模块名 + 错误码 + 量级，150字以内}
alert_link: {原始告警链接}
root_cause: {问题原因分析，包含数据层 + 代码层 + 结论层，300字以内}
suggestion: {建议处理方式，格式为「建议屏蔽 — 原因」或「建议修复 — 原因」}
project: 营地
trace_example: {一条代表性告警 trace 的完整链接，格式为 https://galileo.woa.com/...?traceID=xxx；若无法获取则填「暂无」}
code_location: {与告警最相关的代码文件路径或类名/方法名，供责任人分配使用；若无法定位则填「暂无」}
---结构化结论结束---
```

等待分析器返回完整分析报告，**从报告中提取结构化结论字段**（`---结构化结论---` 块内的内容），存入本次任务上下文备用。

> **清单操作**：分析器返回完整报告后，将 `[ ] Step 2` 改为 `[x] Step 2`，输出更新后的清单。

## Step 3：代码调用链分析 + 代码修改

> ⛔ **门禁**：**禁止执行本步骤，除非 Step 0 ~ Step 2 已全部 ✅，且 Step 2 结构化结论中 `code_location` 字段已成功提取**。
>
> **清单操作**：输出清单，Step 3 标 `🔄`，校验 Step 0 ~ Step 2 已全部打勾。

调度 **dev-assistant** 对告警涉及的代码做完整的调用链深度分析，**并在分析完成后直接修改代码修复问题**。目标是从业务触发侧开始，逐层追踪到最终上报，找出每一步的关键代码位置，再针对根因实施修复。

输出调度提示：

```
🔬 调度 dev-assistant，进行代码调用链深度分析 + 代码修改...
```

通过 `Agent` tool 启动 `dev-assistant`，传入以下 prompt：

```
请对以下伽利略告警做完整的根因调用链代码分析，分析完成后直接修改代码修复问题。

告警问题描述：{problem_desc}
伽利略已定位的代码位置（末端）：{code_location}
根因分析（伽利略层）：{root_cause}
建议处理方式：{suggestion}

【第一阶段：调用链分析】
请在代码库中按以下维度分层追踪（不限于此，视实际代码结构灵活调整）：
1. 业务触发层：是哪个业务功能/前端操作/JS 调用触发了这条链路？
2. 路由/分发层：请求是如何被路由框架接收并分发的？
3. 中间层（如有）：调用了哪些中间件、SDK、管理类？
4. 系统调用层：最终触发了哪个系统 API？
5. Hook/上报层：伽利略 Hook 如何拦截并记录？

对每一层输出：
- 层级名称
- 关键代码文件路径 + 行号
- 核心代码片段（3~10 行）
- 这一层做了什么、为什么会传递到下一层

同时关注：
- 是否存在放大因子（SDK 内部重试、fallback 机制等导致 1 次业务调用 → N 次系统调用）
- 是否存在高频触发路径（循环、定时器、polling）
- 失败后是否有兜底/重试逻辑导致放大

最终以「调用链总图」格式输出从业务触发到上报的完整路径，并附关键 Bug 定位表（文件、行号、严重性）。

【第二阶段：代码修改】
基于上方调用链分析和根因，直接修改代码修复问题：
- 若 suggestion 为「建议修复」：找到根因代码位置，实施修复，输出修改的文件路径、修改前后对比
- 若 suggestion 为「建议屏蔽」：分析是否有代码层面可以减少误报的优化（如增加判断条件、调整上报逻辑），若有则修改；若纯配置屏蔽则跳过代码修改
- 若代码无法直接修改（如三方库、系统调用）：说明原因，输出替代方案或规避建议

修改完成后，以如下格式输出代码修改摘要：
---代码修改摘要---
modified_files: {修改的文件列表，每行一个路径}
fix_desc: {修复内容描述，100字以内}
fix_type: {修复类型：bug修复 / 防御性优化 / 无需修改}
---代码修改摘要结束---

工作目录：{代码库路径，从上下文获取}
```

等待 dev-assistant 返回完整报告，**提取以下字段**存入本次任务上下文备用：
- `call_chain_summary`：调用链总图（文字版，供落表 code_location 字段使用）
- `bug_list`：关键 Bug 定位表（文件 + 行号 + 严重性）
- `modified_files`：修改的文件列表
- `fix_desc`：修复内容描述
- `fix_type`：修复类型

> **清单操作**：dev-assistant 返回完整报告且代码修改（或跳过修改的判断）完成后，将 `[ ] Step 3` 改为 `[x] Step 3`，输出更新后的清单。

## Step 4：代码审查循环

> ⛔ **门禁**：**禁止执行本步骤，除非 Step 0 ~ Step 3 已全部 ✅**。若 Step 3 的 `fix_type` 为「无需修改」，则直接跳过本步骤（标为 `[x]` 并注明「跳过：无代码修改」），进入 Step 5。
>
> **清单操作**：输出清单，Step 4 标 `🔄`，校验 Step 0 ~ Step 3 已全部打勾。

对 Step 3 中 dev-assistant 的代码修改进行审查，不通过则打回重改，最多循环 **3 轮**。

输出调度提示：

```
🔍 调度代码审查小助手，审查代码修改（第 {N}/3 轮）...
```

**循环流程**（初始化 `review_round = 1`）：

**① 启动审查**：通过 `Agent` tool 启动 `cr-assistant`，传入以下 prompt：

```
你是代码审查小助手，请对以下代码修改进行审查。

告警问题描述：{problem_desc}
根因分析：{root_cause}
修复类型：{fix_type}
修复描述：{fix_desc}
修改文件列表：{modified_files}

请重点审查以下维度：
1. 修复是否针对了真正的根因（而非治标不治本）
2. 修改是否引入了新的 Bug 或潜在 Crash 风险
3. 边界条件和异常处理是否完善
4. 修改范围是否最小化（没有不必要的改动）
5. 代码风格是否符合项目规范

输出格式：
---审查结论---
result: 通过 / 不通过
issues: {若不通过，列出具体问题，每条独立一行；若通过则填「无」}
fix_instructions: {若不通过，给出明确的修改指示，dev-assistant 可直接按此执行；若通过则填「无」}
---审查结论结束---
```

**② 判断审查结果**：

- **通过** → 记录 `review_result = 通过`，退出循环，进入 Step 5
- **不通过且 `review_round < 3`** → 执行打回重改：
  ```
  ⚠️ 审查未通过（第 {N} 轮），打回 dev-assistant 重新修改...
  ```
  通过 `Agent` tool 启动 `dev-assistant`，传入以下 prompt：
  ```
  请根据代码审查意见，修改之前对以下告警的代码修复。

  原修复描述：{fix_desc}
  修改文件列表：{modified_files}

  审查发现的问题：
  {issues}

  修改指示：
  {fix_instructions}

  请按修改指示更新代码，完成后重新输出「---代码修改摘要---」块（格式同前）。
  工作目录：{代码库路径，从上下文获取}
  ```
  dev-assistant 返回后更新 `modified_files`、`fix_desc`、`fix_type`，`review_round += 1`，回到步骤 ①

- **不通过且 `review_round == 3`** → 已达最大轮次，不再重改：
  ```
  ⚠️ 代码审查循环已达最大轮次（3 轮），仍存在未解决问题，标记为「需人工复查」。
  ```
  记录 `review_result = 需人工复查`，退出循环，进入 Step 5

**输出审查摘要**：

```
📋 代码审查结果
  审查轮次：{N} 轮
  最终结论：{通过 / 需人工复查}
  {若需人工复查，列出未解决问题}
```

> **清单操作**：审查循环结束（通过或达最大轮次）后，将 `[ ] Step 4` 改为 `[x] Step 4`，输出更新后的清单。

## Step 5：责任人分配

> ⛔ **门禁**：**禁止执行本步骤，除非 Step 0 ~ Step 4 已全部 ✅，且 Step 2 结构化结论及 Step 3 调用链分析均已成功提取**。
>
> **清单操作**：输出清单，Step 5 标 `🔄`，校验 Step 0 ~ Step 4 已全部打勾。

调度**主程小助手**，综合 Step 2 伽利略分析出的代码位置 **以及 Step 3 调用链分析中识别出的各层关键文件**，确定建议处理人。

输出调度提示：

```
👤 调度主程小助手，确定告警责任人...
```

通过 `Agent` tool 启动 `tech-lead-assistant`，传入以下 prompt：

```
你是主程小助手，请根据以下伽利略告警的代码定位信息（包含调用链各层文件），通过 git log 查找最近活跃的开发者，确定建议处理人。

告警问题描述：{problem_desc}
代码位置信息（伽利略末端定位）：{code_location}
调用链各层关键文件（dev-assistant 深度分析）：{call_chain_summary}
根因分析：{root_cause}

请执行 code-owner-assigner 流程（读取 ~/.claude/skills/code-owner-assigner/SKILL.md），
输入模式：文件路径（优先从调用链各层关键文件中提取，覆盖业务触发层、路由层、核心实现层等所有层级的文件）。
若各层文件的 owner 不同，以「最靠近业务触发侧」的层级文件的 owner 为主，同时列出各层 owner 供参考。

输出格式：
---责任人结论---
assignee: {建议处理人姓名或 RTX，排名第一的开发者}
assignee_reason: {分配依据，如最近 N 天有相关文件的提交记录}
---责任人结论结束---

若代码位置信息为「暂无」或无法定位，则输出：
---责任人结论---
assignee: 暂无
assignee_reason: 代码位置未能定位，需人工判断
---责任人结论结束---
```

等待主程小助手返回责任人结论，**从报告中提取 `---责任人结论---` 块内容**，存入本次任务上下文备用。

> **清单操作**：主程小助手返回结论后，将 `[ ] Step 5` 改为 `[x] Step 5`，输出更新后的清单。

## Step 6：文档落表

> ⛔ **门禁**：**禁止执行本步骤，除非 Step 0 ~ Step 5 已全部 ✅**。
>
> **清单操作**：输出清单，Step 6 标 `🔄`，校验 Step 0 ~ Step 5 已全部打勾。

调度**文档小助手**将分析结论写入腾讯文档「伽利略任务记录」表格。

输出调度提示：

```
📝 调度文档小助手，将分析结论写入伽利略记录表...
```

## ══════════ 注意事项 ══════════

### 手动模式注意事项

- **每次响应第一行必须是清单**：无论任何情况，不得省略
- **门禁是硬性阻断**：前序未完成立即停止，不得以任何理由绕过
- **结构化结论提取**：Step 2 完成后必须从分析报告中提取 `---结构化结论---` 块内容，若分析器未按格式输出，主动从报告中归纳整理对应字段，再进入 Step 3
- **调用链 + 代码修改**：Step 3 完成后必须提取 `call_chain_summary`（分层代码位置）、`bug_list` 和代码修改摘要（`modified_files`、`fix_desc`、`fix_type`），作为 Step 4 审查和 Step 5 责任人分配的输入
- **代码审查跳过条件**：若 `fix_type` 为「无需修改」，Step 4 直接标 `[x]` 跳过，进入 Step 5
- **代码审查最大轮次**：3 轮，达到上限后标记「需人工复查」，不阻塞后续流程
- **责任人结论提取**：Step 5 完成后必须从报告中提取 `---责任人结论---` 块内容，若主程小助手未按格式输出，主动从报告中归纳 `assignee` 字段
- **code_location 落表**：Step 6 落表时，code_location 字段使用 Step 3 输出的调用链分层格式，而非 Step 2 的末端位置
- **trace_example 字段**：若分析器未能提供，在 Step 6 落表时填写「暂无」
- **project 字段**：默认填写「营地」，若用户在输入中指定了其他项目名则使用用户指定的值

### 自动巡检模式注意事项

- **P0/P1 判断以告警名称为准**：只要名称含「新P0」或「新P1」字样即纳入，不依赖其他字段
- **去重以 alert_instance_id 为唯一 key**：同一 instance 只分析一次，不因告警名称重复而重复分析
- **登记文件按月分块**：去重时只读当月和上月，无需全量扫描，性能稳定
- **登记文件写入时机**：Step P3 所有并行 Agent 返回后统一写入（手动模式在 Step 5 落表成功后写入）；失败的告警不写登记文件，待人工处理后可补录
- **登记文件不存在时**：首次运行自动创建，视为空登记，全部 Step P1 结果均待分析
- **并行上限 5 个**：超出时按优先级排序（P0 优先），分批执行，避免资源耗尽
- **子 Agent 失败不影响其他**：某条告警分析失败，其余继续执行，失败项在汇总报告中单独列出，标记「需人工处理」
- **时间窗口默认 24h**：用户指定其他窗口时（如「最近 48 小时」「过去 3 天」）按指定值执行
