# 批量模式流程（Batch Mode）

> 进入批量模式的条件：输入中明确包含 2 个及以上 userId，或用逗号/换行/列表分隔的多个用户/问题。

---

## 批量模式编排执行清单

**每次任务开始时初始化以下清单，每个 Step 执行前展示当前状态，执行完成后打勾。**

清单初始状态：

```
[ ] Step B1：域知识检索
[ ] Step B2：批量输入解析（所有用户-问题对已提取）
[ ] Step B3：批量确认（用户已确认所有条目）
[ ] Step B4：分析策略决策与执行（策略已决策，所有批次分析器已完成）
[ ] Step B5：各用户结论汇总
[ ] Step B6：跨用户规律分析
[ ] Step B7：修复建议与优先级排序
[ ] Step B8：域知识更新
```

### 批量清单使用规则

与单用户模式规则完全一致：
- 每次响应第一行必须是当前清单
- 前序 Step 未打勾，禁止执行后续 Step
- Step B3 必须等待用户回复确认后才能打勾

---

### ⛔ 批量模式全局强制规则

1. **每次响应第一行必须是批量清单**，格式标注 `[批量模式]`
2. **禁止在清单中存在未打勾的前序步骤时，输出任何分析内容**
3. **Step B3 自动继续**：展示批量确认卡片后，无需等待用户明确确认，直接进入 Step B4
4. **Step B4 并行度要求**：N 个用户 × M 个分析器 = N×M 个 Agent 调用，**必须在同一批次并行发出**，禁止串行等待

---

## Step B1：域知识检索

> 与单用户 Step 1 完全相同。读取共享知识 + 项目专属知识，为后续分析提供先验背景。

参考主文件「Step 1」章节执行，无差异。

> ⛔ **批量模式知识库禁令（与单用户完全一致）**：
> - 知识库命中只能作为背景参考，**严禁替代实际的 Bugly + 伽利略子智能体调用**
> - 即使今日已对同一批用户做过分析，也必须重新执行 Step B4 的 N×M 并行调用，获取当次 ANR/Crash 事件的实际 trace
> - ANR/Crash 场景必须使用 **精确时间点 ±5min 时间窗口**，禁止复用全天统计数据

> **清单操作**：Step B1 完成，标 `[x]`，输出更新后的清单。

---

## Step B2：批量输入解析

> ⛔ **门禁**：禁止执行，除非 Step B1 已 ✅。
>
> **清单操作**：输出清单，Step B2 标 `🔄`。

从用户输入中逐条提取每个用户的要素（userId/问题描述/发生时间必填，反馈来源/版本号/额外信息选填）：

| # | 要素 | 若缺失 |
|---|------|--------|
| userId | 数字用户 ID | 询问补充 |
| 问题描述 | 具体现象 | 从上下文推断，标注「（推断）」 |
| 发生时间 | YYYY-MM-DD HH:mm 或相对时间 | 默认今天，标注「（默认）」 |
| **反馈来源** *(选填)* | iFeedback URL / 水晶反馈 ID | 若存在则启用该用户的反馈日志分析器 |

### 输入处理规则（与单用户 Step 2 保持一致）

**输入中包含 iFeedback URL 或反馈系统链接**（URL 含 `ifeedback.qq.com` / `wzzs-manage` / `wzzs` 特征，或水晶反馈 ID）：
- 将其记录为对应条目的「反馈来源」
- 后续 Step B4 中该用户将额外启动反馈日志分析小助手（与其他分析器并行）

**输入中包含伽利略告警链接或 Bugly Issue 链接**（URL 含 `alert_instance_id` 或 `/crash-reporting/`、`/exception/crash|anr|foom/` 等特征）：
- 对每个链接，**调用 `营地问题前置信息提取助手`（camp-info-extractor）** 完成核心要素（userId/问题描述/发生时间）提取
- 多个链接并行提取，不串行等待
- **若 camp-info-extractor 返回结果中包含「分析时间窗口」字段**，将其附加到该条目的发生时间中：`{precise_time}（分析窗口：{analysis_start} ~ {analysis_end}）`
- 后续 Step B4 中该用户的伽利略分析器 prompt 必须带入此时间窗口

**输入是文字描述，且问题类型包含 ANR、Crash、崩溃、FOOM 关键词**：
- **优先调用 `营地问题前置信息提取助手`（camp-info-extractor）** 获取每个 userId 的精确发生时间戳和分析时间窗口
  - camp-info-extractor 会对每个 userId 并行查询 Bugly，获取精确 ANR/Crash/FOOM 发生时间，并计算前后各1小时的分析时间窗口
- 将 camp-info-extractor 返回的每个用户的「精确发生时间」和「分析时间窗口」填入对应用户的要素中
- **特别注意**：若 camp-info-extractor 返回结果中包含「分析时间窗口」字段，将其附加到该条目的发生时间中：`{precise_time}（分析窗口：{analysis_start} ~ {analysis_end}）`
- 后续 Step B4 中该用户的伽利略分析器 prompt 必须带入此时间窗口，禁止分析器自行扩展为全天范围

**输入是文字描述（非 ANR/Crash/FOOM 类型）**：
- 直接从文字中提取必填要素（userId/问题描述/发生时间），对模糊时间推断并标注「（推断）」

**解析后输出用户列表预览**：

```
📋 已解析到 N 个用户，等待确认...

  #1  userId: xxx  |  问题: ...  |  时间: ...（分析窗口：... ~ ...）  |  反馈来源: {url/id 或 无}
  #2  userId: yyy  |  问题: ...  |  时间: ...  |  反馈来源: 无
  ...
```

若某条用户信息关键字段缺失（userId 为空），在列表中标注 `⚠️ 缺少 userId`，并在 Step B3 确认卡片中一并询问用户补充。

> **清单操作**：Step B2 完成，标 `[x]`，输出更新后的清单。

---

## Step B3：批量确认

> ⛔ **门禁**：禁止执行，除非 Step B1、B2 已全部 ✅。
>
> ⛔ **硬性等待**：展示确认卡片后，禁止继续执行任何后续步骤，必须等待用户明确回复确认。
>
> **清单操作**：输出清单，Step B3 标 `🔄`。

输出批量确认卡片：

```
📋 批量排查确认 — 共 N 个用户

  #1  userId: {userId}  |  问题: {问题描述}  |  时间: {时间}
  #2  userId: {userId}  |  问题: {问题描述}  |  时间: {时间}
  ...（每行一个用户）

请确认以上信息是否正确。
如需修改某条，请告诉我条目编号（如「#2 的时间改为 2024-03-01」）。
确认后我将同时启动所有用户的分析。
```

用户确认后进入 Step B4。用户修正某条 → 更新对应条目，重新展示确认卡片。

> **清单操作**：用户确认后，Step B3 标 `[x]`，输出更新后的清单。

---

## Step B4：分析策略决策与执行（批量）

> ⛔ **门禁**：禁止执行，除非 Step B1 ~ B3 已全部 ✅，且 B3 是用户在本对话中明确确认后打勾的。
>
> **清单操作**：输出清单，Step B4 标 `🔄`。

### B4.1 逐用户 AI 自主选择分析器

> ⛔ **subagent_type 填写规则（硬性约束，同单用户 Step 5，不得违反）**：
> 1. **必须对照主文件顶部「分析器注册表」逐行取值**，将表中 `subagent_type` 列的值原封不动填入 Agent tool 的 `subagent_type` 参数
> 2. **禁止凭记忆、感觉或"更合适"的理由替换** `subagent_type`
> 3. **Agent ≠ Skill**：注册表中均为 Agent，Skills 不能作为 `subagent_type` 传入，两者绝对不可混用
> 4. **CLAUDE.md 歧义澄清**：同单用户 Step 5 规则第 4 条——在本文件内部通过 Agent tool 调度注册表中的子分析器完全合法，即使子分析器本身是编排型角色也必须用 Agent tool 启动，不得绕过。

与单用户 Step 5.1 **完全相同的选择逻辑**，对每个用户独立判断应启用的分析器：
- 根据该用户的问题描述，结合注册表「能力描述」列自主选择分析器
- 选择规则同单用户 Step 5.1（无崩溃不选 Bugly，无反馈来源且非投诉不选日志助手，投诉类必选日志助手）

**输出批量 AI 选择卡片**：

```
📋 批量分析器选择

  #1 userId={userId1}  已选：[{分析器A}、{分析器B}]  理由：{一句话}
  #2 userId={userId2}  已选：[{分析器A}、{分析器C}]  理由：{一句话}
  ...
```

### B4.2 系统推导每个用户的执行计划（硬编码时序约束）

对每个用户独立检查注册表「串行约束」列，与单用户 Step 5.2 **完全相同的检查逻辑**：
- 若该用户选中了伽利略 **AND** bugly-assistant → **串行两阶段**
- 否则 → **全量并行**

**输出批量执行计划卡片**：

```
📊 批量执行计划

  #1 userId={userId1}  执行方式：{串行两阶段 | 全量并行}
  #2 userId={userId2}  执行方式：{串行两阶段 | 全量并行}
  ...
```

> ⛔ **混合执行提示**：若批量用户中同时包含串行和全量并行：
> - 所有**全量并行**用户的分析器，在同一批次并发发出
> - 所有**串行**用户的 Phase 1（Bugly），也在同一批次并发发出
> - 等待所有串行用户的 Phase 1 返回后，再统一发出其 Phase 2 调用

### B4.3 按计划执行

> ⛔ **N×独立调用硬性规则（不得以任何理由违反）**：
> 1. **每个用户 × 每个分析器 = 一个独立 Agent 调用**，禁止把多个 userId 合并进同一个 Agent 调用
> 2. **违规识别**：如果在某个分析器的 prompt 里出现了多个 userId 列表，这就是违规——立即停止，重新拆分为独立调用
> 3. **唯一例外**：若某用户的某个分析器因要素不足被跳过，该格子可留空，但其余格子仍必须独立调用

**执行逻辑**（依据 B4.2 计划结果）：

```
批次 1（所有全量并行用户的全部分析器 + 所有串行用户的 Phase 1 Bugly）：
  全量并行用户 #i  →  [已选分析器列表]（同时发出）
  串行用户 #j      →  Bugly（Phase 1，等待结果后才启动伽利略）
  ...所有以上调用在同一批次并发发出，等待全部返回...

批次 2（串行用户 Phase 2，注入 Phase 1 的 Bugly 时间戳后启动伽利略及其余分析器）：
  串行用户 #j  →  伽利略（注入 Bugly 精确时间戳）+ 其余已选分析器
  ...所有 Phase 2 调用在同一批次并发发出，等待全部返回...
```

每个分析器的 prompt 格式与单用户 Step 5 标准 prompt 模板相同（参见 `camp-problem-analyzer-references/prompt-templates.md`），添加批量上下文标注 `批量任务 #i，共 N 个用户`。串行用户的 Phase 2 分析器，额外追加 Bugly 结论注入块（与单用户 Step 5.3 执行方式 A Phase 2 的注入块完全一致）。

等待所有批次的分析器全部返回后，进入 Step B5。

> **清单操作**：所有批次执行完毕后，Step B4 标 `[x]`，输出更新后的清单。

---

## Step B5：各用户结论汇总

> ⛔ **门禁**：禁止执行，除非 Step B1 ~ B4 已全部 ✅，且所有分析器结果已收到。
>
> **清单操作**：输出清单，Step B5 标 `🔄`。

收集所有分析器输出，按用户编号逐条展示精简结论：

```markdown

- **Bugly**：{核心发现，1-2 行}
- **初步判断**：{最可能根因，1 行}

## 用户 #2（userId: yyy）
- **伽利略**：{核心发现，1-2 行}
- **Bugly**：{核心发现，1-2 行}
- **初步判断**：{最可能根因，1 行}

...（每个用户一节）
```

> **清单操作**：汇总完成后，Step B5 标 `[x]`，输出更新后的清单。

基于规律分析，输出按影响范围排序的修复建议：


## 批量模式注意事项

- **模式识别是第一步**：收到输入后，先判断单用户还是批量模式，再初始化对应清单，禁止混用两套清单
- **Step B4 先选择再执行**：必须输出批量 AI 选择卡片（B4.1）和批量执行计划卡片（B4.2）后再执行；伽利略与 Bugly 同时被选中的用户自动串行两阶段（Phase 1 全并发 → 等返回 → Phase 2 全并发），其余用户全量并行；禁止逐用户串行等待
- **Step B3 展示确认卡片后直接继续**：批量确认卡片展示后，无需等待用户回复，直接进入 Step B4。若用户提出修正，更新后重新展示并重跑 Step B4
