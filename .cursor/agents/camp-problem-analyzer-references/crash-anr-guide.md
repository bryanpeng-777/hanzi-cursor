# Crash / ANR 分析专项指南

---

## 单用户模式：精确时间点分析（Crash 和 ANR 场景通用）

当问题描述包含「Crash」「崩溃」或「ANR」时，**伽利略日志的分析方式必须优化为「精确时间点定位」**，替代默认的全天日志统计。

### 核心思路

```
① Bugly 分析器 → 获取该用户 Crash/ANR 的精确发生时间戳
② 伽利略分析器 → 以该时间为基准，仅取前后 5 分钟的日志
③ 分析单次 Crash/ANR 触发链路（而非统计全天累计数字）
```

### 在 Step 5 伽利略分析器 prompt 中追加

```
## Crash/ANR 精确时间点分析（优化方法，必须遵守）

本问题类型为 Crash/ANR。禁止拉取全天日志做累计统计，必须按以下步骤执行：

1. **先获取精确发生时间**：
   - 若 Bugly 分析器已返回结论，从中提取该用户 Crash/ANR 的精确时间戳
   - 若尚未获得，先主动查询 Bugly Issue 中该用户的上报时间（取最近一次）
2. **以该时间为基准，仅查询前后 5 分钟的伽利略日志**（替代全天查询）
3. **重点关注时间窗口内**：
   - FlutterEngineCreateToFirstFrameInit（start/end 成对，计算单次 Engine 初始化耗时）
   - FlutterContainerLifeCycle（孤悬的 start 无对应 end = 主线程阻塞点，ANR 专属）
   - FlutterViewErrorShow（触发 Engine 销毁的错误时刻）
   - NetRequest（接口失败与重试风暴的精确时序）
   - 崩溃前最后几条日志（定位 Crash 触发的业务上下文）
4. **按时间顺序还原单次触发链路**（目标：10~20 条日志完整还原）
5. **Engine 初始化次数口径**：FlutterEngineCreateToFirstFrameInit 日志条数 ÷ 2 = 实际次数（start+end 成对）
```

### 价值对比

| 维度 | 全天统计（旧） | 精确时间点定位（新） |
|------|-------------|-------------------|
| 数据量 | 数千条全天日志 | 10~20 条关键日志 |
| 计数指标 | 全天累计，易误导严重程度判断 | 单次触发周期，口径准确 |
| 触发链路 | 无法还原 | 按时序完整还原 |
| 崩溃前上下文 | 被全天噪音淹没 | 清晰可见 |
| Watchdog 阈值验证（ANR）| 无法做到 | Bugly 入库时间 - 伽利略孤悬时刻 ≈ Watchdog 5s + 上报延迟 |

## 单用户模式：FOOM 专项分析

当问题描述包含「FOOM」时，**伽利略日志的分析方式必须切换为「FOOM 内存堆积路径分析」**，与 Crash/ANR 的精确时间点分析不同——FOOM 不是瞬间崩溃，而是内存持续累积后被系统强杀，因此需要还原用户在被杀前的完整操作路径，找到内存堆积的来源。

### 核心思路

```
① Bugly 分析器 → 获取该用户 FOOM 的发生时间（系统强杀时刻）
② 伽利略分析器 → 以该时间为终点，向前拉取 30 分钟的 Trace 日志
③ 专项检查 A：页面多次打开检测（同一页面 start 次数统计）
④ 专项检查 B：用户操作路径分析（完整导航序列 + 循环/深栈识别）
```

### 在 Step 5 伽利略分析器 prompt 中追加

```
## FOOM 专项分析（必须遵守）

本问题类型为 FOOM（内存超限被系统强杀）。FOOM 不是瞬间崩溃，而是内存持续累积的结果，
分析目标是找到内存堆积的操作路径，而非单点崩溃时刻。禁止按 Crash/ANR 精确时间点方式分析，必须按以下步骤执行：

1. **时间范围**：以 FOOM 发生时刻为终点，向前拉取 **30 分钟**的伽利略日志（覆盖内存积累过程）

2. **专项检查 A：页面多次打开检测**
   - 查询 `moduleName=FlutterContainerLifeCycle`，提取所有 `start` 事件，按页面名称（pageName 或 route）分组统计
   - 重点关注：**同一页面 start 次数 ≥ 3 次**（提示可能存在重复入栈、未正常销毁的情况）
   - 输出格式：
     | 页面名 | start 次数 | end 次数 | 差值（未释放） |
     |--------|-----------|---------|--------------|
     | user_home | 5 | 3 | +2（可疑） |
     | discovery | 2 | 2 | 0（正常） |
   - 对「差值 > 0」的页面重点标注，说明可能的内存泄漏风险

3. **专项检查 B：用户操作路径分析**
   - 从 `moduleName=FlutterContainerLifeCycle` 的 `start` 事件中，按时间顺序提取完整的页面跳转序列
   - 同时补充 `moduleName=InnerRouter` / `OutRouter` 中的路由跳转记录，两者合并还原完整导航链路
   - 重点识别以下异常模式：
     - **循环导航**：A→B→A→B 往复跳转（提示每次打开都在堆叠新页面）
     - **深栈累积**：连续打开 5 个以上页面未返回
     - **重复触发入口**：短时间内（5 分钟内）多次进入同一功能模块
   - 输出完整操作序列（时间戳 + 页面名），标注异常片段

4. **综合结论**：
   - 说明最可能导致内存堆积的操作序列
   - 估算问题触发前页面栈深度（未释放 start 总数）
   - 给出最可疑的内存泄漏页面/模块
```

### 价值说明

| 维度 | 不加专项检查 | 加 FOOM 专项检查 |
|------|------------|----------------|
| 分析时间范围 | ±5min 精确时间点（适合 Crash） | 30min 内存积累过程 |
| 页面分析 | 无 | 同一页面 start/end 差值，识别未释放页面 |
| 操作路径 | 无 | 完整导航序列 + 循环/深栈识别 |
| 根因定位 | 只能说「发生了 FOOM」 | 能指出「哪个页面被多次打开/未释放」 |

## 批量模式：11 项指定模式检测

**用于 Step B6 跨用户规律分析**。11 项模式必须逐项执行，不可省略。

每项结论格式为 `✅ 是（X/N 人）` 或 `❌ 否` 或 `⚠️ 数据不足`，并附简短说明。

---

### 模式 1：广告页跳转

**检测目标**：各用户是否均从广告页跳转后触发问题。

查找依据：`moduleName=InnerRouter` / `OutRouter` 中是否含有广告相关路由关键字（`ad`、`promo`、`activity`、`landing`、`banner`、`push`）

| userId | 是否来自广告页 | 广告来源/路由 |
|--------|-------------|-------------|
| {userId1} | 是 / 否 / 不确定 | {路由或来源描述} |

**结论**：{X/N 个用户来自广告跳转}

---

### 模式 2：退后台行为

**检测目标**：各用户是否均在问题发生前退过后台。

查找依据：`moduleName=FlutterContainerLifeCycle` 中是否存在 `background` / `foreground` 状态切换记录

| userId | 是否退过后台 | 后台时长（若可知） |
|--------|-----------|----------------|
| {userId1} | 是 / 否 / 不确定 | {时长或不可知} |

**结论**：{X/N 个用户存在退后台行为}

---

### 模式 3：相似操作路径

**检测目标**：各用户是否具有高度相似的操作序列。

基于「共性操作路径」表格中已提取的跳转链路做相似度横向比较：
- 路径完全相同：高度相似
- 路径部分重合（包含公共子序列）：中度相似
- 路径差异较大：低相似

**结论**：{高度相似 / 中度相似 / 差异显著 / 数据不足}——{描述共同路径片段或主要分歧点}

---

### 模式 4：相同进入界面

**检测目标**：各用户是否均进入过同一个界面（问题触发前的关键页面相同）。

查找依据：「共性操作路径」表格中「问题触发页面」列

| 页面名称 | 出现次数 | 出现用户 |
|---------|--------|---------|
| {页面A} | N1 | userId1, userId2 |

**结论**：{是（X/N 人到达相同页面）/ 否 / 数据不足}

---

### 模式 5：相同最终停留界面

**检测目标**：各用户问题发生时最后停留/卡住在同一个界面。

查找依据：`moduleName=FlutterContainerLifeCycle` 中最后一次 `start` 事件（无对应 `end` = 用户最终停在此页）

| userId | 最终停留页面 | 来源（路由日志 / lifecycle） |
|--------|-----------|--------------------------|
| {userId1} | {页面名} | {来源} |

**结论**：{是（X/N 人停在相同界面）/ 否 / 数据不足}

---

### 模式 6：网络状态

**检测目标**：各用户是否均在相同的网络条件下（弱网、断网、Wi-Fi、蜂窝）触发问题。

查找依据：`moduleName=NetRequest` 中请求的耗时、超时、失败率

| userId | 网络状况（推断） | 关键证据 |
|--------|--------------|---------|
| {userId1} | 弱网 / 断网 / 正常 / 不确定 | {超时次数/失败率等} |

**结论**：{是（X/N 人处于相似网络条件）/ 否 / 数据不足}

---

### 模式 7：App 启动类型

**检测目标**：各用户触发问题时 App 处于何种启动状态（冷启动、热启动、从后台恢复）。

查找依据：
- `moduleName=FlutterEngineCreateToFirstFrameInit`：存在 = 冷启动
- `moduleName=FlutterContainerLifeCycle`：仅有 `foreground` 事件、无 Engine 初始化 = 热启动/从后台恢复

| userId | 启动类型 | Engine 初始化次数 |
|--------|---------|----------------|
| {userId1} | 冷启动 / 热启动 / 后台恢复 / 不确定 | {次数} |

**结论**：{X/N 人启动类型相同}

---

### 模式 8：App 连续运行时长

**检测目标**：各用户在触发问题前 App 已持续运行多长时间。

查找依据：问题发生时间 - 当天最早一条日志时间 = 本次会话运行时长（粗估）

| userId | 运行时长（估算） | 计算依据 |
|--------|--------------|---------|
| {userId1} | {X 分钟 / X 小时} | {日志起始时间 → 问题时间} |

**结论**：{长时间运行（>X 分钟）/ 短时间（刚启动）/ 分布不一致 / 数据不足}

---

### 模式 9：账号特征

**检测目标**：各用户是否具有共同的账号属性（会员状态、绑定游戏账号、注册时长、所在地区等）。

查找依据：日志中是否存在账号相关上报字段（`vip_level`、`game_bound`、`region`、`account_age` 等）

| userId | 账号特征（可观测到的） |
|--------|-------------------|
| {userId1} | {VIP / 非VIP / 已绑定游戏 / 新用户 / …} |

**结论**：{是（X/N 人有共同账号特征）/ 否 / 数据不足}

---

### 模式 10：前置触发动作

**检测目标**：各用户在问题发生前的最后一个具体操作动作是否相同。

查找依据：
- 问题发生时间戳前最近的 `NetRequest` 记录（最后调用了什么接口）
- 最近的业务 module 上报（最后触发了什么业务动作）

| userId | 最后触发动作 | 时间距问题发生 |
|--------|-----------|-------------|
| {userId1} | {接口名/业务动作名} | {X 秒前} |

**结论**：{是（X/N 人最后操作相同）/ 否 / 数据不足}——这通常是复现步骤的最后一步

---

### 模式 11：日志错误模板聚类（跨用户）

**检测目标**：对多个用户的问题时间窗口日志做模板聚类，找出在多用户中同时出现的高频错误模板。

**执行方式**：使用 Galileo CLI `galileo logs analyze templates` 命令，逐用户拉取模板聚类结果，再横向合并比较。

```bash
# 对每个 userId 分别执行（时间窗口取该用户问题发生时刻前后各 10 分钟）
galileo logs analyze templates \
  --query 'tags.userId=<userId_N> AND NOT level=info' \
  --input '{
    "start": "<该用户问题时间 - 10min>",
    "end": "<该用户问题时间 + 10min>",
    "target": "iOS.camp-app",
    "namespace": "Production",
    "tags": ["tags.moduleName", "tags.ret_code"]
  }'
```

> 若多用户时间窗口重叠，可合并为一次查询：
> `--query 'tags.userId=<userId1> OR tags.userId=<userId2> OR tags.userId=<userId3>'`

从每个用户的模板聚类结果中提取 Top 5 高频模板，横向比较：

| 模板内容（精简） | userId1 出现 | userId2 出现 | userId3 出现 | 跨用户频次 |
|------------|:-----------:|:-----------:|:-----------:|:--------:|
| `{模板A}` | ✅ N1次 | ✅ N2次 | ❌ | 2/N 人 |
| `{模板B}` | ✅ N3次 | ✅ N4次 | ✅ N5次 | 3/N 人 |

**跨用户共性模板**（出现在 ≥ 50% 用户中）：
```
{列出跨用户高频模板原文}
```

**结论**：{X/N 个用户共享相同的错误日志模板，核心共性模板为「{模板描述}」，根因集中在 {一句话描述}}
