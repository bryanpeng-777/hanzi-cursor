# Oncall 小助手 — 统一调度中心

接收一切 oncall 相关事务，智能分配给对应子技能处理，完成后自动积累域知识。

支持两种工作模式：
- **巡检模式**：自动拉取我的待处理 Oncall → 分类分配 → 调度对应小助手排查 → 等用户确认关闭
- **常规模式**：处理指定工单或直接调用子技能处理 oncall 事务

---

## 模式判断（入口，优先执行）

> ⛔ **门禁**：收到用户输入后，**第一个动作**必须是判断模式，输出模式确认信息，再进入对应流程。

根据用户输入判断：

| 条件 | 模式 |
|------|------|
| 输入含「巡检」「看看我的工单」「有没有新工单」「查一下工单」 | **巡检模式** → 进入 Step J0 |
| 输入含工单 ID、工单链接、「处理 oncall」「拉工单」「值班」「当班」，或无法判断 | **常规模式** → 进入 Step 0 |

输出模式确认：
```
🔀 模式：{巡检模式 / 常规模式}
```

---

## ══════════ 巡检模式 ══════════

## 编排执行清单（巡检模式）

**每次任务开始时初始化清单，每个 Step 执行前展示当前状态，执行完成后打勾。**

清单初始状态：

```
[ ] Step J0：拉取最新 Oncall（我的待处理工单）
[ ] Step J1：工单分类（分配给对应小助手）
[ ] Step J2：调度对应小助手排查问题
[ ] Step J3：等待用户确认（关闭 / 保留工单）
```

### 清单使用规则

**执行前**：每个 Step 开始前，输出当前清单，当前步骤标 `🔄`：

```
📋 执行进度
  ✅ Step J0：拉取最新 Oncall
  🔄 Step J1：工单分类    ← 当前
  ⬜ Step J2：调度对应小助手排查问题
  ⬜ Step J3：等待用户确认
```

**执行后**：Step 完成后将该项改为 `✅`，再输出一次更新后的清单。

**前序校验**：执行任意 Step Jn 前，检查 Step J0 ~ Step Jn-1 是否已全部打勾。若发现未完成项，**必须先补做该步骤，不得跳过**。

---

### ⛔ 巡检模式全局强制规则（优先级最高）

1. **每次响应的第一行必须是当前执行清单**，格式严格按照上方示例，不得有任何例外
2. **禁止在清单中存在未打勾的前序步骤时，输出任何分析内容或工具调用**
3. **Step J3 是硬性等待**：输出排查结论后必须停下来等用户确认，禁止自动关闭工单

---

## Step J0：拉取最新 Oncall（我的待处理工单）

> ⛔ **门禁**：这是第一步，无前序依赖。响应第一行输出清单，Step J0 标 `🔄`。

调用 Oncall MCP 工具拉取我的待处理工单：

```
工具：get_my_pending_incidents
参数：limit=20（默认拉最近 20 条）
状态过滤：Triggered / Acknowledged（待处理状态）
```

输出拉取结果：

```
📋 我的待处理 Oncall 工单（共 {N} 条）

| # | 工单ID | 标题 | 级别 | 状态 | 来源 |
|---|--------|------|------|------|------|
| 1 | xxxxx  | xxx  | S1   | Triggered | galileo |
| 2 | xxxxx  | xxx  | S2   | Acknowledged | bugly |
```

若无待处理工单：
```
ℹ️ 当前没有待处理的 Oncall 工单，巡检结束。
```
→ 直接输出完成信息，结束流程。

> **清单操作**：Step J0 完成，将 `[ ] Step J0` 改为 `[x] Step J0`，输出更新后的清单。

---

## Step J1：工单分类（分配给对应小助手）

> ⛔ **门禁**：**禁止执行本步骤，除非 Step J0 已 ✅**。
>
> **清单操作**：输出清单，Step J1 标 `🔄`，校验 Step J0 已打勾。

对 Step J0 拉取的每条工单，根据工单标题、来源、详情判断应分配给哪个小助手：

**分类规则**：

| 工单特征 | 分配给 |
|---------|--------|
| 来源为 `galileo` / 标题含「告警」「监控」「伽利略」「上升」「超时」「失败率」 | **伽利略告警登记小助手** |
| 来源为 `bugly` / 标题含「崩溃」「crash」「ANR」「FOOM」「OOM」 | **bugly-assistant（Bugly小助手）** |
| 无法判断 | 标记为「待人工分类」，询问用户 |

输出分类结果：

```
🗂️ 工单分类结果

| # | 工单ID | 标题 | 分配给 |
|---|--------|------|--------|
| 1 | xxxxx  | xxx  | 伽利略告警登记小助手 |
| 2 | xxxxx  | xxx  | Bugly小助手 |
| 3 | xxxxx  | xxx  | ⚠️ 待人工分类 |
```

若有「待人工分类」的工单，输出：
```
⚠️ 以下工单无法自动判断类型，请告知应分配给哪个小助手：
  • 工单 {ID}：{标题}
  [A] 伽利略告警登记小助手  [B] Bugly小助手  [C] 跳过
```
等用户回复后更新分类，再进入 Step J2。

> **清单操作**：Step J1 完成，将 `[ ] Step J1` 改为 `[x] Step J1`，输出更新后的清单。

---

## Step J2：调度对应小助手排查问题（并行）

> ⛔ **门禁**：**禁止执行本步骤，除非 Step J0 ~ Step J1 已全部 ✅**。
>
> **清单操作**：输出清单，Step J2 标 `🔄`，校验 Step J0 ~ Step J1 已全部打勾。

对所有已分类工单，**并行**启动对应小助手进行排查。

**并行数量限制**：
- 工单 ≤ 5 条：全部并行启动（`run_in_background: true`）
- 工单 > 5 条：分批执行，每批最多 5 条，按优先级排序（S0 > S1 > S2），上一批全部完成后启动下一批

输出调度提示：

```
🚀 并行启动 {N} 个排查任务...
  • 任务 1：工单 {ID1}（{标题}） → 伽利略告警登记小助手
  • 任务 2：工单 {ID2}（{标题}） → Bugly小助手
  ...
（最多并行 5 个，超出部分按优先级分批排队）
```

**调度伽利略告警登记小助手**（通过 `Agent` tool，`subagent_type: "伽利略告警登记小助手"`，`run_in_background: true`）：

```
⛔ 角色边界（最高优先级）：你是执行者，不是编排者。请直接分析本条工单，禁止通过 Agent tool 再 spawn 新 Agent 来执行分析流程，否则会导致重复处理。

工单ID：{incident_id}
工单标题：{title}
工单详情：{detail}

请先调用 oncall MCP 工具 incident_detail 获取工单完整详情，从中提取伽利略告警链接（alert_instance_id）。
若找到告警链接，调用伽利略 MCP 工具对告警做完整分析（落表步骤跳过，只输出分析结论）。
若未能提取到告警链接，请根据工单标题和详情进行分析，输出根因推断和处理建议。

分析完成后，以如下格式输出结论供主流程使用：
---Oncall排查结论---
incident_id: {incident_id}
assistant: 伽利略告警登记小助手
root_cause: {根因分析，150字以内}
suggestion: {建议处理方式：建议关闭—原因 / 建议保留—原因}
---Oncall排查结论结束---
```

**调度 Bugly 小助手**（通过 `Agent` tool，`subagent_type: "bugly-assistant"`，`run_in_background: true`）：

```
⛔ 角色边界（最高优先级）：你是执行者，不是编排者。请直接分析本条工单，禁止通过 Agent tool 再 spawn 新 Agent 来执行分析流程，否则会导致重复处理。

工单ID：{incident_id}
工单标题：{title}
工单详情：{detail}

请先调用 oncall MCP 工具 incident_detail 获取工单完整详情，从中提取 Bugly issue 链接或 issue ID。
若找到 Bugly 链接，执行完整的崩溃分析流程（堆栈分析、影响范围、责任人判断）。
若未能提取，请根据工单标题和详情进行分析，输出根因推断和处理建议。

分析完成后，以如下格式输出结论供主流程使用：
---Oncall排查结论---
incident_id: {incident_id}
assistant: Bugly小助手
root_cause: {根因分析，150字以内}
suggestion: {建议处理方式：建议关闭—原因 / 建议保留—原因}
---Oncall排查结论结束---
```

等待所有并行 Agent 返回，收集每个 Agent 的 `---Oncall排查结论---` 块内容，汇总所有工单的排查结论。

**子 Agent 失败处理**：某条工单分析失败，其余继续，失败项在 Step J3 汇总时单独标注「⚠️ 分析失败，需人工处理」。

> **清单操作**：所有 Agent 均返回结果后，将 `[ ] Step J2` 改为 `[x] Step J2`，输出更新后的清单。

---

## Step J3：等待用户确认（关闭 / 保留工单）

> ⛔ **门禁**：**禁止执行本步骤，除非 Step J0 ~ Step J2 已全部 ✅**。此步骤是**硬性等待**，必须停下来等用户回复，禁止自动操作工单。
>
> **清单操作**：输出清单，Step J3 标 `🔄`，校验 Step J0 ~ Step J2 已全部打勾。

汇总输出所有工单的排查结论，等待用户确认每条工单的处理方式：

```
📊 巡检排查结论汇总

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
工单 {ID}：{标题}
🤖 分析方：{小助手名称}
🔍 根因：{root_cause}
💡 建议：{suggestion}
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

（... 每条工单一块 ...）

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
请确认每条工单的处理方式：

工单 {ID1}（{标题}）：
  [A] 关闭 — 告警误报  [B] 关闭 — 无需处理  [C] 保留处理中  [D] 保留待观察

工单 {ID2}（{标题}）：
  [A] 关闭 — 告警误报  [B] 关闭 — 无需处理  [C] 保留处理中  [D] 保留待观察
```

**等待用户回复**（⛔ 硬性等待，不得跳过）。

用户回复后，对选择「关闭」的工单执行关闭操作：

```
工具：close_my_incident
参数：
  incident_id: {incident_id}
  reason: {对应关闭原因：告警误报 / 无需处理}
  note: {根因摘要，从 root_cause 字段截取}
```

输出操作结果：

```
✅ 工单 {ID}（{标题}）已关闭
   关闭原因：{reason}

⏸️ 工单 {ID}（{标题}）已保留，状态：{保留处理中 / 保留待观察}
```

> **清单操作**：用户确认完成、所有操作执行完毕后，将 `[ ] Step J3` 改为 `[x] Step J3`，输出最终清单：

```
📋 执行进度（巡检完成）
  ✅ Step J0：拉取最新 Oncall
  ✅ Step J1：工单分类
  ✅ Step J2：调度对应小助手排查问题
  ✅ Step J3：等待用户确认

🎉 Oncall 巡检完成！
```

## Step 1：意图识别与子技能分配

根据用户输入判断调用哪个子技能：

```
用户输入
├── 提到「工单」「处理 oncall」「拉工单」「值班」「当班」「有没有工单」
│   └── → oncall-handler（完整工单处理闭环）
│
├── 提到某个具体工单 ID 或工单链接
│   └── → oncall-handler（直接处理指定工单）
│
└── 无法判断
    └── 询问用户："你希望我帮你做什么？
        1. 拉取并处理当前待处理工单
        2. 处理指定工单"
```

识别后输出：

```
🔍 意图识别：<识别到的任务类型>
📦 调用子技能：oncall-handler
```

读取并完整执行对应子技能的 SKILL.md：

- `oncall-handler` → `~/.claude/skills/oncall-handler/SKILL.md`

子技能执行完毕后，继续执行 Step 3。

## Step 3：域知识更新判断（处理完成后执行）

oncall-handler 完成当次工单处理、输出处理小结后，判断本次处理是否产生了有价值的新知识：

**首先判断知识归属**：
- 知识涉及特定项目的业务逻辑、模块名、告警惯例 → 写入 `knowledge/{project}/`（`{project}` 即 Step 0 检测到的项目名）
- Oncall 平台操作、通用处置套路、团队约定、MCP 工具用法 → 写入 `knowledge/shared/`
- 有歧义时输出：「这条经验是否项目专属？[A] 是 → `knowledge/{project}/` [B] 否 → `knowledge/shared/`」

| 情况 | 写入目标 | 操作 |
|------|---------|------|
| **新工单模式**：处理了一类 incident-patterns.md 未记录的问题类型或根因 | `{归属}/incident-patterns.md` | 新增结构化条目 |
| **补充已有模式**：命中已有条目但有新的处置细节或反例 | `{归属}/incident-patterns.md` | 更新该条目及「最后更新」日期 |
| **新常识**：发现平台参数、MCP 用法、团队约定等背景知识 | `{归属}/reference.md` | 自由格式追加到对应二级标题下 |
| **重复已知内容** | — | 跳过，不写 |

**incident-patterns.md 条目格式**：

```markdown
## <模式名称>（如：伽利略告警误报-流量放量）

- **工单类型**：伽利略告警 / Bugly 崩溃 / 其他
- **识别特征**：xxx（工单标题/详情中的关键词或特征）
- **处置套路**：xxx（分析步骤、判断依据、常见结论）
- **关闭原因**：告警误报 / 无需处理 / 需代码修复
- **首次记录**：yyyy-mm-dd
- **最后更新**：yyyy-mm-dd
```

**reference.md 写入格式**：自由 Markdown，归入对应二级标题（`## 平台参数` / `## MCP 工具说明` / `## 团队约定`），无固定结构要求。

有写入时，push 到 GitHub：

```bash
cd ~/.claude/knowledge && git add oncall-assistant/ && git commit -m "knowledge(oncall): 新增/更新 <内容摘要>" && git push origin main
```

## ══════════ 注意事项 ══════════

- **「Oncall小助手」是专属触发词**：收到此词时，禁止直接调用单个子技能，必须走本技能完整调度流程
- **巡检模式优先清单**：说「巡检」时必须走 Step J0~J3 清单流程，不得直接调用 oncall-handler
- **域知识优先**：Step 0 命中历史模式时，将其注入 oncall-handler 的分析上下文，加速处理
- **落表由子助手负责**：伽利略和 Bugly 的分析结论由 伽利略告警登记小助手 / bugly-assistant 各自落表，oncall-assistant 不重复落表
- **域知识更新不强求**：重复工单跳过，只有真正有新发现才写入，保持知识库精简
- **Step J3 是硬性等待**：排查结论输出后必须等用户逐一确认，任何情况下不得自动关闭工单
